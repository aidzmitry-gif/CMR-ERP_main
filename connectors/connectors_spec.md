# ТЗ: коннекторы сбора данных для гибридной RAG-базы

Документ — бриф на реализацию для кодинг-агента (Claude Code). Описывает слой
«сбор» (ingestion connectors): что собрать, откуда, как и в каком виде отдать.
Требования помечены как `FR-*` (функциональные) и `NFR-*` (нефункциональные)
для трассируемости. В конце — критерии приёмки и инструкция для агента.

---

## 1. Контекст и цель

Строим внутреннюю базу знаний для команды на собственном сервере (одна нода,
RTX 3090). Данные из нескольких систем собираются, нормализуются LLM-куратором,
эмбеддятся и кладутся в гибридный RAG-индекс (Qdrant), по которому в фоне работает
агент. Этот документ покрывает только **сбор данных из источников**. Транскрипция
звонков, LLM-курирование, эмбеддинг и запись в Qdrant — отдельный воркер, вне
области данного ТЗ.

Источники: **1С**, **Bitrix24 (облако)** — звонки и данные CRM, **Google Docs и
Google Sheets**.

## 2. Область работ

В объёме:
- Три коннектора: Bitrix24, 1С, Google.
- Общая модель записи и контракт вывода (очередь).
- Хранилище курсоров (инкрементальная выгрузка).
- Оркестратор запуска (CLI + пригоден к запуску как фоновый демон).
- Конфигурация через переменные окружения.

Вне объёма (отдельные компоненты, только обозначить точки стыка):
- ASR (faster-whisper) по записям звонков.
- LLM-куратор, эмбеддинг (BGE-M3), реранкер, запись в Qdrant.
- Очередь dead-letter и супервизор демона (коннекторы лишь кладут записи в `inbox/`).

## 3. Стек и ограничения

- Python 3.11+.
- Зависимости минимальны: `requests`, `tenacity`, `python-dotenv`,
  `google-api-python-client`, `google-auth`. Без тяжёлых фреймворков (без Airflow,
  Celery и т.п.) — это должен быть лёгкий пакет, запускаемый и из CLI, и по таймеру.
- Только чтение из источников (никаких записей в 1С/Bitrix/Google).
- Секреты — только через окружение/.env, никогда в коде, в репозитории и в логах.
- Стиль: типизация (type hints), докстринги, без сторонних линтер-зависимостей.

## 4. Архитектура и поток данных

```
Источники            Коннекторы (это ТЗ)              Очередь            Дальше (вне ТЗ)
─────────            ───────────────────              ───────            ───────────────
1С (OData)      ─┐
Bitrix24 (REST) ─┼─►  pull (инкремент по курсору) ─►  data/inbox/*.json ─►  воркер:
Google (API)    ─┘    + скачивание записей звонков ─► data/media/*.mp3      ASR → куратор →
                                                                            эмбеддинг → Qdrant
```

Коннекторы тянут данные инкрементально и кладут каждую запись отдельным JSON-файлом
в `data/inbox/`, а аудио звонков — в `data/media/`. Курсоры хранятся в
`data/state.json`. Воркер (отдельно) забирает файлы из `inbox/`.

## 5. Модель данных

Все коннекторы отдают единый объект `RawRecord` (сырьё до курирования):

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `source` | str | да | `bitrix_call` \| `bitrix_deal` \| `bitrix_contact` \| `bitrix_company` \| `onec` \| `gdoc` \| `gsheet` |
| `source_id` | str | да | уникальный идентификатор внутри источника |
| `record_type` | str | да | `call` \| `deal` \| `contact` \| `company` \| `document` \| `spreadsheet` \| `1c_entity` |
| `payload` | dict | да | структурированные данные источника как есть |
| `fetched_at` | str (ISO-8601, UTC) | да | момент выгрузки |
| `media_path` | str \| null | нет | локальный путь к скачанной записи звонка |
| `source_url` | str \| null | нет | ссылка в исходной системе (провенанс) |

- `FR-1`: вычисляемый ключ `unit_id = "{source}:{source_id}"` — сквозной идентификатор
  для дедупа и upsert ниже по конвейеру.

## 6. Контракт вывода (очередь)

- `FR-2`: каждая запись пишется отдельным JSON-файлом в `data/inbox/`.
- `FR-3`: имя файла детерминированное и стабильное: `{source}_{sha1(unit_id)[:16]}.json`.
  Повторная выгрузка той же сущности перезаписывает тот же файл (идемпотентность).
- `FR-4`: запись файла атомарна (через временный файл `.tmp` + `os.replace`).
- `FR-5`: записи звонков скачиваются в `data/media/{call_id}.mp3`; путь кладётся в `media_path`.
- `FR-6`: курсоры выгрузки хранятся в `data/state.json` (атомарная запись).

## 7. Функциональные требования по коннекторам

### 7.1 Bitrix24 (облако)

Авторизация:
- `FR-10`: доступ через **входящий вебхук**, URL целиком берётся из `BITRIX_WEBHOOK`
  (вид `https://<портал>.bitrix24.ru/rest/<user_id>/<код>/`).
- Требуемые права вебхука: `telephony`, `crm`, `user`, `disk`. У пользователя
  вебхука должно быть право «Статистика звонков — Просмотр».

Звонки:
- `FR-11`: метод `voximplant.statistic.get` (списочный). Значимые поля ответа:
  `ID`, `CALL_ID`, `CALL_START_DATE`, `CALL_TYPE`, `PORTAL_USER_ID` (оператор),
  `PHONE_NUMBER`, `CALL_DURATION`, `CRM_ENTITY_TYPE`, `CRM_ENTITY_ID`,
  `RECORD_FILE_ID` (файл записи), `TRANSCRIPT_ID`, `TRANSCRIPT_PENDING`.
- `FR-12`: инкремент по курсору `ID`: фильтр `{">ID": last_id}`, сортировка
  `{"ID": "ASC"}`, постраничный обход через `start`/`next`.
- `FR-13`: для каждого звонка скачать запись. Алгоритм: если в записи есть прямая
  ссылка (`CALL_RECORD_URL` или эквивалент) — использовать её; иначе по
  `RECORD_FILE_ID` вызвать `disk.file.get` и взять `DOWNLOAD_URL`. Скачивание
  идемпотентно (если файл уже есть — не качать повторно). Имя поля прямой ссылки
  может отличаться между порталами — заложить фолбэк через Disk API.
- `FR-14`: курсор `last_id` обновляется **только после** того, как потребитель
  обработал запись (resume-after-yield), чтобы падение не приводило к пропуску.

Данные CRM:
- `FR-15`: методы `crm.deal.list`, `crm.contact.list`, `crm.company.list`,
  тот же инкремент по `ID` (фильтр `>ID`, сортировка `ID ASC`, пагинация),
  `select: ["*", "UF_*"]` для всех стандартных и пользовательских полей.

Лимиты и устойчивость:
- `FR-16`: соблюдать лимиты интенсивности облака — мягкая пауза между запросами
  (настраиваемый `min_interval`), backoff и повтор при ошибках `QUERY_LIMIT_EXCEEDED`,
  `OVERLOAD_LIMIT` и HTTP 429/5xx.
- `FR-17`: для массового бэкофилла предусмотреть использование метода `batch`
  (объединение вызовов) — как минимум оставить точку расширения.
- Замечание для эксплуатации: записи в облаке расходуют квоту диска портала и могут
  ротироваться — бэкофилл истории запускать как можно раньше.

### 7.2 1С (OData)

Авторизация:
- `FR-20`: стандартный интерфейс OData 1С, базовый URL из `ONEC_BASE_URL`
  (вид `http://<сервер>/<база>/odata/standard.odata/`), HTTP Basic из
  `ONEC_USER`/`ONEC_PASSWORD`.

Выгрузка:
- `FR-21`: состав объектов задаётся конфигом `ONEC_ENTITY_SETS` — список словарей:
  `{name, key_field, date_field?, select?}`. `name` — имя набора сущностей
  (`Catalog_*`, `Document_*`, `AccumulationRegister_*` и т.п.), `key_field` —
  поле ключа (обычно `Ref_Key`).
- `FR-22`: запрос с параметрами `$format=json`, `$top`, `$skip` (пагинация),
  `$orderby`, опционально `$select`.
- `FR-23`: если задан `date_field` — инкремент через `$filter` по этому полю
  (фильтр «больше последнего значения курсора»). Если `date_field` нет — полный
  проход (на текущих объёмах дёшево; дубли отсекаются дедупом ниже).
- Замечание: синтаксис литерала даты в `$filter` может зависеть от версии платформы
  1С — выделить в одно место и пометить как настраиваемое.

### 7.3 Google (Docs + Sheets)

Авторизация:
- `FR-30`: сервисный аккаунт, путь к JSON-ключу из `GOOGLE_CREDENTIALS_FILE`.
  Включить в проекте Google Cloud: Drive API, Docs API, Sheets API.
- `FR-31`: доступ к контенту — либо расшаривание папок/файлов на e-mail сервисного
  аккаунта, либо domain-wide delegation с имперсонацией пользователя из
  `GOOGLE_IMPERSONATE`. Scopes — read-only (`drive.readonly`, `documents.readonly`,
  `spreadsheets.readonly`).

Выгрузка:
- `FR-32`: обход заданных папок `GOOGLE_FOLDER_IDS`; в каждой — листинг файлов через
  Drive `files.list` с фильтром по `mimeType` (Google Doc и Google Sheet),
  пагинация через `pageToken`, поддержка shared drives.
- `FR-33`: инкремент по `modifiedTime` (курсор на папку: максимальное виденное значение).
- `FR-34`: Google Docs — экспорт в текст (`files.export_media`, `text/plain`;
  допустимо `text/markdown`), результат в `payload.text`.
- `FR-35`: Google Sheets — чтение значений по всем листам (метаданные листов →
  `spreadsheets.values.get` по каждому), результат в `payload.sheets`
  (словарь «лист → массив строк»).

## 8. Нефункциональные требования

- `NFR-1` Инкрементальность: повторный запуск продолжает с курсора, не выгружая всё заново.
- `NFR-2` Идемпотентность: повторная обработка одной сущности безопасна (детерминированное
  имя файла, дедуп по `unit_id`, пропуск уже скачанного аудио).
- `NFR-3` Отказоустойчивость: ретраи с экспоненциальной паузой на временные ошибки
  (сеть, лимиты, 5xx); один «плохой» элемент (например, удалённая запись звонка)
  не должен останавливать весь прогон — логировать и продолжать.
- `NFR-4` Без пропусков: курсор продвигается только после успешной фиксации записи.
- `NFR-5` Наблюдаемость: структурное логирование (источник, сколько обработано, ошибки).
  Желательно вывести счётчики для последующего мониторинга (объём за прогон, ошибки).
- `NFR-6` Безопасность: секреты только в окружении; не логировать токены, ключи,
  ссылки с авторизацией; не коммитить `.env` и JSON-ключ.
- `NFR-7` Производительность: целевые объёмы малы (история ~1000+ звонков, ~60/день),
  оптимизация под пропускную способность и устойчивость, не под параллелизм.

## 9. Конфигурация (переменные окружения)

| Переменная | Назначение |
|---|---|
| `DATA_DIR` | корневая папка вывода (по умолчанию `./data`) |
| `BITRIX_WEBHOOK` | URL входящего вебхука Bitrix24 |
| `ONEC_BASE_URL` | URL службы OData 1С |
| `ONEC_USER`, `ONEC_PASSWORD` | учётка 1С (Basic) |
| `GOOGLE_CREDENTIALS_FILE` | путь к JSON сервисного аккаунта |
| `GOOGLE_FOLDER_IDS` | ID папок Drive через запятую |
| `GOOGLE_IMPERSONATE` | e-mail для domain-wide delegation (опционально) |

`ONEC_ENTITY_SETS` задаётся в `config.py` (зависит от конфигурации 1С).

## 10. Структура проекта

```
connectors/
  __init__.py
  config.py        # чтение настроек из окружения
  models.py        # RawRecord
  state.py         # StateStore (курсоры, атомарная запись)
  bitrix.py        # BitrixConnector: fetch_calls(), fetch_crm()
  onec.py          # OneCConnector: fetch()
  gdrive.py        # GoogleConnector: fetch()
  run.py           # оркестратор: persist() + CLI
requirements.txt
.env.example
README.md
```

CLI:
```
python -m connectors.run               # все источники
python -m connectors.run bitrix        # только Bitrix24
python -m connectors.run onec google   # выбранные источники
```

## 11. Граничные случаи и обработка ошибок

- Запись звонка отсутствует/удалена (ротация хранилища) → залогировать, `media_path=null`, продолжить.
- Прямой ссылки на запись нет → фолбэк через `disk.file.get`.
- Достигнут лимит интенсивности Bitrix → backoff и повтор.
- Частично скачанный файл → писать во временный `.part` и переименовывать по завершении.
- Объект 1С без поля даты → полный проход (без инкремента).
- Нестандартный синтаксис фильтра даты в 1С → вынести в одно настраиваемое место.
- Нет доступа к Google-файлу/папке → залогировать и пропустить, не падать.
- Пустой Google Sheet/лист → вернуть пустой массив, не падать.

## 12. Критерии приёмки (Definition of Done)

- [ ] Все три коннектора реализованы и собирают данные согласно `FR-*`.
- [ ] Записи появляются в `data/inbox/` в формате `RawRecord`; звонки — в `data/media/`.
- [ ] Повторный запуск без изменений в источниках не создаёт дублей и не качает аудио заново.
- [ ] Инкремент работает: второй запуск тянет только новое (проверяемо по `state.json`).
- [ ] Падение/перезапуск в середине прогона не приводит к пропуску записей.
- [ ] Временные ошибки (429/5xx/лимиты) переживаются ретраями, один плохой элемент не валит прогон.
- [ ] Секретов нет ни в коде, ни в логах; `.env` и ключ — в `.gitignore`.
- [ ] `python -m py_compile connectors/*.py` проходит без ошибок.
- [ ] Юнит-тесты на разбор ответов и логику курсора с замоканными HTTP-вызовами
      (источники в тестах не дёргать). Покрыть: пагинацию, продвижение курсора,
      идемпотентность имени файла, фолбэк скачивания записи.
- [ ] `README.md` описывает подготовку доступов, установку и запуск.

## 13. Заметки по реализации и ссылки

- Bitrix24 REST: справочник API — https://apidocs.bitrix24.ru/ ; метод
  `voximplant.statistic.get`; лимиты — раздел про интенсивность и метод `batch`.
- 1С OData: стандартный интерфейс OData (публикация на веб-сервере), параметры
  `$filter`/`$top`/`$skip`/`$orderby`/`$select`, `$format=json`.
- Google: Drive API (`files.list`, `files.export`), Sheets API (`spreadsheets.values.get`),
  сервисные аккаунты и domain-wide delegation.
- Два места, заведомо требующие подгонки под конкретную среду: имя поля прямой
  ссылки на запись звонка в Bitrix (фолбэк через Disk API уже предусмотрен) и
  синтаксис фильтра по дате в OData 1С.

## Приложение. Как использовать с Claude Code

1. Положить этот файл в репозиторий (например, `docs/SPEC.md`) и открыть проект в Claude Code.
2. Дать задачу: «Реализуй пакет `connectors/` строго по `docs/SPEC.md`; сверяйся с
   секциями `FR-*`/`NFR-*` и выполни все пункты Definition of Done».
3. Просить агента двигаться по источникам по очереди (Bitrix → 1С → Google), после
   каждого — прогон `py_compile` и юнит-тесты с замоканным HTTP.
4. Реальные доступы (вебхук, ключ Google, учётка 1С) подключать в самом конце,
   на этапе ручной проверки, а не во время кодинга.
