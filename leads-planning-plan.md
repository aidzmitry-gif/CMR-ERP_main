# План лидов — лидоруб собирает, РОП согласует

> Сгенерировано веером агентов (4 цикла исследования Sonnet 5 → синтез Opus 4.8 → сборка HTML Sonnet 5). Локальный черновик-план. BYN. Экран — `leads-planning-preview.html`.

## Суть

План лидов — это ВЕРХ воронки, который спец по лидам (лидоруб) собирает снизу вверх от своих же фактических данных модуля (скоринг, срок ответа, конверсии по источникам, ёмкость) и отправляет РОПу на согласование по образцу /crm/deals/planning (табы «Собрать» → «Согласование»). Он не дублирует месячный план продаж (plan_item), а ПИТАЕТ его: цель по выручке из plan_item реверсируется через обратную воронку в целевое число сырых лидов по каналам. Ключевой принцип — план считается от денег собственнику (цель #1), а не от активности: сырые счётчики звонков/лидов исключены как метрики тщеславия, формула выполнения — только квалифицированные лиды, ставшие сделкой/КП. Цикл согласования честный: РОП возвращает только с обязательным комментарием, лидоруб имеет право на 1 контрпредложение, дальше — эскалация. Экран — новый соседний файл rop-planning-*.html с живым пересчётом обратной воронки и кнопкой «Отправить РОПу на согласование».

## Обратная воронка (цель по деньгам → сырые лиды)

```
ОБРАТНАЯ ВОРОНКА (путь от выручки к лидам), считается СВЕРХУ ВНИЗ от цели по выручке. Коэффициенты берём из СВОЕГО факта за 90 дней (модуль лидов + продажи), норма по отрасли — только стартовая точка при нехватке истории.

Формула (сверху вниз):
  Сделок нужно            = Цель по выручке / Средний чек
  Готовых лидов нужно     = Сделок нужно / Доля сделок (готовый лид → сделка)
  Тёплых обращений нужно  = Готовых лидов нужно / Конв(тёплое обращение → готовый лид)
  Сырых лидов нужно       = Тёплых обращений нужно / Конв(сырой → тёплое обращение, порог авто-скоринга)
  Требуемая сумма сделок в работе = Цель по выручке / Доля сделок   (= запас воронки (раз) × Цель)

Пример (металлопрокат, BYN, 1 лидоруб, 26 раб. дней, вс выходной):
  Цель выручки .............. 1 200 000 BYN/мес   ← якорь из plan_item (план продаж), только для чтения
  Средний чек ............... 20 000 BYN          → Сделок нужно = 60
  Доля сделок: готовый лид→сделка . 20% (свой, 90 дн)   → Готовых лидов нужно = 60 / 0.20 = 300
  Конв. тёплое обращение→готовый лид . 14%          → Тёплых обращений нужно = 300 / 0.14 ≈ 2 143
  Конв. сырой→тёплое обращение (скоринг) . 35%      → Сырых лидов нужно ≈ 6 122 (≈ 235/раб.день)
  Требуемая сумма сделок в работе ........ 1 200 000 / 0.20 = 6 000 000 BYN  (запас воронки 5 раз — норма для доли сделок 15-25%)

Сверка снизу вверх (метод ёмкости): ёмкость 1 лидоруба ≈ 60 сырых/день (с попытками дозвона, график работы 9-18) → ~1 560/мес. Разница между расчётом сверху вниз (6 122) и снизу вверх (1 560) = дефицит ~4 560 лидов → это особенность экрана: план подсвечивает разрыв и предлагает РОПу выбор — (а) поднять качество источников (сырой→тёплое обращение 35%→50% через скоринг/метку источника урезает потребность), (б) второй лидоруб, (в) скорректировать план продаж вниз. Число не «придумано» — оно предзаполнено реверсом и защищается цифрой.

Микс каналов (70/20/10 + порог стоимости привлечения клиента), плановые сырые лиды раскладываются по источникам:
  Проверенные 70% (органика/почта-тёплая база/сарафан) — конверсия сырой→КП выше нормы рынка
  Рост 20% (платная реклама в поиске, отраслевые витрины) — масштаб только при доходе к затратам на привлечение ≥ 3:1
  Эксперимент 10% (платная реклама в соцсетях, рефералы из ИИ-поиска) — авто-флаг «стоимость привлечения выросла >25% за 2 мес → урезать»
Каждый канал сравнивается с внешней нормой рынка по конверсии (разница в процентных пунктах), а не оценивается голым объёмом.
```

## Что заполняет лидоруб (входы плана)

- Цель по выручке месяца (BYN) — НЕ вводится вручную, подтягивается из plan_item (план продаж) как якорь реверса только для чтения; лидоруб видит источник цифры.
- Средний чек и доля сделок (готовый лид→сделка) — авто-подстановка из факта продаж за 90 дней; лидоруб может переопределить с обоснованием (отклонение от базовой подсвечивается РОПу).
- Конверсии воронки: сырой→тёплое обращение (порог скоринга), тёплое обращение→готовый лид — свои фактические из модуля; калибровка ≤90 дней (иначе план помечается предупреждением).
- По КАЖДОМУ каналу/источнику: плановое число сырых лидов на месяц, ожидаемая конверсия сырой→КП, метка группы 70/20/10 (проверенный/рост/эксперимент).
- Бюджет/усилие по каналу (BYN) — для расчёта стоимости привлечения клиента и порога доход/затраты на привлечение ≥ 3:1; авто-флаг перераспределения бюджета при росте стоимости привлечения >25% за 2 мес.
- Ёмкость лидоруба (снизу вверх): сырых лидов/день физически при графике работы 9-18 и попытках дозвона; коэффициент разгона новичка для нового сотрудника (первые 4-8 недель).
- Сезонный коэффициент месяца, разложенный min на 2 компоненты: строительный сезон (пик апрель-октябрь) и бюджетный цикл конца года (декабрь); хранится как данные, не хардкод, с обоснованием ('прошлый год +34% в мае').
- Отдельная группа РЕЦИКЛА: число лидов «не сейчас» в базе + ожидаемая конверсия за квартал + частота касаний (2 нед / 6 нед / квартал) — считается отдельно от новых лидов.
- Обоснование по каждой строке плана — выбор источника-агрегата из выпадающего списка (конв. по метке источника, средняя скорость ответа, историческая ёмкость) + свободный текст; без обоснования план нельзя отправить.

## Цикл согласования (лидоруб → РОП)

Статусы и переходы (макс. 2 круга, дальше эскалация — не бесконечный пинг-понг):

1. draft (Черновик) — лидоруб на табе «Собрать». Реверс предзаполнен от plan_item; каждая строка требует обоснования (источник-агрегат + текст). Пока нет обоснования по строке — кнопка «Отправить РОПу» заблокирована.
   → submitted

2. submitted (Отправлен РОПу) — план заморожен для правок лидоруба, виден на табе «Согласование» у РОП с оба-числами (реверс сверху вниз vs ёмкость снизу вверх, дельта) и флагами (доход к затратам <3:1, стоимость привлечения↑>25%, калибровка >90 дн, отклонение от базовой цифры).
   → approved  или  → returned

3. approved (Согласован) — РОП жмёт «Утвердить». План лидов фиксируется как активный, его целевые Σ КП/сделки становятся входом для plan_item (план продаж). Далее — скользящий режим (см. раздел «Ритм»).

4. returned (Возвращён с правкой) — РОП жмёт «Вернуть»; поле комментария ОБЯЗАТЕЛЬНО (пустой отправить нельзя). Лидоруб видит комментарий.
   → resubmitted

5. resubmitted (Повторно отправлен) — лидоруб делает ОДНУ повторную подачу с новым числом + новым обоснованием, отвечая на комментарий.
   → approved  или  → escalated

6. escalated (Эскалация) — при повторном отказе РОП план НЕ теряется тихо: попадает на видное место в кокпите РОП/скорборде передач с зафиксированным расхождением (позиция лидоруба vs позиция РОП) для решения следующим уровнем/собственником. Каждый переход логируется через outbox → AuditLog.

Правило цикла согласования: РОП не переписывает цифры лидоруба сам (это ломает честность расчёта снизу вверх) — он либо утверждает, либо возвращает с обоснованием; финальное число всегда авторства лидоруба.

## Ритм

Скользящий ежемесячный пересчёт плана с 4 еженедельными чекпоинтами (не фиксируется на квартал залпом). Месячный lead_plan_item пересматривается по неделям: система показывает план/факт с начала месяца (посуточно уже есть) + прогноз «дотянет ли до плана» (аналог гэп-до-плана из доски продавца, слайс 3), считая по КВАЛИФИЦИРОВАННОМУ факту (лид с КП / маршрутизированный = квалифицирован; входящий необработанный — нет). Опережающие показатели (срок ответа, конверсия скоринга, дозвон) смотрят еженедельно ДЛЯ КОУЧИНГА и НЕ входят в формулу выполнения. Итоговые показатели (квалиф. лиды→сделки, Σ КП) смотрят ежемесячно ДЛЯ РАСЧЁТА выполнения. При отклонении недельного факта от плана сверх порога (напр. −15%) лидоруб ОБЯЗАН подать корректировку через тот же цикл Собрать→Согласование, а не ждать конца месяца — иначе недобор выручки прячется от РОП до последнего дня.

## Экран — блоки (спецификация экрана)

### Шапка плана лидов + статус + действие
Определение периода и текущего состояния цикла согласования; главная точка отправки на согласование.

_Контролы:_ Селектор периода (месяц); статус-бейдж (Черновик/Отправлен/Согласован/Возвращён/Повторно/Эскалация); имя лидоруба; кнопка «Отправить РОПу на согласование» (заблокирована, пока не заполнены обоснования); вторичная «Сохранить черновик».

### Якорь: цель по выручке (из плана продаж)
Показать, ОТ ЧЕГО считается реверс — цель #1 деньги; убрать ощущение «придумай цифру».

_Контролы:_ Карточка только для чтения: Цель выручки BYN/мес из plan_item со ссылкой-провенансом на /crm/deals/planning; средний чек и доля сделок (авто из продаж, кнопка «переопределить» с обоснованием).

### Живой калькулятор обратной воронки
Реверс выручка→готовый лид→тёплое обращение→сырые лиды с моментальным пересчётом при правке любого коэффициента.

_Контролы:_ 5 уровней-строк с формулами и числами; редактируемые поля конверсий (сырой→тёплое обращение, тёплое обращение→готовый лид, доля сделок); авто-пересчёт «Сырых лидов нужно/мес и /раб.день»; индикатор даты последней калибровки скоринга (⚠ если >90 дн).

### План сырых лидов по каналам (микс 70/20/10)
Раскладка требуемого объёма по источникам с контролем качества, а не только объёма.

_Контролы:_ Таблица: канал/метка источника | план сырых лидов | ожид. конверсия сырой→КП | норма рынка по типу | разница п.п. | группа 70/20/10 | бюджет BYN | стоимость привлечения | доход к затратам. Флаги: «ниже нормы рынка», «стоимость привлечения↑>25%→урезать», «доход к затратам<3:1→обоснуй». Строка «Итого» сверяется с калькулятором воронки.

### Ёмкость снизу вверх vs потребность сверху вниз (дельта)
Сверка реальности: физическая ёмкость лидоруба против требуемого от цели — ядро честного плана.

_Контролы:_ Поле ёмкости (сырых/день) + коэффициент разгона новичка (для нового); авто-расчёт ёмкость/мес; блок «Дельта = потребность − ёмкость» с цветом; при дефиците — предложения (поднять качество / второй лидоруб / скорректировать план продаж вниз).

### Сезонная корректировка
Отличить рост амбиций от объективной сезонности металлопроката в РБ.

_Контролы:_ Множитель месяца, разложенный на компоненты (строительный сезон / бюджетный цикл конца года); показ плана ДО и ПОСЛЕ сезонной корректировки; поле обоснования с прошлогодним фактом.

### Бакет отложенных «не сейчас» (отдельно)
Не терять медленную, но реальную конверсию реанимированных лидов в общем плане/факте.

_Контролы:_ Число лидов среди отложенных; ожид. конверсия за квартал; частота касаний (2 нед / 6 нед / квартал); отдельная плановая Σ КП по отложенным, не смешанная с новыми лидами.

### Панель показателей: опережающие (недельно) vs итоговые (месяц)
Разделить коучинговые сигналы и метрики выполнения; исключить тщеславные счётчики.

_Контролы:_ Две колонки: Опережающие (норматив ответа <5мин, конв. скоринга, дозвон, запас воронки) — помечены «коучинг, не выполнение»; Итоговые (квалиф.→сделки, Σ КП BYN, доход к затратам, конв. отложенных) — «расчёт выполнения»; целевые значения; «число созданных лидов» ЯВНО помечено как не показатель эффективности.

### Обоснование + история согласования
Прозрачность источника цифр и аудит цикла Собрать→Согласование.

_Контролы:_ По каждой строке — выбор источника-агрегата + текст; лента статусов с комментариями РОП (обязательными при возврате); счётчик кругов (1/2); при escalated — блок расхождения «позиция лидоруба vs РОП»; повтор действия «Отправить/Вернуть» по роли.

- Дочерняя таблица lead_plan_channel (строка канала плана): plan_id FK, source/utm, planned_raw_leads, exp_conv_raw_kp, bucket enum(proven/growth/experiment), budget_byn, cac_byn, ltv_cac, benchmark_conv — для микса 70/20/10 и флагов.
- Дочерняя таблица lead_plan_justification: plan_id/строка, aggregate_source enum (conv_by_utm/avg_sla/historic_capacity/...), value_base (авто), value_override, comment — реализует правило «нет обоснования → нет согласования».

**Цикл согласования** реализован как реальный стейт-машин (не просто визуал): draft → submitted → returned (комментарий обязателен, блокируется без него) → resubmitted (круг 2) → approved/escalated (2 круга максимум, дальше расхождение выносится в отдельный блок «позиция лидоруба vs РОП»). Проверено сквозным JS-прогоном всей цепочки состояний — работает корректно.

**Найденный и исправленный баг при верификации:** изначально `applyTheme()` вызывался до объявления `const $`, что через temporal dead zone тихо останавливало весь скрипт (без видимой ошибки в консоли до целевой проверки) — поправлено порядком объявлений. Второй баг: `setTab()` и `setRole()` вызывали друг друга безусловно → бесконечная рекурсия (`Maximum call stack size exceeded`) при любом клике по вкладке/роли, из-за чего кнопки «Утвердить/Вернуть» у РОПа не разблокировались после первого переключения роли. Обе функции слиты в одну `applyRole()` без рекурсии. После фикса весь сценарий (расчёт, реюз каналов, ROP-флаги, возврат/эскалация, обе темы) проверен через headless-браузер и работает без ошибок в консоли.

**Честные заглушки:** данные — металлопрокат, BYN, реалистичные (цель 1 200 000 BYN/мес, 60 сделок, требуемая сумма сделок в работе 6 000 000 BYN, дефицит ёмкости ≈4560 сырых/мес — намеренно показан как факт, а не скрыт).
