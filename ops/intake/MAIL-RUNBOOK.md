# Почтовый сборщик: подготовленный этап

`mail_stage.py` — автономный сборщик в очередь для admin@enersys.by.
На сервер он ещё не установлен, реальное подключение не проверено.
Пароль приложения необходим для первого IMAP-входа.

Он использует только IMAP с TLS, EXAMINE/readonly и BODY.PEEK[]. Не отправляет
письма, не удаляет, не переносит и не помечает их прочитанными. SMTP не используется.
Кандидаты и письма для разбора сохраняются в закрытой SQLite-базе вместе
с оригиналом; вложения не запускаются и не теряются из оригинала.

`mail_delivery.py` связывает сборщик, `mail_receipts.py` и `receipt_queue.py`:
оригинал MIME и неизменяемый запрос сохраняются до сети, повтор использует тот
же delivery_id. Только GET со статусом delivered, номером лида и хешами вложений
помечает доставку подтверждённой. Код подготовлен и проверен на синтетических
письмах, но на сервере ещё не запущен. Категория `candidate` —
техническая предварительная классификация, а не подтверждённый клиентский лид.
На реальной выборке нужно проверить правила, извлечение вложений и устранение
копий из сборщика order@microchips.by. Разные закупки одного заказчика нельзя
объединять только по email, даже если существующий CRM endpoint умеет это делать.

## Подготовленный порядок запуска на Linux после доступа

1. Сохранить имя ящика и отдельный пароль приложения в закрытый JSON-файл
   вне репозитория. Образец — `mail-config.example.json`; права реального
   файла `0600`, каталог `0700`. Не использовать обычный пароль аккаунта.
2. Один раз выполнить `init`: он фиксирует границу новых писем по UIDNEXT,
   не импортируя старую историю. Дата этой границы должна совпадать с
   согласованным началом импорта. Повторный init запрещён.
3. Выполнить `poll`, проверить очередь и оригиналы сообщений. Один запуск
   ограничен 50 письмами; большие письма остаются отмеченными для разбора,
   без скачивания MIME более 32 MiB. Приёмник принимает до 8 вложений,
   10 MiB каждое и 20 MiB суммарно. Неподдерживаемый формат остаётся для разбора.
4. Только после проверки реальных примеров включать подготовленную доставку
   из очереди в CRM и расписание. Ни таймер, ни периодическая задача пока
   не созданы.

Команды ниже — инструкция; в этом проходе на сервере они не выполнялись:

```sh
python3 mail_delivery.py init --config /etc/crm-intake/admin-enersys-mail.json --queue /var/lib/crm-intake/mail.sqlite3
python3 mail_delivery.py poll --config /etc/crm-intake/admin-enersys-mail.json --queue /var/lib/crm-intake/mail.sqlite3
python3 mail_delivery.py status --queue /var/lib/crm-intake/mail.sqlite3
```

`mail_delivery.py` держит non-blocking flock на весь запуск. Каталог очереди
должен существовать с правами 0700. JSON дополнительно содержит существующий
CRM intake token; обычный пароль Яндекс и секреты в репозиторий не записывать.

Legat и копии сайта сейчас остаются в review: необходимы реальные примеры с
точными tender/lot/template либо form/result ID. Рассылки и служебные письма
не отправляются как клиентские лиды; оригиналы сохраняются. `status` показывает
счётчики причин разбора; готового уведомления в интерфейсе CRM пока нет.

## Проверки

Локальные unittest используют только синтетические письма и подменённый IMAP.
Они не доказывают доступ к реальному ящику или создание лида в рабочей CRM.

```sh
python -m unittest -v test_mail_stage test_mail_receipts test_mail_delivery test_receipt_queue
```
