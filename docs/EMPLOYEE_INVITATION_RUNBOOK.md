# Приглашение сотрудника: production runbook

> Назначение: безопасно включить и проверить внутренний сценарий приглашения. Все команды на сервере выполняет **оператор** вручную; секреты, SMTP-пароли, токены и тела писем не копируются в чат, git или логи.

## Что делает сценарий

1. Уполномоченный сотрудник выбирает существующего активного HR-сотрудника, вручную указывает его корпоративный email, отдел и будущую роль. В текущей HR-карточке email не хранится, поэтому соответствие HR ID и адреса подтверждается оператором перед отправкой.
2. ERP проверяет HR-запись, затем создаёт Keycloak-пользователя и посылает одноразовое письмо `VERIFY_EMAIL` + `UPDATE_PASSWORD`.
3. Новый пользователь получает только realm-role `onboarding`: в ERP доступен лишь экран ознакомления, без списков, CRM, модулей и данных других сотрудников.
4. Будущие отдел и роль сохранены как ожидаемые. Рабочий доступ выдаёт отдельно директор/уполномоченный руководитель после проверки; приглашавший не может активировать его сам.

**Запрещено:** использовать этот runbook для реального сотрудника, пока оператор не подтвердит непосредственно перед отправкой точные ФИО, корпоративный email, HR ID, отдел и будущую роль.

## 1. Предварительные гейты — без них стоп

- Релиз собран с одним Alembic head и с проверенными `upgrade → downgrade -1 → upgrade`; применяется общий [RELEASE checklist](../coordination/RELEASE.md).
- До deploy запустить локальный offline-гейт исходников (он не читает `.env`, не обращается к сети и не выводит значения секретов):

  ```sh
  python scripts/invitation_release_gate.py
  ```

  Он проверяет один Alembic head, миграции `0108`–`0110` с реальным `downgrade`, обязательные имена переменных в этом runbook и статические production-guards настроек. Успех этого гейта не заменяет проверку работающего контейнера ниже.
- Серверное дерево `/opt/cmr-erp` чистое, известны текущий SHA и точка rollback.
- Прод-контейнер работает именно в `AIOS_ENVIRONMENT=prod` и `AIOS_AUTH_MODE=oidc`; `dev`/header-trust не является приемлемым режимом для приглашений.
- У Keycloak есть постоянный публичный issuer, доступный пользователям и приложению; Keycloak не работает в одноразовом `start-dev` без persistence.
- SMTP Keycloak настроен и протестирован администраторами Keycloak. Учётные данные SMTP хранятся только в защищённом серверном secret store/override с правами оператора.

Перед тестовым приглашением оператор проверяет именно **работающий контейнер**, только наличие и режим, не выводя значения секретов:

```sh
cd /opt/cmr-erp

docker compose exec -T app sh -lc '
  printf "environment=%s\\n" "$AIOS_ENVIRONMENT"
  printf "auth_mode=%s\\n" "$AIOS_AUTH_MODE"
  case "$AIOS_DATABASE_URL" in
    *"aios:aios@"*) echo "database=DEV_DEFAULT_BLOCKER" ;;
    "") echo "database=MISSING" ;;
    *) echo "database=configured" ;;
  esac
  for name in \
    AIOS_KEYCLOAK_ISSUER \
    AIOS_KEYCLOAK_AUDIENCE \
    AIOS_KEYCLOAK_ADMIN_BASE_URL \
    AIOS_KEYCLOAK_ADMIN_REALM \
    AIOS_KEYCLOAK_ADMIN_CLIENT_ID \
    AIOS_KEYCLOAK_ADMIN_CLIENT_SECRET \
    AIOS_KEYCLOAK_INVITE_CLIENT_ID \
    AIOS_KEYCLOAK_INVITE_REDIRECT_URI
  do
    eval "value=\\${$name}"
    test -n "$value" && echo "$name=set" || echo "$name=MISSING"
  done
  test "${AIOS_KEYCLOAK_INVITE_LIFESPAN_SECONDS:-0}" -ge 300 \
    && echo "invite_lifespan=valid" \
    || echo "invite_lifespan=INVALID"
'

docker compose ps
curl -fsS http://127.0.0.1:8000/health
```

Ожидается: `environment=prod`, `auth_mode=oidc`, `database=configured`, все перечисленные Keycloak-переменные имеют статус `set`, `invite_lifespan=valid`, контейнеры `Up`, `/health` отвечает `200`.

Если compose выводит пароль, client secret, database URL с паролем или SMTP-настройки — не пересылать вывод; остановиться и показать оператору только имя проблемной переменной.

## 2. Настройка Keycloak

В целевом realm должны существовать realm roles:

- `onboarding` — стартовая изолированная роль, без бизнес-ролей;
- `identity_provisioner` — только для отдельного machine-to-machine клиента приглашений, не для человека;
- утверждённые рабочие роли ERP (например `sales`, `sales_head`), которые могут быть назначены только при активации.

Разделить учётные записи:

- сервисный аккаунт вызова ERP имеет только `identity.invite.prepare` и `identity.invite.send`;
- внутренний Keycloak Admin service account минимально создаёт нового пользователя, назначает/снимает роли и запускает action-email;
- директор/уполномоченный руководитель получает право `identity.invite.activate` через свою ERP-роль;
- обычные пользователи, включая `identity_provisioner`, не получают административных Keycloak-прав и не могут активировать рабочий доступ.

Проверить audience mapper: access token для ERP содержит корректные `iss`, `aud` и realm-role. Для `AIOS_KEYCLOAK_INVITE_CLIENT_ID` заранее зарегистрировать ровно тот HTTPS `AIOS_KEYCLOAK_INVITE_REDIRECT_URI`, который будет передан в action-email; произвольный redirect URI недопустим. Проверку проводить тестовым пользователем, не отправляя токен в чат.

## 3. Настройка почты

- Адрес отправителя утверждён в Keycloak realm SMTP и принадлежит компании (например `invites@belakb.by`).
- Доменная аутентификация SPF/DKIM/DMARC проверена у почтового провайдера. SendPulse может быть провайдером SMTP, но письмо приглашения фактически отправляет Keycloak через свой SMTP transport.
- В From/Reply-to не использовать личную почту сотрудника или администратора.
- Не использовать пароль SendPulse или SMTP в `.env`, репозитории, документации, скриншотах, curl-командах либо сообщениях.

## 4. Deploy и проверка миграции

Выполнить пункты 1–5 [RELEASE checklist](../coordination/RELEASE.md). После `docker compose up -d --build` миграции выполняются entrypoint приложения; не запускать их параллельно вручную.

Пост-смоук оператора:

```sh
cd /opt/cmr-erp && \
docker compose exec -T app alembic heads && \
docker logs --tail 150 aios-app-1
```

Ожидается ровно один Alembic head; в логах нет `Multiple head revisions`, `alembic ... FAILED`, traceback или ошибок проверки OIDC. При красном результате — не приглашать никого, идти по rollback-процедуре RELEASE.

## 5. Безопасный тест письма

1. Создать в HR **отдельную тестовую запись** с активным статусом и корпоративным тестовым почтовым ящиком/алиасом, контролируемым компанией. Не использовать личный Gmail, адрес действующего сотрудника или адрес клиента.
2. В ERP открыть «Настройки → Приглашения», выполнить preflight. Он не создаёт Keycloak-пользователя и не отправляет письмо.
3. Сверить на экране HR ID, email, отдел и будущую роль. Нажать отправку только после отдельного подтверждения оператора.
4. Получить письмо в тестовом ящике, перейти по ссылке, подтвердить email и создать пароль.
5. Войти этим тестовым пользователем. Подтвердить, что доступны только `/onboarding`, собственный минимальный `/system/access` и технический `/health` без пользовательских данных; запросы к CRM/спискам/модулям получают `403` или не показаны интерфейсом.
6. Директор/уполномоченный руководитель отдельно проверяет ожидаемые отдел и роль, затем активирует тестовый доступ из ERP.
7. После обновления сессии проверить доступ ровно к разрешённому рабочему модулю, а также отсутствие доступа к несвязанным модулям.

Фиксировать только безопасные доказательства: timestamp, HR ID тестовой записи, статус preflight/invite/activation, result code и скриншот без токенов/ссылки action-email. Не сохранять пароль и не пересылать URL из письма.

## 6. Реальное приглашение

Перед каждым реальным письмом уполномоченный оператор подтверждает **в этот момент**:

- ФИО и HR ID сотрудника;
- корпоративный email получателя;
- отдел и будущую роль;
- что это новый пользователь, а не существующая Keycloak-учётная запись;
- что тест из раздела 5 уже прошёл в текущем production-режиме.

После подтверждения повторить preflight в ERP и сверить его результат. Только затем выполнить ровно одну отправку с новым idempotency key. Если Keycloak сообщает о существующем пользователе, HR-данные изменились, письмо не пришло или статус требует reconciliation — **не делать повторную отправку/не менять роли вручную**; зафиксировать инцидент и сверить состояние в ERP и Keycloak.

## 7. Evidence и аварийный стоп

Успехом считаются одновременно: OIDC production режим, один Alembic head, активный SMTP sender, письмо в корпоративный тестовый ящик, onboarding без данных и отдельная успешная активация.

Для состояния `sending`, `failed` или `cleanup_pending` назначенный platform-оператор сначала делает только read-only сверку: сопоставляет HR ID, request ID, локальный статус и `error_code` с Keycloak user ID/realm-role и безопасной записью AuditLog. Пока две стороны не согласованы, запрещены повторное письмо, ручная смена ролей и новая заявка для того же сотрудника. Текущее UI показывает ожидающий onboarding, но не заменяет эту эксплуатационную сверку для неоднозначных состояний.

Немедленно остановиться при любом из условий: `AIOS_ENVIRONMENT=dev`, не-`oidc` auth mode, невалидный issuer/audience, несколько migration heads, неработающий SMTP, неожиданная рабочая роль у onboarding-пользователя, ошибка Keycloak или несовпадение HR-данных. Не откатывать БД, не удалять пользователей и не сбрасывать Keycloak вслепую; сначала сохранить безопасные статусы и применить раздел rollback из RELEASE при необходимости.
