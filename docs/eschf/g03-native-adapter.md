# G03: локальный пакет нативного адаптера

09.09.2026. **Локальная реализация для проверки; G03 не принят.** Основа — принятый G02,
commit `acba1a81a675d85256c04b47afe806c324fe4ee4`. Код 1С не компилировался и не выполнялся.
Пакет не содержит подключения к 1С, установки, HTTP endpoint, подписи или отправки.

## Что реализовано

- `integrations/onec_eschf/native_adapter.bsl`: тело минимального общего модуля-кандидата.
  Использует два сохранённых штатных метода: `ЗаполнитьДанныеПоСчетуФактуре`, затем
  `УдалитьПространствоИмен`, как на строках812/818 исходного inner-модуля. Возвращает
  финальную строку, нативный номер, исходные error/refusal и отдельный статус. Никакой
  собственной генерации номера, XML или налога. Разрешённая ветка тела — исходная
  СФ на реализацию с ТЧ ТоварыУслуги; исправления, импорт и итоговая ТЧ Продажи исключены.
  Метаданные/контекст общего модуля ещё не выбраны: устанавливать это тело сейчас нельзя.
- `adapter.py`: валидирует предоставленную связь source↔native, immutable original,
  CP selection, область native UUID, хеши исходника/снимка/полученных зависимостей;
  сравнивает значения нативных строк и итогов с предоставленным XML, сохраняет **ровно
  переданные байты** и SHA256 без XML-пересериализации. Стандартная библиотека и уже
  установленный Pydantic; новых зависимостей нет.
- `capture_local` возвращает только `LocalEnvelope(verification_scope=local_envelope_only)`.
  Поле scope имеет `init=False`: конструктор и `dataclasses.replace` не могут назначить
  ему `runtime_ready`. До validation создаётся одна глубокая отделённая копия всех
  модельных входов; validation и сериализация используют именно её. Изменение исходных
  словарей во время проверки не попадает в envelope. Это не доказывает атомарность чтения 1С.
  `compare_local` проверяет неизменность захваченного материала, а новый согласованный
  материал можно захватить и сравнить повторно. Нулевой наблюдённый DataVersion сам по
  себе не блокирует эти локальные операции и не становится доказанной native version.
- `dependencies.json`: точные символы, строки, SHA256 исходников и непокрытые зависимости.
  Python-код не включает генератор XML; упрощённый генератор находится только в тестах.

## Граница доверия и binding

`SourceOriginal` должен поступить из авторизованного immutable original API владельца
sales после проверки факта выпуска, версии и отсутствия замены. Поле `issued` здесь —
переданный факт: локальная библиотека не умеет подтвердить его права или происхождение.
Нельзя подавать пользовательский JSON напрямую в эту функцию как доверенный источник.

`Binding` — запись будущего доверенного resolver/reconciliation store. Она связывает:

1. ID/версию оригинала, SHA256 UTF-8 HTML и отдельный canonical snapshot hash;
2. exact hash seller-снимка и ссылку на подтверждённый выбор native организации;
3. CP legal/branch IDs/revisions/parent/tax mode/portal code именно `source.party`;
4. scoped `(information_base_id, metadata_object, UUID)` СФ, организации, контрагента,
   основания, плюс хеш всего предоставленного native capture;
5. неизменяемое свидетельство сверки сторон, реквизитов, строк, сумм и основания.

Непустая `*_evidence_ref` **не удостоверяет подлинность** записи. Эта версия проверяет
совпадение предоставленной записи и данных; resolver/store, официальные реквизиты и
сверка ERP↔native ещё не реализованы. Создавать binding по имени, УНП, mock `post_document`
или хешу произвольного native документа запрещено контрактом G02. Для локального теста
используются явно синтетические записи. При изменении source или capture прежняя запись
не проходит; для успешного нового захвата требуется новый согласованный binding.

Canonical формат задан кодом: JSON UTF-8, sorted string keys, компактные separators,
ensure_ascii=false. Decimal-поля — строки. Float/NaN/Decimal-объекты и нестроковые ключи
отклоняются, чтобы не скрыть потери числовой точности. Это внутренний формат сравнения,
он не объявляется нативным форматом сериализации 1С. `captured_dependencies` содержит
значения зависимости, а не timestamp/ID попытки чтения: изменяемые технические метки
нельзя включать в доказательство неизменности содержимого.

## Ошибки и байты

BSL сохраняет `native_error` и `refusal` из штатных выходных параметров. Непустая ошибка
даже при `refusal=false` не даёт успешного кандидата. `native_empty_result` отдельно
обозначает `Неопределено`/пустую строку: manager:7285 может очистить результаты, а
inner:271–272 вернуться без заполнения ошибки. Причины тогда остаются в сообщениях
пользователю. `diagnostic_capture=unresolved`, пустой `native_messages` не означает, что
сообщений не было. API захвата не выдуман; его нужно найти и проверить. Неожиданное
исключение BSL остаётся исключением вызова и не преобразуется в успешный результат.

Оболочка не вызывает верхний `СформироватьСчетФактуруXDTO`: тот через
`ДобавитьЗаписьПоСостояниюЭД` пишет регистр в привилегированном режиме. Нижняя ошибка
XDTO может писать технический журнал; это отдельная проверяемая зависимость.

`capture_local` требует уже полученные `bytes`, явную гипотезу `codec=utf-8` либо
`utf-8-sig` и ссылку на её свидетельство. Defaults нет. Проверяется BOM и строгое
равенство decoded bytes исходной финальной строке. Гипотезы в тестах синтетические;
кодировка/BOM реального экспорта и будущего входа подписи не подтверждены.
XML проверяется по identity/unsigned/roster/totals, **не** по всем header-правилам/XSD.
Итоги читаются из обязательных атрибутов `roster` согласно pinned XSD:198–201;
дочерние элементы итогов отклоняются. Проверяемые singleton-пути (general, number,
documentType, roster, значения строки и vat) не могут содержать дубли. Проверяемые
скалярные поля не могут содержать вложенные элементы.
Подпись, DTD и entity declarations отклоняются. XML parser используется для сравнения,
сохранённые байты не переписываются. Идентичный внешний вид или семантически эквивалентное
XML не разрешают подменить один набор байтов другим.

## Тесты и границы доказательств

Команды из корня изолированного worktree:

```powershell
python -B -m pytest --confcutdir tests/onec_eschf tests/onec_eschf -q
ruff check --no-cache integrations/onec_eschf tests/onec_eschf
```

`--confcutdir` изолирует этот пакет от общего conftest, который импортирует приложение
и БД; `-B` отключает pyc-записи. Тестам не нужны данные/ключи/процесс 1С.

P01–P08 проверяют значения строк товаров/услуг, четыре rateType, смешанные строки,
акциз/итоги/классификаторы/единицы. Числа не пересчитываются по ставке. F01–F15 покрывают
локальную часть договора: head/shared; чужой филиал; stale selection; совпадение имени;
неизвестный tax mode; заменённый/невыпущенный original; изменение HTML; разные ИБ;
rate captions; supplier identity/evidence gap; canonical mismatch; подмена recipient;
старый schema1; service coercion/потеря точности/изменение согласованной суммы.

Дополнительно проверяются native failures/empty result, точные байты/BOM/пробелы,
модифицированные суммы/номер/подпись, изменение внешней зависимости, повтор после нового
binding, immutable копия envelope, статический запрет mutating-вызовов и порядок двух
нативных вызовов. Это реальные локальные тесты, но их fixtures **не являются** ответом
1С или доказательством финансовой/налоговой применимости примера.

Независимый ручной `tests/onec_eschf/fixtures/original-p02.xml` проходит существующую
pinned XSD через уже установленный dev `lxml`. Налоговые варианты также проходят XSD;
их тестовый builder не вызывает `row_values` адаптера. XSD проверяет форму fixture,
а не налоговое право или совпадение с native XDTO package. Регрессии отдельно проверяют
одинаковые/противоречивые дубли cost/number/general/roster/vat/rate, totals-children,
мутацию caller input внутри validation hook и попытки подменить scope.

Особенно: P04 — только NO_VAT row mapping. В native inner:306–312,493–503,534–540
для domestic документа со всеми строками БезНДС подавляются реквизиты recipient.
Проверенный документный сценарий и его связь с recipient ещё нужны; генератор тестов
не воспроизводит этот header и не выдаётся за нативный результат. В manager:7631–7640
для БезНДС также требуется соответствующий дополнительный признак.

## Изолированная runtime-приёмка G03

1. Зафиксировать platform/config/DB fingerprints и доказать main/DB equality, доступный
   контекст, минимальные зависимости и XDTO пакеты. Подготовить точную установку только
   при необходимости; установка на сервер — после отдельного P2. ИБ стенда должна быть
   явно идентифицирована, изолирована от рабочих данных/обмена/портала; никаких копий ключей.
2. В утверждённом стенде создать синтетические native документы/справочники с P01–P08
   и корректными полными заголовками/дополнительными признаками; separately NO_VAT,
   товар/услуга, упаковки/классификаторы, допустимый номер. Получить native enum identity
   и результат resolver, не использовать строки представления вместо enum.
3. Сравнить результат двух вызовов оболочки с **штатным** финальным XML после очистки,
   полученным из разрешённого изолированного baseline. Нативный верхний baseline пишет
   состояние: разрешён только в стенде в явном тестовом пакете. Зафиксировать точные
   строки/байты/номера/hash, источник byte conversion, BOM/CRLF/Unicode, отсутствие подписи.
4. Ошибки: непроведённый документ, недопустимое основание, пустая ТЧ, некорректные
   классификаторы/БезНДС-признаки, XDTO failure, ошибка очистки. Сопоставить точный
   error/refusal и **все** native сообщения; пустой результат без причины — провал проверки.
5. Полная актуальность: в доказанной транзакционной границе/режиме изоляции проверить
   СФ и обе ТЧ, организации/контрагента, их юрадреса/страны, основание/договор,
   номенклатуру/названия/маршрут, упаковки/классификаторы/ставки, enums/XDTO/code revision.
   Изменить каждую группу между повторными чтениями, включая конкурентную транзакцию.
   Старое подтверждение должно отклоняться; после нового согласования рабочий путь
   должен успешно завершаться. Один DataVersion или два SELECT подряд недостаточны.
6. Проверить порядок строк (native query не содержит ORDER BY), неизменный повтор,
   changed-and-restored/race сценарий, потерю результата. Сравнить бизнес-объекты и
   регистры до/после wrapper; зафиксировать диагностические записи отдельно.

Пройдены только локальные проверки — runtime acceptance остаётся открытым. Транспорт,
trusted resolver/store, CP integration и full-projection freshness не заменяются
возвратом `LocalEnvelope`. Изменять global readiness/AC по этим тестам нельзя.
