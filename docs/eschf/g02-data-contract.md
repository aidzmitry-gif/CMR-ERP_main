## Наблюдаемое в ERP и разрыв интеграции

В собственном `Counterparty` есть `id`, `revision` и `requisites`; ORM использует revision как optimistic version. Однако `sales.documents.capture` выбирает покупателя по `Counterparty.name == Deal.counterparty`, берёт первый ID и не сохраняет party IDs/revisions. Нельзя считать такой снимок доказательством однозначно выбранной стороны.

В CP G13 `capture` соединяет `Counterparty.id == Deal.counterparty_id`, проверяет активность, отсутствие merge и принадлежность `branch.legal_entity_id == cp.id`. Снимок содержит `party`:

| Стабильное поле | Фактический источник CP G13 | Предлагаемое назначение ЭСЧФ |
| --- | --- | --- |
| legal_entity_id / legal_entity_revision | Counterparty.id / revision | PartySelection получателя, не GUID 1С |
| branch_id / branch_revision | CounterpartyBranch.id / revision, иначе null | Выбор филиала получателя |
| branch_legal_entity_id | CounterpartyBranch.legal_entity_id | Проверка принадлежности выбранному юрлицу |
| display_name / legal_name / legal_entity_unp | Карточка Counterparty; legal_name nullable | display_name только для UI; официальное имя/УНП требуют проверки |
| branch_name / branch_address | CounterpartyBranch.name / address | Снимок филиала; address нейтрален, не автоматически налоговый адрес |
| branch_tax_mode / portal_branch_code | branch.tax_mode / portal_branch_code, иначе null | Проверенные налоговый режим и код; unknown не заменять shared |
| identity_status | Литерал selected после проверок capture | Факт выбора ERP, не подтверждение налоговой регистрации |

`seller` CP G13 по-прежнему формируется через `_seller_with_facsimile`: `_seller_requisites` берёт `seller_name/unp/address/...` из core.config, branding добавляет изображения. Это не второй `party` и не доказанная stable identity организации-поставщика. `buyer` допускает реквизиты из `terms_json`; налоговый адрес нельзя считать доверенным только из-за наличия строки. `legal_name` может быть null, а buyer.name иметь fallback к cp.name: для ЭСЧФ такой fallback не заменяет официальное имя.

Обе версии sales сохраняют `schema_version=1`. Поэтому один этот номер не различает старый снимок без party и CP G13: проверяются обязательные поля и происхождение точного snapshot, а не только schema_version. Налоговые признаки сторон (взаимозависимость, оффшор, крупный плательщик, специальная сделка) штатный запрос читает из документа отдельно для каждой стороны, а не из Counterparty. Нужны подтверждённые значения на дату операции; не подставлять false из отсутствия ERP-поля.

`CounterpartyAlias(source, external_ref)` и `CounterpartyBranchAlias(source, external_ref)` — отдельные связи. Наличие alias не доказывает конкретную 1С-ссылку и контекст ИБ. Предлагаемый ключ связи: `(information_base_id, metadata_object, reference)` плюс stable ERP ID; его resolver пока не реализован/не принят. Нельзя искать по имени, одному УНП или использовать branch ID как код портала.

### Обязательный налоговый охват G03

Адаптер обязан поддержать строки **и товаров, и услуг** общей штатной ТЧ `СчетФактураВыданный.ТоварыУслуги`, а не только offline `Line(kind=service, vat_rate=20)`. В wire не требуется выдуманный goods/service boolean: тип источника здесь — `native_invoice_row` с metadata object, native invoice UUID и НомерСтроки. Если бизнес-сценарий требует отдельного различения товара/услуги, его даёт проверенный источник номенклатуры в G03; названия и наличие ТНВЭД сами по себе не определяют тип. Оба вида сохраняют собственные классификаторы/единицы и одинаково проходят отображение штатной строки.

| Обязательный сценарий | Источник определения в сохранённом коде | Числовая ставка и ожидаемый rateType | Требование G03 |
| --- | --- | --- | --- |
| Обычная строка товара или услуги | ИспользоватьРасчетнуюСтавкуНДС=false; СтавкаНДС не НДС0/БезНДС | Точное число из штатного ПолучитьСтавкуНДС; DECIMAL | Поддержать наблюдённые20% и любое другое числовое значение, подтверждённое той же штатной веткой для документа; не заводить выдуманный whitelist ставок |
| Нулевая ставка для строки | СтавкаНДС=НДС0, расчётная=false | Число из того же native resolver; ZERO | Сохранить отдельный rateType, не переводить в NO_VAT |
| Без НДС для строки | СтавкаНДС=БезНДС, расчётная=false | Число из native resolver, без угадывания по надписи; NO_VAT | Сохранить отличие от ZERO, не применять20% |
| Расчётная ставка строки | ИспользоватьРасчетнуюСтавкуНДС=true | РасчетнаяСтавкаНДС напрямую; CALCULATED имеет приоритет | Сохранить число и суммы источника; не пересчитывать налог как net×rate |
| Строка с акцизом | СтоимостьАкциза | Тип/ставка определяются независимо четырьмя ветками выше | Сохранить отдельный excise и native totals, не поглощать акциз в price |
| Классифицированная строка | КодТНВЭДЕАС.Код, КодОКЭД.Код, Упаковка.Код | Не зависит от выбора ставки | Передать непустые коды; отсутствие кода сохранять как отсутствие. Единицу отображать как штатный Число(СокрЛП(КодЕдИзм)); код не выводить из названия |
| Смешанные строки | Несколько строк ТЧ со своими ставками/кодами | rateType/rate отдельны для каждой строки | Сохранить порядок/НомерСтроки и native суммы каждой строки, не приводить весь документ к одной ставке |

Эта матрица определяет обязательную функциональность, а не налоговое право на применение ставки: вход должен пройти штатные проверки конкретного документа. Идентичность native enum и доступность resolver уточняются в изоляции G03. Произвольный текст `RatePresentation` не является enum identity. Неподдерживаемые специальные header-сценарии (например, итоговая розница с отдельной ТЧ Продажи) должны быть явно распознаны; их нельзя выдавать за обработанную ТЧ ТоварыУслуги. Проверка исправлений/аннулирования остаётся G06.

## Версия документа, хеш и подтверждение

`DealDocument.id/version`, `snapshot_json`, `original_html`, `content_sha256`, `supersedes_id/superseded_by_id` наблюдаются в собственном sales. Одна строка — одна версия; ORM защищает сохранённый оригинал от изменения. Наличие кода не доказывает текущие production миграции/SQL guards.

`content_sha256` = SHA256 точных UTF-8 байтов `original_html`. Это **не** хеш snapshot JSON и не хеш XML. `preparation.canonical` использует JSON `sort_keys=True`, `ensure_ascii=False`, separators `(',', ':')`, `allow_nan=False`; `sales.documents.digest(dict)` использует другие separators по умолчанию. Их нельзя считать взаимозаменяемыми.

Предлагаемый пакет подготовки связывает source ID/version + original HTML hash + отдельный snapshot hash + обе стороны/revisions + контекст ссылок 1С. Окончательный XML/hash/номер возвращает только будущий проверенный адаптер. Версия конфигурации не заменяет версию документа или справочника. `onec_ref`/`posted`/mock `post_document` не подтверждают наличие настоящего нативного счёта-фактуры либо приём порталом.

Дополнительный разрыв offline `prepare`: функция сверяет каждую сторону с переданными reference_records, но **не связывает** recipient с source_snapshot.party/buyer и provider с seller. Будущий контракт обязан проверять эти две связи; корректный hash документа и существование сторон в справочнике недостаточны. Строка reference_evidence_ref не доказывает доверенность переданного набора. Также offline Line допускает только service, но prepare не проверяет реальный тип исходного SKU: переименование товара в услугу должно блокироваться новым проверенным источником типа. Sales `agreed_gross_amount` требует отдельного правила согласования округления либо отказа, а не автоматического пересчёта сохранённого итога.

Преобразование CP party в offline PartySnapshot не прямое: при отсутствии всех branch-полей предлагается явное `head` вместо CP null; shared допускается только при проверенных parent/revisions/четырёхзначном коде и общей налоговой регистрации. independent/unknown блокируются до отдельного подтверждённого resolver. Существующий PartySnapshot для head/shared требует taxpayer_unp == legal_entity_unp и taxpayer_name == legal_name; эти равенства не доказывают происхождение официальных значений. Недостающие taxpayer_name/address, reference_evidence_ref и налоговые флаги нельзя заполнять значениями по умолчанию и объявлять проверенными.

## Что нужно для AC02 и следующего этапа

### Конкретный пакет полей для владельцев источника и адаптера

Минимальная предлагаемая граница не требует выдумывать CP ID для своей организации. Для поставщика можно использовать отдельную типизированную identity `(information_base_id, Catalog.Организации, native_uuid)`, сохраняемую в ERP-снимке адаптера. Это проект изменения wire-контракта, не уже доступный integer PartySelection. Связь с выбранным seller исходного документа подтверждается явным сравнением официальных реквизитов и сохранённым основанием выбора организации; совпадения имени или УНП недостаточно для автоматического создания связи.

| Поля | Уже доступны | Что именно отсутствует / минимальная поставка |
| --- | --- | --- |
| source_document_id/version | DealDocument.id/version, snapshot.document_id/version | Новый owner API не нужен ради самих полей; нужен авторизованный способ получить один сохранённый original + snapshot после совместимой интеграции |
| source_content_sha256 | DealDocument.content_sha256 = digest(original_html) | Проверить оригинал и статус выпуска; не генерировать HTML заново |
| source_snapshot_sha256 / capture schema | snapshot_json, schema_version1 | В ESCHF envelope вычислить отдельный canonical hash и явно проверить наличие party/revisions; hash не является native DataVersion |
| recipient_selection | CP G13 snapshot.party | Интегрировать принятый CP/sales состав; resolver обязан сопоставить именно snapshot.party с recipient, а не произвольную карточку |
| provider_selection | seller config values; G01 ограниченно подтвердил одну организацию 1С | Сохранить типизированную native identity и подтверждённую связь с seller; не использовать branding.id=1 как legal ID |
| provider_revision / reference evidence | DataVersion организации прочитан с её UUID в одной строке: System.String12, Base64/8байт | Ненулевой observed-only токен; поведение при изменениях и полнота зависимой проекции проверяются в G03. Hash реквизитов не выдавать за native DataVersion |
| native_document_identity/version | Имя метаданных и поля документа установлены | Reference UUID уже прочитан ограниченным SELECT; остаются связь с ERP и доказанный токен версии/полный scoped snapshot до вызова адаптера |
| supplier/recipient tax flags | Точные поля штатного документа установлены | Все четыре flags каждой стороны прочитаны для контрольного документа и false; для нового документа требуются его значения и проверка сценария на дату операции |

Источник уже имеет read API: `GET /sales/documents/{doc_id}/snapshot` возвращает сохранённый snapshot после `originals.original(doc)`; `GET /sales/documents/{doc_id}/render` возвращает original HTML с ETag=content_sha256 и X-Document-State. Оба проверяют sales.deal.read и видимость сделки; оба есть также в pinned CP G13. Поэтому новый owner endpoint ради чтения источника **не требуется**. Отдельно проверяются DocumentOut.id/version/content_sha256/issued_at/original_state и отсутствие замены. Эти GET не требуют issued_only: один HTTP200 не доказывает выпуск. JSON amount/line decimals берутся из snapshot строками, не из float DocumentOut.amount. Маршрут preview пересчитывает проект и не заменяет сохранённый original.

### Обязательная связь ERP → нативный документ

Текущий `_post_document_to_1c` (`sales/routes.py:355`) передаёт только `kind`, `number`, `counterparty` как строку и `amount`. `integrations/client.py:236` возвращает `ref="1С-<number>"` и posted=true без записи 1С. Следовательно ни эта ref, ни событие sales.document.posted не являются native binding. Даже правильно прочитанная проведённая СФ не связана с произвольным ERP-счётом.

Минимальный предлагаемый binding record принадлежит будущему ESCHF-адаптеру: `(source_document_id, source_document_version, source_content_sha256, source_snapshot_sha256, provider_identity, recipient_selection, native_information_base_id, native_metadata_object, native_invoice_uuid, native_version_evidence, basis_reference, binding_evidence, prepared_xml_sha256)`. Первые четыре поля происходят из авторизованного неизменяемого original ERP; party/строки/основание сверяются с соответствующей нативной СФ перед формированием. binding_evidence фиксирует подтверждённое происхождение связи (создание штатным адаптером из этого source либо проверенное согласование существующей связи), не просто время чтения.

Нет проверенной связи → preparation блокируется. Есть связь, но поменялся source/hash/стороны/нативные данные → прежнее согласование недействительно. Существующие source version/hash доступны; новая бессрочная последовательность версий источника не нужна. Отдельно требуется надёжное свидетельство native version и повторная сверка окончательных байтов в G03. Полный сценарий начинается с документа ERP и никогда не подменяется выбором случайной проведённой СФ.

### Реальные контрольные заголовки H02

Одно чтение `g02-control` завершено за26907ms, период `[2026-06-12,2026-09-10)`, фиксированный фильтр утверждённой организации, максимум20документов. Получены20разных invoice UUID и один organization UUID; все20проведены и имеют основание. В наблюдаемой выборке provider IsBranch=false и коды филиалов обеих сторон пусты. Выборка ограничена, не доказывает отсутствие иных сценариев и не является выбором документа для P4. UUID и исходные строки остаются в локальной root-квитанции `CRM-ESCHF-001-g02-control-receipt.json` (SHA256 `09bcbcc4af2e3533d84375fb8d59a91742994448874d02036e325b80ea3db9b6`); публичная карта не содержит идентификаторов документов. NativeDataVersion не прочитан, связь этих документов с ERP ещё не установлена. COMrelease=completed; явных mutating calls0.

Для ссылок использованы стандартные UUID/String, описанные [1Ci Values and types](https://kb.1ci.com/1C_Enterprise_Platform/FAQ/Development/Standards/Values_and_types/?language=en); работоспособность COM-вызовов в текущей конфигурации подтверждает квитанция, а не документация сама по себе.

Дополнительно `g02-lines-v2` прочитал **тот же первый UUID** из хеш-проверенной квитанции:2строки, лимит20 не достигнут,26891ms. В обеих заполнены ТНВЭД и единицы, RatePresentation=`20%`, расчётная ставка не включена, акциз0; все четыре прочитанных supplier flags false. Коды и признаки наблюдаются, но представление ставки не заменяет стабильный enum/code; тип номенклатуры не прочитан, поэтому ТНВЭД не выдаётся за доказательство её типа. Это реальный сценарий строк с классификаторами, которого нет в offline service-only контракте. Перенос таких строк требует подтверждённого kind и сохранения кодов. Числовое преобразование COM double→decimal и равенство net+VAT=gross не являются доказательством финансовой точности исходника; сумма не утверждена для отправки.

Локальная квитанция `CRM-ESCHF-001-g02-lines-v2-receipt.json`, SHA256 `6bc17390aa13ca7519940d950248d6d68c45d6687f16f43ed9b7643b5bb0718d`; наружу используются только обезличенные агрегаты. Header и lines прочитаны в разные моменты без native version: их совместная транзакционная согласованность не доказана. До v2 была одна локальная ошибка Get-FileHash в Python subprocess (640ms, до сети); замена на .NET SHA256 проверена до исправленной попытки. Обе завершённые удалённые операции имеют Complete=true/COMrelease=completed; formation/sign/send не выполнялись.

Точный пакет дальнейшей реализации: сохранить существующий sales original API; согласованно интегрировать pinned CP G13 без потери зависимостей владельца; реализовать в ESCHF envelope типизированный provider binding и обязательную связь recipient с source.party; переносить classifiers/rate-kind без service20 coercion; проверять native version/окончательные байты в G03. На этом checkpoint дополнительный ввод пользователя для безопасного чтения не требуется. Требуют решения владельцев: совместимый integration checkpoint CP/sales и приёмка нового binding-контракта; оператору затем предъявляется конкретный заполненный ERP-document↔native-reference diff, а не просьба одобрить случайный контрольный образец. P4 не подготовлен.

### Уточнение native version и границы G02/G03

После приведённых выше header/lines выполнен отдельный запрос к той же СФ: `Д.ВерсияДанных`, `Д.Организация.ВерсияДанных` и текущая `Д.Организация` взяты одним SELECT. Диагностика `g02-version-shape` установила для обоих полей COM `System.String`, длина12; независимое локальное декодирование показало канонический Base64,8байт. Токен СФ — все байты0, токен организации — ненулевой. Значения сохраняются локально в `CRM-ESCHF-001-g02-version-shape-receipt.json`, SHA256 `00fb5441134c2b847de7fc6187d65154ff5b1c572f62eb33af54bca2f31852d8`. Все четыре recipient flags в этом наблюдении false. Прежние header/lines квитанции не содержат версии; текущий итог приведён в этом разделе. Первая попытка предполагала BinaryData и была отклонена guard при преобразовании; новые факты получены отдельной проверкой типа без такого предположения.

Контракт native_version_evidence теперь конкретен: `{native_identity, field: "ВерсияДанных", encoding: "base64", byte_length: 8, token, observed_at, trust: "observed_only"}` для наблюдаемого источника/версии конфигурации. Identity организации берётся из той же строки, а не переносится из старой выборки. Не увеличивать токен как число, не преобразовывать строку повторно через Base64String, сравнивать декодированные байты/каноническую строку. Иная длина/тип требует явного пересмотра контракта, а не тихого преобразования.

Нулевой токен не доказывает дефект или неизменность документа, но **не принимается как достаточное свидетельство актуальности**. В таком случае подготовка/подтверждение должны отказать с `native_version_unproven`, пока G03 не установит изолированным тестом корректный способ повторной сверки всей зависимой проекции и окончательных XML-байтов. Даже ненулевая версия организации не покрывает изменения её контактной информации, внешних зависимостей и всей СФ. Версия контрагента не прочитана. Ни один из новых токенов не делает прошлые header/lines атомарным снимком.

`native_version_unproven` — временный запрет неподтверждённого пути, не окончательная реализация с постоянным отказом всех СФ. Приёмка G03 требует работающей защиты актуальности всей подписываемой проекции: либо пригодные native tokens с проверенными зависимостями, либо доказанный content hash полного снимка/точного XML и согласованное повторное чтение с проверкой в границе транзакции. Способ выбирается по изолированным доказательствам; отсутствие native token не разрешает придумать его или сравнивать только часть полей. Полный рабочий путь остаётся обязательным результатом цепочки.

Для G02 доказаны перечисленные наблюдаемые имена, типы и доступность полей; согласованы конкретный contract binding, налоговая матрица и требуемые отказы. Для G03 остаётся реализация доверенного resolver/binding, проверка поведения токенов и согласованности полного снимка в изоляции, main/DB equality и окончательный XML. Пользователь сейчас не должен одобрять обход `native_version_unproven` или случайную контрольную СФ. Запрос P2 допустим только с конкретным проверенным кодом, стендом, целями и откатом; пакет пока не подготовлен.

Оператору потребуется согласовать конкретные расхождения только после получения подготовленного сравнения seller-снимка с официальными реквизитами 1С и выбора требуемых налоговых сценариев. Чтение, сверка схем, вычисление хешей и подготовка такого сравнения укладываются в P1 и не требуют повторного общего «продолжай». Установка/подпись/отправка остаются отдельными пакетами.

G02 принят после независимого correctness/simplify review: идентичности, версии, матрица и P01–P08/F01–F15 согласованы. Приёмка контракта включает: согласованный контракт stable CP/sales checkpoint и совместимых зависимостей; проверенные источники полей обеих сторон и scoped 1С-ссылок; правила налоговой регистрации филиала, официальных реквизитов и необходимых строк/ставок; приёмка контрольных примеров и явного отказа для неподтверждённых сценариев. Реализация binding, интеграция runtime и проверка повторного формирования относятся к G03/G04/G07; их отсутствие само по себе не должно бесконечно удерживать приёмку контракта G02. Согласование проекта не является production приёмкой.

G03 отдельно: main/DB equality, внешний контекст/доступность нижней функции, анализ её зависимостей, изолированное окончательное XML/номер/ошибки. Никаких formation/sign/send в G02. P2 — точный пакет установки изоляции при необходимости, P3 — выпуск, P4 — конкретный показанный документ. Сам факт наличия рабочих исходников эти разрешения не заменяет.
