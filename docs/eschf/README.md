# CRM-ESCHF-001 — подключение ЭСЧФ Беларуси

Дата проверки: 09.09.2026. Результат: способ интеграции подтверждён; реализован и проверен **локальный подготовительный пакет**. Подключения к порталу, юридической подписи, отправки, рабочего UI и production-релиза нет.

## Рекомендация и границы

Пользователь указал организацию **УНП192766048**, подписанта **бухгалтер**, сначала план размещения ЭЦП **на текущем Linux-сервере CRM ERP**, затем уточнил: **ключ уже установлен на сервере1С, отправка ЭСЧФ из1С работает**. Последнее — подтверждение пользователя, а не выполненный нами тест отправки. Рекомендуемый первый маршрут: **Linux ERP → действующая1С → портал**, с возвратом окончательного XML, подписанного контейнера, квитанций и статусов в ERP. Проект конкретного обмена — [onec-contract.md](onec-contract.md). Проверять Linux-криптосредства нужно для отдельного будущего переноса подписи, а не как условие первого пилота через1С.

Linux-сервер проверен на чтение: **Ubuntu26.04 LTS, x86_64**, команда `command -v java` не нашла Java в PATH (это не полный поиск установленных runtimes). Публичная проверка УНП через ГРП завершилась TLS timeout; полное имя организации не придумано и не перенесено из непроверенного источника.

По указанию пользователя найдены свежие результаты задач «Проверь готовность карточки товара» и «CRM-SKU-001 · H01 · Интерфейс карточки…». На **Windows-сервере 1CSRV** подтверждён вход через WinRM под ограниченным токеном существующей учётной записи. Прочитанные файлы IIS связывают публикацию `ka_copy` с базой `localhost / ka_copy`; версии обработчика OData и зарегистрированного COM Connector — **8.3.18.1661**. Это версии компонентов платформы, не версия конфигурации. Через существующее соединение ERP получены HTTP200 для service document и metadata, доступны 42 сущности. Сохранённый отбор метаданных касался реализаций/складской аналитики и не устанавливает наличие либо отсутствие интерфейса ЭСЧФ.

Доступ к серверу и OData уже существует; повторно запрашивать его у пользователя не требуется. В последнем доступном отчёте прямой вход COM в ИБ ещё не выполнен, чтение метаданных конфигурации подготовлено в исходной задаче. Название `ka_copy` само по себе не доказывает назначение базы. Её связь с рабочей отправкой ЭСЧФ, версия конфигурации и точные методы ещё не подтверждены. Зафиксированные факты и SHA-256 исходных отчётов — [onec-evidence.json](onec-evidence.json); пароли и ключи не переносились.

Вариант последующего размещения подписи непосредственно на Linux: отдельный процесс получает согласованный неизменяемый документ. **Совместимость ЭСЧФ SDK и криптосредств с Ubuntu26.04 пока не подтверждена.** ActiveX-вариант рассчитан на Windows; Java-интерфейс в SDK сам по себе не доказывает поддержку Linux. В руководстве пользователя перечислены Windows-системы, top-level архив не содержит `.so/.deb/.rpm`; это наблюдения о полученном пакете, не доказательство отсутствия всех Linux-продуктов у Авест. До получения поддерживаемого пакета нельзя заменять его самописной подписью или выдавать Wine за проверенное решение.

## Нормативная и техническая модель филиалов

Проверено постановление МНС **31.03.2026 №14**, зарегистрированное 29.04.2026 №11-1/44816. Старую инструкцию 2016 года нельзя использовать как единственную актуальную основу. Прочитан текст, опубликованный МНС; отдельный полный аудит законодательства вне темы этого подключения не выполнялся.

| Случай | Юридическая идентичность | Реквизиты ЭСЧФ | Допуск локального пакета |
|---|---|---|---|
| Головное юрлицо | `legal_entity_id`, `branch_id=null` | УНП и полное согласованное имя юрлица; адрес из проверенной записи | Подготовка кандидата |
| Филиал, не исполняющий налоговые обязательства по п.3 ст.14 НК | То же юрлицо + отдельный `branch_id` | УНП юрлица; код филиала портала; официальный адрес филиала | Подготовка кандидата при явных связях |
| Филиал, исполняющий обязательства в части своей деятельности | Связь с юрлицом сохраняется; налоговая регистрация отдельно | Нельзя автоматически копировать УНП головного или генерировать собственный | Экспорт заблокирован до проверки регистрации |
| Неизвестный режим / иностранная структура | Не выводится из совпадения УНП/названия | Требуется отдельная проверенная модель | Экспорт заблокирован |

Основания: п.60 Инструкции разделяет первые два режима филиала; п.21.11 — код поставщика (строка8.1), п.22.11 — код получателя (17.1). П.60 прямо требует код получателя при продаже филиалу, не исполняющему налоговые обязательства. Пп.21.12–13, 22.12–13 определяют имя/адрес; источник имени — ГРП, адрес соответствующего филиала — справочник портала. Полное юридическое имя и имя налогоплательщика сохранены раздельно; для поддержанного режима head/shared согласуются без подмены рабочим названием.

В техническом описании 10.03.2026: `provider/unp`, `provider/branchCode`, `provider/name`, `provider/address` и аналогичные поля `recipient`. `branchCode` — **четыре цифры**, строка с ведущими нулями, значение справочника «Филиалы» (ограничение формата10). Это не ID ERP/1С и не банковский код. Правило12 разрешает равные УНП при разных кодах филиалов; правило13 требует существования УНП в реестре. XSD сама эти бизнес-проверки не обеспечивает.

**Неустановленное:** актуальный первичный порядок присвоения собственного УНП исполняющему обязательства филиалу не получен. Официальная ссылка МНС на общую часть НК (`https://pravo.by/document/?guid=3871&p0=hk0200166`) вернула403. Это не основание утверждать, что каждый филиал имеет собственный УНП. Нужны действующая запись налоговой регистрации и её связь с головным юрлицом; до этого режим `independent` блокируется.

Код разрешён пустым в незавершённой карточке, но требуется перед подготовкой ЭСЧФ shared-филиала. ## Реализованный безопасный этап

Пакет `modules/eschf` не включён в `ENABLED_MODULES`, не содержит HTTP API, ORM, сетевого клиента, ключей, подписи или фоновых заданий. Это запускаемый локальный этап подготовки, а не объявление готовности всей интеграции.

Поддержан **исходный XML для обычной услуги между белорусскими SELLER/CUSTOMER со ставкой20%**, по явному выбору пользователя. Это ограничение первой реализации, не правило для всех ЭСЧФ. Товары, импорт/экспорт, иные ставки, комиссии, исправленные и дополнительные документы возвращают ошибку неподдержанного сценария; общую бизнес-модель для них нельзя заменять этим примером.

Проверяются идентичность/версии/родитель стороны, форматы кодов, суммы Decimal, соответствие строк и итогов источнику, хеши источника, неизменяемость снимка, экранирование XML, хеш закреплённой XSD и соответствие ей. УНП/код справочника онлайн не проверяются, оригинал источника и записи справочника должны поступать от будущего доверенного адаптера. `xsd_valid=true` не означает юридическую корректность или приём порталом.

`lifecycle.py` — чистая локальная политика обработки результатов и повторов. Она принимает уже проверенное адаптером свидетельство; криптографическую проверку не реализует. `signature_verified` нельзя принимать от клиента. В БД ещё нет уникального ограничения, блокировки конкурентных отправителей или очереди; локальная проверка коллизий не выдаётся за такую защиту.

## Подпись, статусы, исправления и повторы

Нормативный порядок: предварительный контроль проверяет подпись, структуру и УНП автора; XML-квитанция подтверждает приём либо отказ. Затем основной контроль проверяет реквизиты, справочники, зависимости и ссылки на прежние ЭСЧФ. Его результат запрашивается отдельно. Дату выставления формирует портал (пп.11–12), локальный генератор её не заполняет.

В SDK: `Login`/`Connect`, `CreateEDoc`/`Sign`, `SendEDoc`, `Ticket`, `GetStatus`, `Verify`, `GetList`, `GetEDoc`. Эти названия подтверждены руководством; они не были вызваны. УНП сертификата должен соответствовать автору и одной из сторон ЭСЧФ. Нужны действующие сертификат/атрибутный сертификат и полномочия; закрытый ключ остаётся у уполномоченного подписанта. Проверка подписей портала обязательна также для квитанций и статусов.

| SDK-код | Значение для ERP |
|---|---|
| `COMPLETED` | Выставлен |
| `COMPLETED_SIGNED` | Подписан получателем |
| `ON_AGREEMENT` | На согласовании |
| `ON_AGREEMENT_CANCEL` | Аннулирован поставщиком, требуется подтверждение получателя |
| `CANCELLED` | Аннулирован |
| `IN_PROGRESS` | Обработка; SDK предлагает запрос через3часа |
| `NOT_FOUND` | Нет документа **или нет права просмотра**; требуется сверка |
| `ERROR` | Ошибка выставления; сохранить код/сообщение |
| неизвестный код | Сохранить сырой ответ, запросить сверку, не считать успехом |

Типы ORIGINAL, FIXED, ADDITIONAL, ADD_NO_REFERENCE не взаимозаменяемы. Исправление создаёт новый связанный документ; выпущенный оригинал не редактируется. Исправленный к двусторонне подписанному и некоторые отрицательные дополнительные ЭСЧФ требуют согласования. Аннулирование двусторонне подписанного не завершено до подтверждения второй стороны. Основание: №14, пп.5–7, 15 и соответствующие правила исправлений; SDK, приложение2.

Проект будущей очереди: `eschf.invoice` хранит неизменяемые снимки/версии/родителя исправления, `eschf.attempt` — попытки и claim token, `eschf.portal_observation` — исходные подписанные квитанции/статусы, корреляцию и время портала. Операция создания намерения и outbox — одна транзакция. Уникальность `(среда, УНП автора, номер ЭСЧФ)` общая для филиалов этого УНП; повтор с другим хешем — конфликт. Номер вида `УНП-год-10цифр` выделяется согласованным счётчиком **между ERP и 1С**, а не копированием номера PDF.

После timeout/падения между отправкой и записью квитанции — `delivery_unknown`, автоматический повтор запрещён. Сначала сверка статуса/скачивание с портала по автору/номеру/контенту. `NOT_FOUND` само по себе не разрешает повтор. Квитанция со старым временем, другим автором, номером или хешем подписанного документа не продвигает статус. Каждый повтор/исправление требует явного решения и сохранения истории.
