# Машиночитаемый манифест пилота бухгалтерии

Перед импортом начальных остатков бухгалтер собирает отдельную папку с исходными
файлами и `manifest.json`. Проверка выполняется локально:

```powershell
py -3 scripts/accounting_pilot_preflight.py --manifest <путь-к-manifest.json>
```

Команда не подключается к 1С, не записывает данные в ERP, не создаёт квитанции и
не ставит документы в очередь. Успешный результат подтверждает только полноту,
целостность и внутреннюю совместимость входного пакета. Проведение импорта и
принятие сверки остаются отдельными действиями бухгалтера.

После этого можно отдельно сверить тот же пакет с **текущей базой ERP**. Укажите
адрес асинхронного PostgreSQL-подключения через переменную среды, не в аргументе
командной строки:

```powershell
py -3 scripts/accounting_pilot_live_preflight.py --manifest <путь-к-manifest.json> --database-url-env ERP_PILOT_READONLY_URL
```

Этот необязательный шаг повторяет проверку файлов, затем в транзакции только для
чтения сверяет ID книги, УНП и название юрлица, действующую редакцию политики
(`effective_from` и `order_reference`), квитанцию начального импорта, если она
уже есть, и **точные байты** правой ОСВ с текущим экспортом проводок ERP.
`opening_import_status=not_imported` допустим до импорта; несовпадающая квитанция
или ОСВ блокирует live-результат. Для PostgreSQL используется повторяемый снимок;
экспорт ОСВ в этом режиме не берёт блокировку записи. Проверка не импортирует
остатки, не подтверждает происхождение выгрузки из 1С, бухгалтерскую политику
по существу или готовность отказаться от 1С. Результат относится только к
состоянию базы и файлов на время этой проверки.

Обе команды перед успешным ответом повторно читают `manifest.json` и каждый
приложенный файл. Если файл исчез или его байты изменились во время проверки,
успешный протокол не выдаётся. Эта финальная сверка не блокирует папку после
завершения команды: для импорта и приёмки бухгалтер повторно проверяет хэши
того же пакета.

В разделе «Бухгалтерия → Импорт остатков» бухгалтер выбирает исходную выгрузку
и подготовленный `opening-balance-v1` JSON. Браузер сверяет SHA-256 выбранной
выгрузки с `source_digest` пакета перед просмотром и непосредственно перед
подтверждением. Байты выгрузки не отправляются в API импорта и не сохраняются
этим экраном. Проверка двух выбранных файлов не заменяет полный preflight
манифеста, проверку подлинности выгрузки и согласование остатков.

## Состав папки

Пути в манифесте относительны к его папке. Нельзя указывать абсолютные пути,
`..`, повторять путь или пару `source_system`/`source_id`. Для каждого файла
укажите SHA-256 в нижнем регистре и основание его происхождения. Для
`opening_source`, `opening_balances`, `osv_left`, `osv_right` и выбранного
зарплатного вида допустим ровно один файл; остальные виды могут состоять из
нескольких файлов.

Обязательные виды: `opening_source`, `opening_balances`, `bank_statement`, `inventory`,
`receivables`, `vat`, `fx`, `primary_documents`, `osv_left`, `osv_right`.
Дополнительно обязателен **один** зарплатный вид: `payroll_register` при
`payroll.mode=external_verified_import` или `payroll_zero_activity` при
`payroll.mode=no_accruals`. Режим собственного расчёта ERP пока не принимается
для перехода: G06C не завершён. Для внешнего реестра нужны класс
`external_system_export` либо `source_register`; для подтверждения отсутствия
начислений — `primary_document` либо `source_register`. Имя системы-источника
файла должно совпадать с `payroll.source_system`.
Дополнительно можно приложить `supporting_calculation`: он сохраняет контекст
расчёта, но не закрывает ни один обязательный вид доказательства.

Каждый файл получает два явных признака происхождения:

- `evidence_role=required_evidence` — доказательство, которое закрывает один
  обязательный вид;
- `evidence_role=supporting_calculation` — вспомогательный расчёт, например
  таблица распределения доставки. Такой файл допускается только с
  `kind=supporting_calculation`.

Поле `source_class` не позволяет выдать оперативную таблицу за первичный
документ. Для выписки банка нужна `bank_statement`, для курсов —
`official_rate`, для первички — `primary_document`; реестры и ОСВ принимают
только соответствующий экспорт или регистр. Оперативный файл можно указать
только как `operational_workbook` во вспомогательном расчёте.

`opening_source` — неизменённая исходная выгрузка остатков из 1С, отдельный файл
с классом `external_system_export`. `opening_balances` — подготовленный JSON
пакета `opening-balance-v1`, который уже проходит модель ERP. Его `source_system`
совпадает с исходной выгрузкой и манифестом, а `source_digest` равен SHA-256
точных байтов `opening_source`. Это связывает пакет с приложенным файлом, но
не удостоверяет, что файл действительно получен из 1С или содержит все остатки.
`cutover_date` должен совпасть с манифестом.
На одну дату перехода для каждого юрлица принимается один подтверждённый пакет;
квитанция должна охватывать все начальные проводки юрлица. После подтверждения
новые начальные проводки блокируются; исправления оформляются отдельными
корректирующими операциями.
`osv_left` — нормализованная CSV ОСВ внешней учётной системы с классом
`external_system_export`; `osv_right` — нормализованная CSV ОСВ ERP с классом
`erp_control_export`. Их заявленные `source_system` должны различаться. Оба
файла должны относиться к одной книге и периоду, иметь статус `closed_periods`,
ноль непроведённых документов и ноль расхождений. Программа сверяет хэши и
данные, но не сохраняет файлы и не удостоверяет источник одной лишь декларацией.
Правую CSV скачайте в разделе «Сверка ОСВ» для выбранной книги и периода:
`GET /accounting/organizations/{org_id}/reconciliation/erp-osv.csv?start=YYYY-MM-DD&end=YYYY-MM-DD`.
Локальный preflight проверяет файл и заявленный класс происхождения без БД;
при предварительной сверке и новом подтверждении ERP дополнительно требует
точного совпадения правой CSV с текущей выгрузкой собственных проводок.
Флаг `reconciliation_ready` относится только к этой паре закрытых ОСВ и
разрешает бухгалтеру принять один протокол сверки. `cutover_ready` остаётся
ложным: один протокол не доказывает подлинность левой выгрузки, два месячных
закрытия, квартальный и годовой циклы, восстановление и готовность выпуска.
История старых квитанций без этой проверки остаётся читаемой, но не является
доказательством готовности к переходу.

## Строгая схема `belarus-pilot-input-v6`

Замените все значения в угловых скобках подтверждёнными данными. Пустые поля,
`unknown`, `n/a`, `todo` и другие заполнители отклоняются. Политика должна
действовать в дату перехода, а дата перехода — быть первым днём пилотного месяца.

```json
{
  "protocol_version": "belarus-pilot-input-v6",
  "pilot": {
    "month": "<YYYY-MM>",
    "cutover_date": "<YYYY-MM-01>",
    "authorization_evidence": "<решение о пилоте или ссылка на протокол>"
  },
  "organization": {
    "external_id": "<устойчивый ID юрлица в источнике>",
    "erp_book_id": "<положительный ID книги этого юрлица в ERP>",
    "name": "<полное наименование юрлица>",
    "unp": "<9 цифр УНП>"
  },
  "owners": {
    "chief_accountant": "<устойчивый ID главного бухгалтера>",
    "accountant": "<устойчивый ID бухгалтера>",
    "bank_operator": "<устойчивый ID оператора банка>"
  },
  "policy": {
    "effective_from": "<YYYY-MM-DD>",
    "effective_to": "<YYYY-MM-DD>",
    "revision": "<редакция учётной политики>",
    "order_reference": "<приказ или иной документ>",
    "responsible_id": "<устойчивый ID ответственного>",
    "evidence": "<ссылка или идентификатор подтверждённой политики>"
  },
  "payroll": {
    "mode": "<external_verified_import или no_accruals>",
    "source_system": "<система внешнего расчёта или реестр отсутствия начислений>",
    "verified_by": "<ID бухгалтера или главбуха из owners>",
    "evidence": "<основание проверки начислений или отсутствия начислений>"
  },
  "responsibility": {
    "sales": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "procurement": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "bank": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "inventory": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "settlements": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "vat": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "fx": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "production": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "repairs": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "fixed_assets": {"owner": "<erp|external|not_applicable>", "source_system": "<ID системы или null>", "evidence": "<основание>"},
    "payroll": {"owner": "<external|not_applicable>", "source_system": "<ID источника или null>", "evidence": "<основание>"}
  },
  "artifacts": [
    {
      "kind": "<один из обязательных видов>",
      "evidence_role": "<required_evidence или supporting_calculation>",
      "source_class": "<класс происхождения файла>",
      "source_system": "<система-источник>",
      "source_id": "<устойчивый ID выгрузки или документа>",
      "path": "<относительный путь к файлу>",
      "sha256": "<64 символа SHA-256 файла в нижнем регистре>",
      "evidence": "<основание происхождения файла>"
    }
  ]
}
```

`responsibility` задаёт ответственную систему по каждому участку **только для
месяца пилота**. При `owner=not_applicable` поле `source_system` должно быть
JSON `null`; в остальных случаях требуется ID системы. Для зарплаты
`external_verified_import` означает `owner=external` с тем же `source_system`,
а `no_accruals` — `owner=not_applicable`. Все одиннадцать участков должны быть
перечислены. Preflight проверяет заполнение и непротиворечивость этих заявлений,
но не доказывает фактическое владение процессом и не читает смысл зарплатного
реестра. Подтверждение бухгалтера и сверка остаются обязательными.

`organization.erp_book_id` берётся из выбранной книги ERP и должен точно
совпасть с `Юрлицо ID` в обеих ОСВ. Это предотвращает принятие совпадающей пары
ОСВ другого юрлица. Связь `external_id` источника с книгой ERP и УНП остаётся
заявлением подготовителя пакета и подлежит отдельной сверке бухгалтером;
preflight не получает её из реестра юридических лиц.

Манифесты v2–v5 намеренно не считаются полным пакетом перехода: в v2 не было
обязательного источника по зарплате и распределения ответственности, v3 не
связывал ID книги ERP с организацией, а v4 позволял объявить обе ОСВ выгрузками
одной и той же системы, а v5 не связывал `source_digest` остатков с файлом
исходной выгрузки. Даже v6 требует отдельного подтверждения подлинности файлов
и связи внешнего ID с книгой и УНП бухгалтером.

Сначала заполняется манифест, затем для каждого файла рассчитывается его хэш.
После любого изменения файла нужно сформировать новый SHA-256 и повторить
проверку. Успешный ответ содержит `manifest_sha256` точных байтов проверенного
`manifest.json`: зафиксируйте его в протоколе бухгалтера вместе с хэшами
исходных файлов. `opening_import.command_digest` сравните с одноимённым полем
квитанции ERP после подтверждения импорта: совпадение связывает проведённый
пакет с проверенным содержимым без учёта транспортного `request_key`.
Любое редактирование манифеста требует нового preflight и
нового решения по пакету. Успешный preflight не назначает данные основной компании, не снимает
внешние блокеры и не заменяет согласование реального перехода.

## Диагностика неполного пакета

При неуспешной проверке команда возвращает `ok: false` и первую строгую ошибку.
Если сам `manifest.json` читается как JSON-объект, в ответ также добавляется
`intake`. Это только инвентаризация названий видов файлов:

- `required_artifact_kinds` — базовый набор плюс зарплатный вид по **заявленному**
  поддерживаемому режиму; при нераспознанном режиме зарплатный вид ещё не выбран;
- `declared_candidate_artifact_kinds` — виды, которые лишь заявлены в манифесте;
- `missing_required_artifact_kinds` — виды, которые ещё не заявлены.
- `payroll_mode_candidate` и `payroll_kind_candidates` — только непроверенная
  подсказка о выбранном режиме и допустимых видах зарплатного источника.

`intake.status=unverified_artifact_kind_inventory` не подтверждает ни файл,
ни его SHA-256, происхождение, содержимое или применимость. Строгий preflight
остаётся обязательным и продолжает проверять каждый источник отдельно.
