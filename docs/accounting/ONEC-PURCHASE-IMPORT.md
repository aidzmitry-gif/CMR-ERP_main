# Месячные накладные поступления из 1С: подготовка черновиков

Команда `map-onec-purchases` превращает проверенный кэш документов 1С в payload существующей накладной закупки CRM ERP. Она не создаёт документы в базе, не выбирает бухгалтерские счета, не рассчитывает валютный курс и не проводит операции.

## Порядок подготовки

1. Из метаданных OData конкретной базы 1С бухгалтер или интегратор выбирает точный тип `Document_*` и реальные имена свойств документа и табличной части. Примеры ниже условные: названия полей в вашей базе могут отличаться.
2. Каждый `Ref_Key` поставщика, договора, склада, валюты и номенклатуры сопоставляется с конкретной записью CRM ERP. Сопоставление по похожему названию или автоматический выбор запрещены.
3. В карту переносятся точные суммы без НДС, ставка и сумма НДС из строки. Импортёр сверяет сумму НДС с базой и ставкой по действующему правилу закупки: округление до копейки `ROUND_HALF_UP`. Если 1С рассчитала иначе, документ попадает в список ошибок и месячный пакет целиком не формируется.
4. Формируются черновые payload накладных и контрольные SHA-256. Неизвестная валюта, справочная ссылка, поле или строка блокирует весь пакет; частичный пакет не выдаётся.
5. После ручной проверки черновики передаются в раздел «Закупки» через штатный API `receipt-documents`. В карточке бухгалтер проверяет счета и предпросмотр проводок; подтверждение проведения — отдельное действие с digest предпросмотра.

Текущий поток закупки принимает BYN. Валютную накладную следует остановить для отдельного расчёта по учётной политике; нельзя конвертировать её курсом из коммерческого резерва. Сумма НДС должна быть явно присутствовать в источнике. Система не выводит её из общей суммы.

## Карта сопоставления

Все значения ID ниже вымышлены. JSON Pointer чувствителен к регистру и точному имени поля. `document_date` всегда `/Date`, поскольку именно это поле задаёт период извлечения 1С.

```json
{
  "schema_version": "onec-purchase-map-v1",
  "entity": "Document_ПоступлениеТоваровУслуг",
  "organization_id": 17,
  "paths": {
    "document": {
      "number": "/Number",
      "document_date": "/Date",
      "operation_date": "/Date",
      "supplier_ref": "/Контрагент_Key",
      "contract_ref": "/Договор_Key",
      "warehouse_ref": "/Склад_Key",
      "currency_ref": "/Валюта_Key",
      "lines": "/Товары"
    },
    "line": {
      "sku_ref": "/Номенклатура_Key",
      "quantity": "/Количество",
      "net_amount": "/СуммаБезНДС",
      "vat_rate": "/СтавкаНДС",
      "vat_amount": "/СуммаНДС",
      "vat_basis": "/ОснованиеНДС"
    }
  },
  "currency_refs": {
    "<1C currency Ref_Key>": "BYN"
  },
  "suppliers": {
    "<1C supplier Ref_Key>": {
      "id": 301,
      "name": "Поставщик из справочника ERP",
      "unp": "123456789"
    }
  },
  "contracts": {
    "<1C contract Ref_Key>": {
      "id": 401,
      "number": "Д-2026/1"
    }
  },
  "warehouses": {
    "<1C warehouse Ref_Key>": {
      "id": 501,
      "code": "MINSK",
      "title": "Основной склад"
    }
  },
  "skus": {
    "<1C item Ref_Key>": {
      "id": 601,
      "code": "SKU-01",
      "title": "Товар из справочника ERP",
      "unit": "шт"
    }
  }
}
```

Если партия явно не передана в строке 1С, локальный lot-идентификатор создаётся детерминированно из исходного `Ref_Key` документа и номера строки. Это ключ прослеживаемости импорта, не утверждение о партии производителя.

## Локальный запуск

```powershell
$env:IMPORT_CACHE_DIR = 'C:\путь\к\месячному\кэшу'
$env:IMPORT_ONEC_PURCHASE_MAPPING = 'C:\путь\к\onec-purchase-map.json'
python scripts/import_month.py map-onec-purchases
```

Для формирования кэша отдельно задаются точный OData-тип `IMPORT_ONEC_PURCHASE_ENTITY` и период `IMPORT_ONEC_FROM` / `IMPORT_ONEC_TO`, затем запускается `extract-onec-purchases`. При несовпадении digest или периода пакет не строится. Файлы `onec_purchase_drafts_*.jsonl` и sidecar содержат организацию, идентификаторы источника, целевые MDM ID и суммы; храните их как бухгалтерские данные.

Текущая версия не вызывает API автоматически и не принимает решение о счетах запасов, НДС, расчётов с поставщиком или дате проводки. Чтобы проверить реальное проведение месяца, нужны фактическая карта метаданных 1С, сверенные справочники и отдельный тест на изолированной PostgreSQL-базе.
