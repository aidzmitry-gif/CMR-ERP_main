# Единый сценарий оформления документов

Требование пользователя от 24.09.2026. Применяется к документам CRM, закупок,
склада, финансов и бухгалтерии. Готовность каждого вида документа проверяется
отдельно; наличие похожего механизма у другого вида не считается приёмкой.

1. У документа есть устойчивый ID, юрлицо, вид и отображаемый номер. Номер в
   реестре открывает именно этот документ и его версию в пределах прав юрлица.
2. Поля, для которых существует справочник (контрагент, договор, номенклатура,
   склад, статья и другие), выбираются по ID из него. При сохранении фиксируются
   ID и существенные реквизиты на дату документа; переименование справочника
   не переписывает историю. Неизвестные старые связи показываются как
   несопоставленные, без догадки по названию.
3. При редактировании видна команда **«Сохранить и закрыть»**. Она закрывает
   форму только после подтверждённой сервером записи. Ошибка, потеря ответа
   или конфликт версий оставляют форму открытой; повтор не создаёт дубль.
   При несохранённых изменениях простой выход предупреждает пользователя.
4. Каждое успешное изменение имеет неизменяемую запись: серверное время,
   исполнитель, вид документа, ID/номер, редакция, изменённые поля и значения
   до/после. История доступна из карточки и отфильтрована по юрлицу. Старые
   записи без автора или прежнего значения помечаются как неполные.
5. Проведённый или отправленный документ не правится как черновик. Исправление
   создаёт связанную редакцию либо корректирующий документ по правилам вида,
   с основанием и сохранением исходного оригинала.

| Заказ поставщику | Номер ведёт из списка в карточку; серверные команды содержат исполнителя, время и эффект, а карточка показывает историю изменений. «Сохранить и закрыть» отправляет одну атомарную команду для новой позиции, фрахта, плана и статуса. Сервер хранит одну квитанцию и историю изменённых полей; сбой позднего шага откатывает весь пакет. При создании поставщик и позиции выбираются из справочников по ID; имя/УНП поставщика и код/название/единица товара фиксируются в неизменяемой квитанции. Изменившийся или заблокированный справочник блокирует новую запись. Миграции 0177–0178 согласуют проверки PostgreSQL с этими квитанциями. Несохранённые поля или неопределённый результат команды предупреждают при переходе по внутренней ссылке, смене юрлица и закрытии или перезагрузке страницы. | Прежние API-команды ради точного повтора ещё допускают строкового поставщика и SKU. | Счёт CRM | Реестр сделки хранит номер и связанные версии, оригинал выпущенного счёта защищён. Выпуск требует подтверждённой привязки покупателя к общему справочнику контрагентов по ID и сохраняет снимок реквизитов. В форме подтверждения покупатель выбирается поиском по карточкам справочника с видимыми УНП и ID; выдача ограничена правами на сделку и юрлицо. | Сделка может быть создана без подтверждённого контрагента. Нет единого редактирования с историей полей «до/после» и исполнителем для каждого изменения. |
| Накладная поступления | Черновик и редакции находятся в разделе закупок, проведённый источник защищён. Новая форма и API требуют выбора активного поставщика по ID; версия сохраняет его имя/УНП. Новый документ или исправление без ID отклоняются. Точный повтор ранее сохранённого строкового источника сохраняется; старые редакции без ID читаются как несопоставленные и могут получить новую редакцию после выбора поставщика. Несопоставленный старый черновик не идёт на расчёт проводок или новую складскую приёмку, а уже проведённый исторический источник остаётся читаемым. Новая несохранённая накладная предупреждает при выборе другой накладной, смене юрлица, переходе по внутренней ссылке и закрытии или перезагрузке страницы. «Сохранить и закрыть» скрывает форму и оставляет запись в реестре только после подтверждения сервером следующей версии этого документа; ошибка оставляет форму с правками открытой. История показывает исполнителя, серверное время и сравнение полей «было → стало» соседних неизменяемых редакций, включая строки накладной; полный снимок можно раскрыть. | Справочник поставщиков закупок связан с основным MDM-каталогом только по УНП без FK; эта связь не даёт доказанной единой карточки контрагента. |
| Остальные виды | Требуют проверки по каждому маршруту. | Общая приёмка не заявлена. |

закрытие или перезагрузку страницы. Затем применить контракт к остальным документам по отдельности.
