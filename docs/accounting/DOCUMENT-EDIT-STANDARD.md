# Единый сценарий оформления документов

Требование пользователя от 24.09.2026. Применяется к документам CRM, закупок,
склада, финансов и бухгалтерии. Готовность каждого вида документа проверяется
отдельно; наличие похожего механизма у другого вида не считается приёмкой.

1. У документа есть устойчивый ID, юрлицо, вид и отображаемый номер. Номер в
   реестре открывает именно этот документ и его версию в пределах прав юрлица.
2. Поля, для которых существует справочник (контрагент, договор, номенклатура,
   склад, статья и другие), выбираются по ID из него. При сохранении фиксируются
   ID и существенные реквизиты на дату документа; переименование справочника
   не переписывает историю. Неизвестные старые связи показываются как
   несопоставленные, без догадки по названию.
3. При редактировании видна команда **«Сохранить и закрыть»**. Она закрывает
   форму только после подтверждённой сервером записи. Ошибка, потеря ответа
   или конфликт версий оставляют форму открытой; повтор не создаёт дубль.
   При несохранённых изменениях простой выход предупреждает пользователя.
4. Каждое успешное изменение имеет неизменяемую запись: серверное время,
   исполнитель, вид документа, ID/номер, редакция, изменённые поля и значения
   до/после. История доступна из карточки и отфильтрована по юрлицу. Старые
   записи без автора или прежнего значения помечаются как неполные.
5. Проведённый или отправленный документ не правится как черновик. Исправление
   создаёт связанную редакцию либо корректирующий документ по правилам вида,
   с основанием и сохранением исходного оригинала.

## Текущее покрытие по коду на 25.09.2026

| Участок | Есть | Пробел |
| --- | --- | --- |
| Карточка сделки CRM | «Сохранить и закрыть» закрывает редактор только после успешного ответа PATCH; отказ, сбой и конфликт оставляют значения в форме, уход с несохранёнными правками предупреждает. GET карточки отдаёт отпечаток восьми полей редактора; при PATCH с этим отпечатком сервер под блокировкой сделки проверяет исходные значения и возвращает 409 при устаревшей форме. PATCH записывает изменённые поля «до/после», автора и серверное время в общий журнал аудита одной транзакцией со сделкой; карточка показывает историю только после проверки права видеть точную сделку. Неизвестное юрлицо старой сделки отображается как неизвестное. | Это контроль конкуренции формы карточки, а не глобальная версия всей сделки: старые API-клиенты без отпечатка продолжают работать. Сохранение пока не возвращает квитанцию с версией; журнал не защищён отдельным ограничением БД от прямого изменения. Валюта суммы сделки не закреплена в этом поле. Старые изменения до включения журнала неизвестны. PostgreSQL и пользовательский сценарий ещё требуют проверки. |
| Товарные позиции сделки CRM | Подбор идёт по ID активной номенклатуры. Добавление использует стабильный ключ запроса при повторе после неопределённого ответа; повтор с другой ценой отклоняется. Количество и цена строки имеют отпечаток текущей редакции; сохранение и удаление из формы передают его серверу. Конкурирующее изменение возвращает 409, оставляет введённые поля и не переписывает строку. Добавление, изменение и удаление записывают автора, время, SKU и значения «до/после» в историю сделки одной транзакцией. Одновременные PATCH проверены на временном PostgreSQL: один 200, второй 409, одна запись аудита. | Старые API-клиенты ещё могут отправлять PATCH/DELETE без отпечатка. Прямой доступ к БД не защищён от обхода журнала. История до включения аудита неизвестна; пользовательская проверка интерфейса ещё нужна. Изменение строки сделки не изменяет уже выпущенный оригинал счёта. |
| Заказ поставщику | Номер ведёт из списка в карточку; серверные команды содержат исполнителя, время и эффект, а карточка показывает историю изменений. «Сохранить и закрыть» отправляет одну атомарную команду для новой позиции, фрахта, плана и статуса. Сервер хранит одну квитанцию и историю изменённых полей; сбой позднего шага откатывает весь пакет. При создании поставщик и позиции выбираются из справочников по ID; имя/УНП поставщика и код/название/единица товара фиксируются в неизменяемой квитанции. Изменившийся или заблокированный справочник блокирует новую запись. Миграции 0177–0178 согласуют проверки PostgreSQL с этими квитанциями. Несохранённые поля или неопределённый результат команды предупреждают при переходе по внутренней ссылке, смене юрлица и закрытии или перезагрузке страницы. | Прежние API-команды ради точного повтора ещё допускают строкового поставщика и SKU. Старые профили поставщиков без подтверждённого Counterparty ID остаются несопоставленными; новый документ с ними не создаётся. |
| Счёт CRM | Реестр сделки хранит номер и связанные версии, оригинал выпущенного счёта защищён. Выпуск требует подтверждённой привязки покупателя к общему справочнику контрагентов по ID и сохраняет снимок реквизитов. В форме подтверждения покупатель выбирается поиском по карточкам справочника с видимыми УНП и ID; выдача ограничена правами на сделку и юрлицо. | Сделка может быть создана без подтверждённого контрагента. Нет единого редактирования с историей полей «до/после» и исполнителем для каждого изменения. |
| Замена счёта CRM | Выпущенный счёт сохраняет исходный оригинал. Для товарного счёта, выпущенного в ERP, новая версия становится доступной после проверенного аннулирования старого: квитанция аннулирования привязана к тому же юрлицу и версии, возврат оплаты и отсутствие отгрузки проверены, резерв освобождён. Новый выпуск использует обычные ERP-проверки цен, покупателя и склада, атомарно связывает версии; точный повтор ключа не создаёт второй резерв. На PostgreSQL проверен сценарий с резервом «со склада». | Отмена и выпуск происходят отдельными подтверждёнными действиями: неудача второго не возобновляет старый счёт. Замена режима «под заказ», счета после физической отгрузки и пользовательская проверка экрана ещё не приняты; для отгруженного счёта требуется отдельное исправление/возврат. |
| Черновики документов сделки | Номер в реестре открывает карточку точного документа. Условия оплаты и поставки редактируются только у черновика; «Сохранить и закрыть» требует отпечаток его исходных полей и подтверждение точного ответа API. Конфликт, отказ или неизвестный результат оставляют ввод в форме. Серверная история показывает автора, время и значения до/после, отдельно по ID документа и в рамках доступа к сделке. | История включена только для двух полей с этого выпуска; прежние правки неизвестны. Выпуск новой версии счёта подтверждён только для ERP-счёта после проверенного аннулирования прежнего и освобождения резерва. Прямое изменение БД вне API не защищено отдельным запретом для журнала. PostgreSQL и реальная приёмка остальных полей ещё открыты. |
| Исключение: продажа вне CRM | Ручная форма бухгалтерских проводок по документу вне CRM ищет покупателя в общем справочнике через API выбранного юрлица. Новые preview и confirm требуют ID, имя, УНП и редакцию действующей карточки; свободный текст и устаревшие реквизиты отклоняются. Товар выбирается по ID из активного справочника SKU; код, название и единица сверяются при расчёте и проведении. Снимки покупателя и товара попадают в основание проводки, а точный повтор ранее проведённой операции остаётся доступным после изменения справочника. Служебные пространства источников CRM и WMS нельзя выдать за внешнее основание, включая варианты номера с пробелом или ведущим нулём. Форма считает продажу проведённой только после сверки квитанции с юрлицом, источником, версией, видом операции, политикой, датами и digest подготовленного пакета; несовпадение оставляет пакет для точного повтора. | Исторические продажи без ID остаются читаемыми без автоматического сопоставления. Договор и склад этой ручной формы ещё вводятся текстом; невозможность автоматического сопоставления произвольного внешнего документа с CRM требует бухгалтерской сверки. Пользовательский сценарий и PostgreSQL-проверка ручной формы остаются открытыми. |
| Бухгалтерское списание запасов | После предварительного расчёта форма сверяет квитанцию проведения с юрлицом, источником, версией, политикой, датами и digest пакета. Для списания нулевой стоимости дополнительно проверяются регистрационный номер, токен и основание. Несовпадение не закрывает подготовленный пакет и не показывает ложный успех. | Склад и номенклатура этой ручной формы ещё вводятся текстом; подтверждение на PostgreSQL и пользовательский сценарий остаются открытыми. |
| Накладная поступления | Черновик и редакции находятся в разделе закупок, проведённый источник защищён. Новая форма и API требуют выбора активного поставщика по ID; версия сохраняет его имя/УНП. Новый документ или исправление без ID отклоняются. Точный повтор ранее сохранённого строкового источника сохраняется; старые редакции без ID читаются как несопоставленные и могут получить новую редакцию после выбора поставщика. Несопоставленный старый черновик не идёт на расчёт проводок или новую складскую приёмку, а уже проведённый исторический источник остаётся читаемым. Новая несохранённая накладная предупреждает при выборе другой накладной, смене юрлица, переходе по внутренней ссылке и закрытии или перезагрузке страницы. «Сохранить и закрыть» скрывает форму и оставляет запись в реестре только после подтверждения сервером следующей версии этого документа; ошибка оставляет форму с правками открытой. История показывает исполнителя, серверное время и сравнение полей «было → стало» соседних неизменяемых редакций, включая строки накладной; полный снимок можно раскрыть. | Старые профили поставщиков без Counterparty ID остаются несопоставленными; новые редакции поступлений требуют активной подтверждённой связи. |
| Прямое бухгалтерское поступление | Новое поступление нельзя создать через старые `/accounting/.../purchases/preview` и `/confirm`: API направляет в реестр накладных «Закупок». Общий маршрут ручной операции также не создаёт новую проводку вида `inventory_purchase`; новая проводка допускается только через проверенный источник закупок. Старая бухгалтерская форма заменена переходом в реестр с выбранным юрлицом. Для ранее проведённой прямой операции остаются просмотр расчёта и точный повтор той же версии без нового движения. | Исторические прямые поступления без первичной накладной перечисляются отдельно для ручной сверки; автоматического сопоставления по имени нет. |
| Ручная бухгалтерская операция | Форма показывает расчёт проводок до записи; «Провести и закрыть» закрывает её только после квитанции с ID, юрлицом, источником, версией, видом операции, политикой, датой и digest проверенного пакета. При ошибке или несовпадении квитанции форма остаётся открытой. Проведённая запись доступна через журнал и карточку операции; исправление создаётся отдельной связанной операцией. | Это не черновик с «Сохранить и закрыть»: ещё нет истории редактирования полей черновика «до/после» и предупреждения при выходе с несохранённой формой. |
| Запрос цен (RFQ) | Новый RFQ с устойчивым номером RFQ-ID создаётся из заявки с подтверждённым юрлицом; номер открывает карточку в реестре. Предложение принимает только активного поставщика, связанного с основным справочником по ID. Ключи создания и предложения позволяют повторить неопределённую отправку без дубля; браузер сохраняет такой ключ до подтверждения. Победитель выбирается в том же юрлице, без автоматического заказа. История создания, предложения и выбора победителя хранит автора, серверное время и состояние до/после; другой компании она не выдаётся. | Старые RFQ без подтверждённого ключа не появляются в реестре выбранной компании и требуют ручного сопоставления. Для RFQ ещё нет полноценного черновика с общей командой «Сохранить и закрыть»; PostgreSQL-приёмка миграции и пользовательский сценарий остаются открытыми. |
| Остальные виды | Требуют проверки по каждому маршруту. | Общая приёмка не заявлена. |

Программные переходы из глобального окна входящего звонка теперь запрашивают
подтверждение у открытого редактора до перехода в сделку или создания лида.
Осталось закрыть кнопку браузера «Назад» и остальные программные переходы:
App Router не предоставляет редакторам `beforePopState` из Pages Router
([API App Router](https://nextjs.org/docs/app/api-reference/functions/use-router),
[API Pages Router](https://nextjs.org/docs/pages/api-reference/functions/use-router)).
Текущий guard защищает ссылки внутри приложения, закрытие и перезагрузку
страницы. Проверка остальных видов документов проводится отдельно.
