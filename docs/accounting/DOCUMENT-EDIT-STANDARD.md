# Единый сценарий оформления документов

Требование пользователя от 24.09.2026. Применяется к документам CRM, закупок,
склада, финансов и бухгалтерии. Готовность каждого вида документа проверяется
отдельно; наличие похожего механизма у другого вида не считается приёмкой.

1. У документа есть устойчивый ID, юрлицо, вид и отображаемый номер. Номер в
   реестре открывает именно этот документ и его версию в пределах прав юрлица.
2. Поля, для которых существует справочник (контрагент, договор, номенклатура,
   склад, статья и другие), выбираются по ID из него. При сохранении фиксируются
   ID и существенные реквизиты на дату документа; переименование справочника
   не переписывает историю. Неизвестные старые связи показываются как
   несопоставленные, без догадки по названию.
3. При редактировании видна команда **«Сохранить и закрыть»**. Она закрывает
   форму только после подтверждённой сервером записи. Ошибка, потеря ответа
   или конфликт версий оставляют форму открытой; повтор не создаёт дубль.
   При несохранённых изменениях простой выход предупреждает пользователя.
4. Каждое успешное изменение имеет неизменяемую запись: серверное время,
   исполнитель, вид документа, ID/номер, редакция, изменённые поля и значения
   до/после. История доступна из карточки и отфильтрована по юрлицу. Старые
   записи без автора или прежнего значения помечаются как неполные.
5. Проведённый или отправленный документ не правится как черновик. Исправление
   создаёт связанную редакцию либо корректирующий документ по правилам вида,
   с основанием и сохранением исходного оригинала.

Программные переходы из глобального окна входящего звонка теперь запрашивают
подтверждение у открытого редактора до перехода в сделку или создания лида.

Статус договора, заказа или счёта «Выпущен в ERP» относится только к локальному
документу. Отсутствие ссылки 1С не является ошибкой выпуска и не показывается
как предупреждение. Если проверенный исходящий адаптер вернул внешнюю ссылку,
она отображается отдельно; локальный выпуск сам по себе не доказывает проводку
в бухгалтерии или отправку документа клиенту.

Для исправления черновика накладной закупок API принимает ключ запроса и
сохраняет его в неизменяемой редакции. Повтор с тем же ключом, автором,
исходной версией и содержимым возвращает уже сохранённый результат, даже если
справочник с тех пор изменился. При потерянном ответе форма удерживает точную
команду и повторяет её без новой редакции; «Сохранить и закрыть» срабатывает
только после подтверждения ID, номера версии и ключа редакции. Для старых
редакций ключ отсутствует и не реконструируется задним числом. Проверка
конкурентного повтора на PostgreSQL остаётся частью общей приёмки БД.

Для новой физической приёмки по накладной склад выбирается из реестра WMS,
привязанного к юрлицу. ID и стабильное имя склада входят в неизменяемую
команду приёмки; сервер и миграционный guard проверяют их совпадение и
владельца. Если склад в первичной накладной назван иначе, отличие допускается
только как явное сопоставление с основанием, без переписывания оригинала.
Старые физические приёмки без ID склада остаются читаемыми и точно повторяемыми;
автоматического присвоения им нового ID нет. Поле склада самой накладной
остаётся текстовым оригиналом поставщика, а физический склад привязан к WMS.

Новая накладная закупок выбирает договор по ID из отдельного реестра,
привязанного к юрлицу и проверенному поставщику. Номер договора замораживается
в редакции; сервер проверяет ID, поставщика и даты. Если зарегистрированного
договора нет, пользователь указывает явное основание исключения. Старые
текстовые ссылки на договор не сопоставляются автоматически и не проходят
новое проведение до редакции с ID или основанием. Регистрация договора требует
номера, даты подписания и описания проверенного оригинала; сама по себе запись
в реестре не заменяет проверку подписанного документа бухгалтером.
Ошибочно зарегистрированный или более не действующий договор отзывается
однократно с причиной, автором, серверным временем и устойчивым ключом команды.
Отзыв скрывает его из списка действующих договоров; исторический ID и
сохранённые редакции накладных не изменяются. Новый договор с прежним номером
регистрируется отдельной карточкой и новым ID с собственным основанием.
Если ответ на отзыв потерян, интерфейс повторяет ровно ту же команду.
Раздел «Отозванные договоры поставщика» показывает номер, ID, основание
регистрации, автора и время регистрации, а также автора, время и причину
отзыва. Отозванные договоры загружаются отдельным запросом
`GET /procurement/organizations/{org_id}/supplier-contracts?supplier_id={id}&status=revoked`;
обычный список `status=active` остаётся единственным источником выбора для
новой накладной. Оба списка ограничены выбранным юрлицом и поставщиком.
История отзыва загружается страницами до 100 записей; следующая страница
запрашивается по паре `before_at`/`before_id` от последней показанной записи.
При одинаковом времени отзыва вторым ключом порядка служит неизменяемый ID.
Осталось закрыть кнопку браузера «Назад» и остальные программные переходы:
App Router не предоставляет редакторам `beforePopState` из Pages Router
([API App Router](https://nextjs.org/docs/app/api-reference/functions/use-router),
[API Pages Router](https://nextjs.org/docs/pages/api-reference/functions/use-router)).
Текущий guard защищает ссылки внутри приложения, закрытие и перезагрузку
страницы. Проверка остальных видов документов проводится отдельно.
