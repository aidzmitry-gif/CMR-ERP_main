# Пример переноса остатков

Это синтетический пример формата `opening-balance-v1`, а не выгрузка действующего ООО и не подтверждённая бухгалтером проводка. Он проверен моделью `ImportInput` из кода `6e86b38`; проверка структуры не заменяет предварительный расчёт на настроенном юрлице.

- `opening-source.synthetic.json` — пять исходных остатков с аналитикой.
- `opening-package.synthetic.json` — соответствующее тело запроса импорта. SHA-256 в `source_digest` рассчитан по точным байтам первого файла (UTF-8, без BOM).

| Счёт в примере | Дебет, BYN | Кредит, BYN | Аналитика |
|---|---:|---:|---|
| 51 | 1000,00 | — | Дополнить по рабочему плану юрлица |
| 41 | 500,00 | — | Склад, товар, партия; количество 5 |
| 62 | 200,00 | — | Покупатель, договор, документ расчётов |
| 60 | — | 300,00 | Поставщик, договор, документ расчётов |
| 80 | — | 1400,00 | Явный остаток исходного примера |
| Всего | 1700,00 | 1700,00 | 1 запись, 5 строк |

Капитал в примере взят из исходной строки. При расхождении реальной выгрузки нельзя вычислять капитал как недостающую разность или добавлять компенсирующую строку.

## Подготовка реального пакета

1. Зафиксировать одно юрлицо и дату перехода. Текущий протокол принимает только первое число месяца; это ограничение реализации, а не утверждение о нормативном требовании.
2. Сохранить исходную выгрузку неизменной. Внести SHA-256 её точных байтов в `source_digest`; если исходных файлов несколько, предварительно согласовать единый архив и хешировать его. Пересохранение файла с другими переносами строк меняет хеш.
3. Заменить все идентификаторы `DEMO-*` на сопоставленные устойчивые идентификаторы справочников. Один пакет относится к юрлицу из URL. Поле `policy_id: 1` в примере — технический заполнитель, его необходимо заменить идентификатором применимой политики этого юрлица. Счета, субсчета и обязательная аналитика должны соответствовать его рабочему плану.
4. Перенести раздельные дебетовые и кредитовые остатки по аналитике, количество и партии. Суммы передавать десятичными строками без разделителей тысяч. Валютные остатки дополнительно требуют исходной суммы, курса, масштаба, даты и источника курса; текущий пример содержит только BYN. Он не показывает забалансовый импорт.
5. Заполнить `batch`, устойчивый `source` каждой записи, версию источника, правило и объяснение, даты, основание сверки `evidence`. Создать новый `request_key` для нового пакета. Пересчитать четыре контрольных значения: число записей, число строк, дебет и кредит. Даты отражения всех записей должны совпадать с `cutover_date`, `opening` должен быть `true`; пакет исправлений этим протоколом не поддерживается.
6. Выполнить только предварительный расчёт: `POST /accounting/organizations/{org_id}/imports/preview`. В интерфейсном API префикс — `/api/accounting`. Нужны права главного бухгалтера выбранного юрлица. Проверить применимость политики, счета, аналитику и контрольные итоги; JSON-валидация сама этого не доказывает.
7. После сверки бухгалтером тот же пакет передаётся в `/imports/confirm`. Сохранить квитанцию, идентификаторы проводок и исходную выгрузку. Повтор точного пакета с прежним ключом идемпотентен; менять ключ ради повторной загрузки нельзя. Новые суммы требуют отдельного согласованного исправления, а не изменения проведённой истории.

Ограничения текущей модели: не более 500 записей и 1000 строк суммарно в пакете. Большую выгрузку нельзя произвольно делить на несбалансированные части или компенсировать расхождения придуманными счетами. Способ переноса согласуется до подтверждения.

Для реального месяца использовать также [контрольный комплект приёмки](../PILOT-MONTH-ACCEPTANCE.md). Ни один файл из этой папки не был отправлен в рабочую бухгалтерскую базу.
