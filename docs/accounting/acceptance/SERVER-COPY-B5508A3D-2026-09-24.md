# G07P: проверка точного backend-кандидата на наполненной копии

24.09.2026, 09:27–09:39 UTC. Рабочий backend и БД остались без переключения:
после проверки действующее приложение было запущено с прежним image ID
`sha256:4d86679ee28ea17494e3eeed7e183a0e838b4b19f5f1caf0e804d8c5ed441d9b`,
рабочая схема — `0116 (head)`.

Ранее сохранённый live-read архив 07:33 UTC (1 841 158 байт, SHA-256
`0d3bd395a2c58bf24e314d0412863aa813f98eb4a9f4fe361d716cd9663e3971`)
повторно восстановлен в две отдельные БД: эталон `aios_before` и копию
`aios_copy`. Обе начинались с `0116`. PostgreSQL-контейнер имел
`--network none`, без открытых портов, с отдельным анонимным томом и
архивом, подключённым только для чтения. Production volume не подключался.

На сервер загружен exact Linux/amd64 backend image
`sha256:013ee1c3601bd4d9e3bfe44c6f0824aab485d053b96a42c7b17a8d3fae7580e0`
из локального source `b5508a3d`. Только против `aios_copy` этот image
выполнил явный `alembic upgrade head`: результат `0176`. Сравнение
эталона и мигрированной копии по исходным колонкам показало
`matched=113`, `baseline_rows=49959`, `missing_columns=[]`,
`content_mismatches=[]`. Служебная `alembic_version` исключена из
сравнения содержимого. После проверки временный PostgreSQL-контейнер и
его анонимный том удалены; рабочее приложение осталось запущенным на
прежнем image и схеме `0116`.

Это доказательство совместимости миграций с одной прочитанной копией,
а не готовность к production. Архив сделан без остановки записи и не
является final write-frozen backup. Не проверены полный write freeze,
парное восстановление приватных файлов, переключение/возврат frontend
и backend, authenticated UI, реальная сверка с 1С и приёмка бухгалтером.
Решение смешанного выпуска остаётся **NO-GO**.
