# CRM-ACC-001: локальная проверка барьеров записи backend-кандидата

Точный source `b5508a3d0f887d54d3a4998bf27bd62370208961` собран из
2617/2617 Git blobs корня и десяти закреплённых модулей. Локальный
Linux/amd64 image:
`sha256:013ee1c3601bd4d9e3bfe44c6f0824aab485d053b96a42c7b17a8d3fae7580e0`
(122385709 байт). Он **не** опубликован и не отправлен на сервер.

На пустой синтетической PostgreSQL во внутренней Docker-сети без host-портов
этим образом отдельно выполнена миграция до Alembic `0176`. Затем создана
временная роль с `pg_read_all_data`, без прав записи и с транзакциями только
для чтения. Она прочитала контрольную строку; прямой `INSERT` завершился
`cannot execute INSERT in a read-only transaction`.

Backend запущен с этой ролью, read-only root filesystem и тремя явными
флагами: `AIOS_SKIP_AUTOMIGRATE=1`, `AIOS_DISABLE_ASYNC_WRITERS=1`,
`AIOS_BLOCK_HTTP_WRITES=1`. `GET /health` вернул 200, `POST /health` вернул
503 с кодом `pilot_http_writes_disabled`. В startup-логе подтверждены
пропуск неявной миграции и фоновых задач; синтетический пароль в нём не
встречается. После проверки Alembic остался `0176`, контрольная строка —
одна. Обычный режим без флагов сохранил прежний HTTP 405 на POST `/health`
и запуск Alembic в entrypoint. Целевые lifecycle/background тесты — 6 passed;
Ruff, compileall и diff-check прошли.

Временные контейнеры, БД/volume, сеть и материализованный source удалены;
локальный image сохранён. Это проверка барьеров на синтетических данных:
GET-маршруты не объявляются безопасными для записи только по HTTP-методу,
поэтому ограничение БД обязательно. На реальном сервере ещё нужны
проверка всех входящих путей и писателей, миграция наполненной копии **этим**
image, парный write-frozen backup/restore, испытанный frontend switch,
OIDC-проверка бухгалтера и сверка с 1С. Решение о выпуске — `NO-GO`.
