## Ворота до начала окна

1. Повторно считать фактические server image ID, `alembic current`,
   systemd frontend WorkingDirectory/ExecStart/BUILD_ID, Compose и runtime
   fingerprint. Снимок от 06:30 UTC — ориентир, не разрешение переключить
   изменившийся сервер. Любой дрейф — новая карточка и новая репетиция.
2. Довести до проверяемого состояния отдельный маршрут миграционного и
   frontend-выпуска. Он должен сверять полные image ID и SHA-256 архива,
   не брать файлы из грязного `/opt/cmr-erp`, выдавать финальный receipt и
   не запускать `belakb-deploy-v1 apply` на изменённой схеме. Существующий
   systemd frontend не принимает Docker tar как готовую замену: требуется
   отдельно испытанный способ переключения и возврата его runtime.
3. Инвентаризировать все источники записи: API, фоновые задачи, таймеры,
   webhooks, прямой DB-доступ и внешние интеграции. Подготовленные ранее
   Caddy maintenance/read-only правила и PGOPTIONS кандидата проверялись на
   отдельном стенде; непосредственно перед этим выпуском проверить их заново.
   Read-only одного процесса не блокирует иных писателей.
4. Согласовать конкретный тестовый набор юрлиц, ролей и документов с
   бухгалтером. Реальная учётная политика, начальные остатки, налоговые
   версии и сверка с 1С пока не приняты; выпуск пилота не делает их готовыми.

## Последовательность только после прохождения ворот

1. Зафиксировать ID окна и входные хеши. Закрыть внешний приём изменяющих
   запросов, остановить таймеры и фоновые записи, дождаться завершения
   транзакций. До доказанного отсутствия всех писателей БД не делать dump
   для отката. Сохранять исходные настройки и состояния служб, не очищать
   очереди. Для непринятых webhook после окна нужна сверка источника.
2. Создать **новый write-frozen** защищённый custom dump БД и согласованный
   снимок файлов/вложений/приватных payroll-источников. Записать SHA-256,
   размеры, права доступа, состав и общую точку времени. Проверить
   `pg_restore --list`, восстановить эту пару в отдельный изолированный
   стенд и повторить `0116 → 0176` точным образом с построчной сверкой.
   Live-read dump от 07:33 UTC годится только как репетиция, не как этот
   rollback baseline.
3. Если копия, файлы или контрольные суммы не совпали — остановиться **до
   production-миграции** и вернуть прежний приём без переключения. Если
   прошли, явно проверить ровно одну исходную ревизию `0116` и выполнить
   миграцию отдельным контролируемым процессом под блокировкой записи.
   Старт приложения с его автоматическим `alembic upgrade head` не должен
   становиться неявным первым шагом миграции. После неопределённого сбоя
   сначала считать фактическую схему; слепой повтор запрещён.
4. При `0176` сверить исходные таблицы, строки, регистры и приватные файлы.
   Только затем запустить backend-кандидат с контролируемой read-only
   конфигурацией, проверить image ID, конфигурационный fingerprint,
   `alembic current`, health и отсутствие новых записей/отправок.
   Новый кандидат поддерживает `AIOS_SKIP_AUTOMIGRATE=1` для явного пропуска
   миграции при запуске API, `AIOS_DISABLE_ASYNC_WRITERS=1` для пропуска
   startup-хуков, outbox/tick-цикла, синхронизации курсов и почтового worker,
   а также `AIOS_BLOCK_HTTP_WRITES=1` для запрета HTTP-методов изменения.
   Эти флаги **не являются** полномочиями БД и не делают GET-запросы
   гарантированно без записи: нужны отдельные сетевой gate и роль БД только
   для чтения. Квитанция синтетического прогона —
   `PILOT-BACKEND-READONLY-GATES-2026-09-24.md`.
5. Переключить frontend только через отдельно испытанный маршрут с
   сохранённой старой точкой запуска и точным BUILD_ID. Проверить login
   redirect, реальный OIDC-вход уполномоченного пользователя, выбор юрлица,
   план счетов, предварительный расчёт проводки, журнал, ОСВ и переход к
   первичному документу. Изолированный анонимный HTTP smoke этого не
   заменяет. Результат записать в receipt до открытия записи.
6. После явного принятия пилотного сценария восстановить обычный режим
   записи и таймеры по сохранённым исходным состояниям; проверить очереди
   и непринятые события. Зафиксировать новый baseline. Внешнюю отчётность,
   ЭСЧФ и реальные 1С-остатки не отправлять/импортировать этой процедурой.

## Возврат и стоп-состояния

- До изменения production-схемы можно вернуться к исходным сервисам и
  настройкам после проверки, что данных они не меняли.
- После `0176` старый backend с графом до `0116` нельзя считать
  совместимым. Возврат образа сам по себе БД не откатывает. Нужен либо
  отдельно проверенный совместимый rollback image для `0176`, либо
  отдельный контролируемый возврат пары БД+файлы к write-frozen снимку.
  Ни один из этих вариантов ещё не принят для кандидата.
- Восстановление снимка уничтожило бы записи после его времени. После
  первого возможного нового write, включая фоновые задачи, автоматический
  откат запрещён. При неопределённости сохранить режим обслуживания,
  зафиксировать новые операции и согласовать восстановление или исправление
  вперёд; не запускать старый app и не открывать доступ по таймауту.
- Frontend можно вернуть к сохранённой старой точке запуска только после
  проверки её совместимости с фактической схемой/API и точного BUILD_ID.

Финальный receipt должен содержать ID окна, фактические исходные image,
схему, frontend BUILD_ID и runtime fingerprint; SHA-256 пары backup;
результат восстановления и сверки; команду и итог миграции; точные новые
image/BUILD_ID; проверки ролей, юрлица и документа; состояние очередей;
время открытия записи; решение `DEPLOYED`, `ROLLED_BACK` либо
`MANUAL_RECOVERY_REQUIRED`; и следующий baseline. `STARTED` или HTTP 200
без входа не являются итогом.

## Итог локальной проверки

Точные локальные backend/frontend image IDs, hash frontend tar и единственный
head `0176` подтверждены. Новый backend-кандидат стартовал с синтетической
PostgreSQL без неявной миграции и фоновых процессов; на пустой БД отдельная
миграция им же дошла до `0176`. Синтетическая роль без прав записи отклонила
INSERT, а HTTP write gate отклонил POST при работающем GET. Серверная
репетиция наполненной **live-read
копии** выполнена и для нового backend image: 113/113 прежних таблиц и
49 959 строк совпали. Standalone frontend стартовал и остановился под
локальным WSL systemd на точной версии Node. Но final write-frozen backup,
испытанный switch/rollback рабочего systemd-сервиса, текущий server
preflight, authenticated UI и сверка с 1С отсутствуют. Поэтому
решение остаётся `NO-GO`, а цель — активной.
