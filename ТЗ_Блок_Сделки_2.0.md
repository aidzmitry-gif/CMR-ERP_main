# ТЗ «Блок Сделки 2.0» — управляемая воронка продаж

**Модуль:** `sales` (git submodule → github.com/aidzmitry-gif/CRM.git; правка = коммит в submodule + bump указателя в суперпроекте)
**Схема БД:** `sales` · **API-префикс:** `/sales` · **Источник схемы Postgres:** Alembic
**Автор постановки:** РОП (5 лет, построение и автоматизация ОП)
**Статус:** черновик к реализации
**Дата:** 2026-06-11

## 0. Цель и принцип

Сейчас блок сделок — это «движок воронки» (канбан, лиды, документы, события). Цель 2.0 —
превратить его в **инструмент управления отделом продаж**: чтобы РОП мог ежедневно
контролировать движение сделок, видеть прогноз выручки, конверсию и работу каждого менеджера,
а сделки не «умирали молча».

> **Границы scope:** сама сделка и её рабочий контур — карточка, доска сделок, экран сделки, задачи/история/прогноз **по сделке**, плюс **личный план менеджера** (план/факт на день/неделю/месяц/год; продавец ставит его себе сам и согласует с РОПом — SALES-47). Всё это живёт **в блоке сделок**. Отдельно (в другом окне) — только **агрегатная вкладка РОПа**: сводки план/факт по всем менеджерам, рейтинги, аналитика отдела. Её данные и события мы здесь закладываем, но сам управленческий экран — **вне scope**.

Внедряем 7 блоков + сопутствующие правки, каждый — самостоятельный и поставляемый отдельно. Порядок в §8.

| Код | Блок | Приоритет | Объём |
|-----|------|-----------|-------|
| SALES-40 | Закрытие в проигрыш + причины отказа | 🔴 critical | S |
| SALES-41 | Задачи по сделке + контроль просрочки | 🔴 critical | M |
| SALES-42 | `owner` → сотрудник + видимость «свои/все» | 🔴 critical | M |
| SALES-43 | История стадий + висяки (по сделке) | 🟠 high | S–M |
| SALES-44 | Вероятность + взвешенная сумма (поля сделки) | 🟠 high | M |
| SALES-47 | Личный план продаж (день/неделя/месяц/год) + согласование с РОПом | 🟠 high | M |
| SALES-46 | Сопутствующее (created_at, speed-to-lead, сумма из позиций, антидубль) | 🟡 medium | S каждый |
| SALES-49 | Сворачиваемая панель чатов + счётчик непрочитанных | 🟡 medium | S |

### Соглашения, общие для всех блоков
- **Транзакция** — у роута; репозиторий не коммитит. События — `core.event_bus.emit(session, type, payload)` в той же транзакции (→ outbox → audit).
- **Мягкие ссылки между схемами** (как `DealItem.sku_id`): храним `*_id` как `int` **без** cross-schema FK, резолвим join-ом. Это касается `owner_id → hr.employee`.
- **RBAC:** новые права объявляются в [permissions.py](modules/sales/permissions.py); роли `Менеджер` / `РОП` / `Админ` (суперюзер).
- **Миграции:** на каждый блок — отдельная Alembic-ревизия `sales: <код> <описание>`. В SQLite-dev таблицы создаются `create_all` автоматически.
- **Тесты:** маркеры `unit` (логика без I/O), `api` (httpx ASGI на SQLite), `integration` (Postgres testcontainers). На каждый блок — минимум api-тест на happy-path + 1 граничный.

## SALES-40 — Закрытие в проигрыш + причины отказа

### Проблема
[stages.py](modules/sales/stages.py) имеет единственную терминальную стадию `won`. Нельзя
посчитать конверсию (нет `lost`), нет причины слива. Сделки зависают навсегда.

### Модель данных
**Новая таблица-справочник `sales.loss_reason`:**

| Поле | Тип | Прим. |
|------|-----|-------|
| id | int PK | |
| code | str(32) unique | `price`, `competitor`, `no_need`, `no_answer`, `timing`, `no_stock`, `other` |
| title | str(128) | «Дорого», «Ушёл к конкуренту», … |
| sort_order | int | порядок в выпадашке |
| active | bool | мягкое скрытие из выбора |

**Изменения `Deal`** ([models.py](modules/sales/models.py)):
- `lost_reason_code: str | None` (String(32), nullable) — код причины из справочника.
- `lost_comment: str | None` (String(255), nullable) — комментарий менеджера.
- (`closed_date` уже есть — используем как дату закрытия в обе стороны.)

**Стадия:** добавить в `STAGES` колонку `{"id": "lost", "title": "Закрыто: Отказ", "color": "#EF4444"}`.

### API
- `POST /sales/deals/{id}/lose` — `{reason_code: str, comment?: str}` → `DealRead`.
  Правила: `reason_code` обязателен и должен быть `active`-кодом справочника (иначе 422);
  ставит `stage="lost"`, `closed_date=today`, заполняет `lost_reason_code/comment`;
  emit `sales.deal.lost` `{deal_id, reason_code, amount, owner_id, entity_ref}`.
- `POST /sales/deals/{id}/win` — без тела → `DealRead`. Ставит `stage="won"`, `closed_date=today`;
  emit `sales.deal.won`. (Согласовать с `on_shipment_delivered` в [events.py](modules/sales/events.py) — логистика закрывает в `won`; вынести установку won в общий хелпер, чтобы оба пути писали `closed_date` и событие.)
- `GET /sales/loss-reasons` → список активных причин (для выпадашки).
- (Опц.) `GET|POST|PATCH /sales/loss-reasons` под правом `sales.deal.approve` — управление справочником РОПом.

### Бизнес-правила
- Перетаскивание карточки в колонку `lost` на канбане **обязано** открыть модалку выбора причины — нельзя закрыть в отказ без причины. Drag в `won` причины не требует.
- Повторное закрытие уже закрытой сделки — 409 (или переоткрытие отдельным действием — вне scope).

### UI
- Канбан: новая колонка «Закрыто: Отказ» (красная), по умолчанию **свёрнута/в конце**.
- Drag в `lost` → модалка `LoseDealModal` (radio со списком причин + поле комментария).
- Карточка сделки: при `stage in (won, lost)` показывать плашку результата и причину отказа.

### Метрики, которые открывает блок
- **Win rate** = `won / (won + lost)` за период по `closed_date`.
- **ТОП причин отказа** — `GROUP BY lost_reason_code` (материал для разбора с командой).

### Критерии приёмки
- [ ] Нельзя перевести сделку в `lost` без валидной причины (API возвращает 422).
- [ ] `closed_date` проставляется при `win` и `lose`.
- [ ] `sales.deal.lost` / `sales.deal.won` появляются в audit_log.
- [ ] На доске есть колонка отказа; модалка причины работает.

## SALES-41 — Задачи по сделке + контроль просрочки

### Проблема
`next_step` — просто строка ([models.py:27](modules/sales/models.py#L27)). Поля карточки
«что сделать / время / дата» ([deal-card.tsx:33](frontend/src/components/kanban/deal-card.tsx#L33))
**не сохраняются** — это мок ([api.ts mapDeal](frontend/src/lib/api.ts#L39)). РОП не может построить
два главных отчёта: «сделки без задачи» и «просроченные задачи».

### Модель данных
**Новая таблица `sales.deal_task`:**

| Поле | Тип | Прим. |
|------|-----|-------|
| id | int PK | |
| deal_id | int FK → sales.deal.id | |
| title | str(255) | что сделать |
| kind | str(16) | `call`/`meeting`/`email`/`chat`/`doc`/`other` |
| assignee_id | int \| null | мягкая ссылка на `hr.employee` (см. SALES-42) |
| due_at | datetime \| null | дедлайн |
| status | str(16) | `open` → `done` / `canceled` (default `open`) |
| result | str(255) \| null | итог/коммент при закрытии |
| created_at | datetime | server_default now |
| done_at | datetime \| null | |

**Производное (не хранить):** `overdue = status == "open" AND due_at < now()`.

### API
- `GET /sales/deals/{id}/tasks` → список задач сделки (открытые первыми, по `due_at`).
- `POST /sales/deals/{id}/tasks` — `{title, kind, due_at?, assignee_id?}` → `TaskOut`; emit `sales.task.created`.
- `PATCH /sales/tasks/{task_id}` — частично: сменить `due_at` (перенос), `status=done`+`result` (закрытие). При закрытии — `done_at=now`, emit `sales.task.completed`.
- `GET /sales/deals?has_open_task=false` — сделки без открытой задачи (для подсветки «брошенных» прямо на доске сделок).
- (сводная очередь задач по менеджерам/просрочке — это **вкладка РОПа в отдельном окне**, вне scope; данные для неё доступны через фильтры `GET /sales/deals/{id}/tasks` и поле `due_at`/`status`.)

### Бизнес-правила
- `next_step` сделки делаем **производным** от ближайшей открытой задачи (title + due_at), либо оставляем как короткую ручную заметку — выбрать на ревью; в карточке показывать именно ближайшую задачу.
- Фоновая эскалация (опц., поверх `_background_loop` ядра): задачи, просроченные > N часов, эмитят `sales.task.overdue` → уведомление менеджеру + РОПу (канал — Telegram, когда снимут заглушку [telegram.py](modules/sales/telegram.py)).

### UI
- Карточка на доске: ближайшая задача с датой; **красный индикатор**, если просрочена; жёлтый — если срок сегодня.
- Экран сделки ([deals/[id]/page.tsx](frontend/src/app/crm/deals/[id]/page.tsx)): блок «Задачи» — список + «＋ задача» + кнопка «Выполнено».

### Что открывает блок (данные, без управленческих экранов)
- Флаг просрочки на сделке; доля сделок без открытой задачи; число касаний по сделке.

### Критерии приёмки
- [ ] Задача создаётся/закрывается/переносится через API; `overdue` считается корректно.
- [ ] `GET /sales/tasks?due=overdue` отдаёт только просроченные открытые.
- [ ] Отчёт «сделки без открытой задачи» работает.
- [ ] На карточке виден индикатор просрочки.

## SALES-42 — `owner` → сотрудник + видимость «свои / все»

### Проблема
`owner` — строка ([models.py:26](modules/sales/models.py#L26)). Опечатка = потеря сделки из отчёта;
нет передачи сделки; нет правила «менеджер видит только свои». Параллельно в
[leads.py](modules/sales/leads.py) менеджеры захардкожены в `MANAGERS` — два источника правды.

### Модель данных
- `Deal.owner_id: int | null` — **мягкая ссылка** на `hr.employee.id` (без cross-schema FK, как `sku_id`).
  Поле `owner: str` **оставляем** на переходный период как денормализованную подпись (заполняем `full_name` сотрудника), чтобы не ломать существующий UI/отчёты — депрекейтим позже.
- **Иерархия команд** (для «РОП видит своих»): добавить `hr.employee.manager_id: int | null` (ссылка на руководителя) — правка модуля `hr`. Если иерархию пока не делаем — видимость строим по роли (РОП/Админ — все; Менеджер — только свои `owner_id`).
- (Опц.) пометка, кто из `hr.employee` — продавец: поле `department == "Продажи"` или `role`-таблица; используется как источник для списка менеджеров вместо `MANAGERS`.

### API
- В `POST/PATCH /sales/deals` принимать `owner_id`; денормализованный `owner` проставлять из `hr.employee.full_name` на бэке.
- `POST /sales/deals/{id}/reassign` — `{owner_id}` под правом `sales.deal.write` (или отдельное `sales.deal.reassign` для РОПа) → меняет владельца, пишет в историю (см. SALES-43), emit `sales.deal.reassigned`.
- **Скоуп видимости:** в `GET /sales/board`, `/deals`, `/tasks` применять фильтр по текущему пользователю:
  - `Админ`, `РОП` → все сделки;
  - `Менеджер` → только `owner_id == me` (+ подчинённые, если есть `manager_id`).
  - Текущего пользователя берём из `get_current_user` ([auth.py](core/services/auth.py)); требуется маппинг `CurrentUser.username → hr.employee.id` (добавить хелпер `current_employee_id(session, user)`).
- `GET /sales/managers` → список продавцов из `hr.employee` (заменяет хардкод `MANAGERS` для UI и роутинга лидов).

### Миграция данных
- Бэкфилл `owner_id`: сматчить существующий `Deal.owner` (строка) с `hr.employee.full_name`; несовпавшие — пометить в лог, оставить `owner_id = null`.
- Роутинг лидов ([leads.py](modules/sales/leads.py)) перевести на `hr.employee` (специализация по гео/продукту — вынести в данные сотрудника или отдельный конфиг; убрать `MANAGERS`-хардкод). Это отдельная под-задача, можно фазой 2.

### Бизнес-правила / подводные камни
- Auth сейчас dev-заглушка (заголовки `X-User`/`X-User-Roles`, дефолт «Админ»-суперюзер) — **скоуп видимости должен корректно работать и в dev**: если пользователь не резолвится в сотрудника, для роли Менеджер показывать пусто (а не «всё»), чтобы правило не протекало.
- Не ставить жёсткий FK `sales → hr` (кросс-схема) — придерживаться мягкой ссылки (конвенция проекта).

### Критерии приёмки
- [ ] Сделка создаётся с `owner_id`; `owner`-строка заполняется автоматически из ФИО.
- [ ] Менеджер через `/sales/board` видит только свои сделки; РОП/Админ — все.
- [ ] `reassign` меняет владельца и фиксируется событием.
- [ ] Список менеджеров отдаётся из `hr.employee`.

## SALES-43 — История стадий + висяки (по сделке)

### Проблема
Drag&drop пишет только текущий `stage` ([update_deal](modules/sales/routes.py#L348)); истории нет.
Нельзя посчитать время в стадии, цикл сделки, «висяки». У `Deal` **нет `created_at`** — без него
не вычислить длину цикла.

### Модель данных
- **`Deal.created_at: datetime`** (server_default now) — обязательное дополнение (нужно и для SALES-44 и расчёта цикла сделки).
- **`Deal.stage_changed_at: datetime`** (server_default now) — денормализация «когда вошёл в текущую стадию» (дешёвый расчёт «дней в стадии» без чтения истории).
- **Новая таблица `sales.deal_stage_event`:**

| Поле | Тип | Прим. |
|------|-----|-------|
| id | int PK | |
| deal_id | int FK → sales.deal.id | |
| from_stage | str(32) \| null | null для первого события (создание) |
| to_stage | str(32) | |
| changed_by | str(128) | username/ФИО инициатора |
| changed_at | datetime | server_default now |

### Логика записи
- Писать событие в истории **в каждой точке смены стадии**: `create_deal`, `convert_lead`, `update_deal` (когда `stage` в payload реально меняется), `win`/`lose` (SALES-40). При записи обновлять `stage_changed_at = now`.
- Вынести в хелпер `set_stage(session, deal, to_stage, by)` — единая точка, чтобы все пути писали историю одинаково.

### API
- `GET /sales/deals/{id}/history` → хронология смен стадий конкретной сделки.
- `GET /sales/deals?stuck_days=N` → сделки без смены стадии дольше N дней (**«висяки»**, `now - stage_changed_at > N`), исключая `won/lost` — для подсветки на доске сделок.
- (агрегатная аналитика воронки — velocity по стадиям, средний цикл отдела — это **вкладка РОПа**, вне scope; вся история уже лежит в `deal_stage_event`.)

### UI
- Карточка/доска: бейдж «N дн. в стадии»; подсветка «висяков» (оранжевая рамка при `> порога`).
- Фильтр на доске «Только висяки».
- На экране сделки — таймлайн стадий.

### Критерии приёмки
- [ ] Любая смена стадии (вкл. drag&drop, win/lose, конвертацию) пишет строку в `deal_stage_event` и обновляет `stage_changed_at`.
- [ ] `GET /sales/deals?stuck_days=7` отдаёт корректный список.
- [ ] Бейдж «N дн. в стадии» на карточке считается из `stage_changed_at`.

## SALES-44 — Вероятность + взвешенная сумма (поля сделки)

### Проблема
`amount` — единственное денежное поле. Нет вероятности и ожидаемой даты закрытия → нельзя
ответить «сколько закроем в этом месяце».

### Модель данных
**Изменения `Deal`:**
- `probability: int | null` (0..100) — вероятность; если не задана, берётся дефолт по стадии.
- `expected_close_date: date | null` — ожидаемая дата закрытия (отдельно от `deal_date`).

**Дефолты вероятности по стадии** (константа в коде, переопределяется полем):

| stage | probability |
|-------|-------------|
| new | 10 |
| qual | 30 |
| prop | 50 |
| appr | 75 |
| won | 100 |
| lost | 0 |

**Взвешенная сумма** = `amount * probability / 100`.

### API
- В `PATCH /sales/deals/{id}` — принимать `probability`, `expected_close_date`.
- В `board`/`DealRead`/детали сделки отдавать `probability`, `expected_close_date`, `weighted` (вычисляемое `amount × probability / 100`).
- (агрегатный прогноз по периоду/менеджерам — **вкладка РОПа в отдельном окне**, вне scope; считается из этих полей сделки.)

### UI
- Карточка: маленький бейдж вероятности и ожидаемой даты закрытия.
- Колонки канбана уже показывают `count·sum` — добавить второй ряд «взвешенно: X» (агрегат по колонке-стадии, в рамках самой доски сделок).

### Критерии приёмки
- [ ] `probability` дефолтится по стадии, переопределяется вручную.
- [ ] `weighted` (`amount × probability / 100`) отдаётся в деталях сделки и на доске.
- [ ] Перевод сделки между стадиями меняет дефолтную вероятность (если не переопределена).

## SALES-46 — Сопутствующие улучшения (мелкие, но болезненные)

Небольшие задачи, каждую можно делать независимо.

1. **`Deal.created_at`** (если не сделан в SALES-43) — нужен для цикла и когорт. Бэкфилл: `created_at = min(deal_date, first stage_event)` или дата миграции.
2. **Speed-to-lead.** В `Lead` добавить `first_response_at: datetime | null` — проставляется при первом действии (qualify/route/первое сообщение). Отчёт `GET /sales/leads?no_response_minutes=N` (лиды без ответа дольше N). Метрика «среднее время до первого ответа». Сильнее всего влияет на конверсию.
3. **Сумма сделки из позиций.** Сейчас `amount` ручной и расходится с `DealItem × цена`. Ввести расчёт `amount` из позиций (`Σ qty × last_price`) с флагом «ручная сумма» (если РОП/менеджер зафиксировал вручную — не перетирать). Заодно — задел под **маржу/себестоимость** (связка с [ТЗ ценообразования](pricing-calculation-todo.md): продажная цена vs landed cost из закупок).
4. **Антидубль контрагента.** Связь сейчас по `name`-строке ([_counterparty_for_deal](modules/sales/routes.py#L129)). ## SALES-47 — Личный план продаж (день/неделя/месяц/год) + согласование с РОПом

### Контекст (что уже есть)
Секция **«План / Факт»** уже живёт в блоке сделок ([deals-workspace.tsx:234](frontend/src/components/kanban/deals-workspace.tsx#L234)) с переключателем **День/Неделя/Месяц/Квартал/Год**. Бэк: `sales.kpi_target` (план) + `sales.activity` (факт), `GET /sales/kpis?period=` ([routes.py:213](modules/sales/routes.py#L213)); цели засеяны в [scripts/seed.py:84](scripts/seed.py#L84) (звонки, холодные, заявки и **сумма отгрузки** — это и есть план продаж в деньгах). **Остаётся в сделках** — это рабочий экран продавца.

### Проблема
1. **План глобальный**: `KpiTarget` без владельца, `kpis` суммирует активности всех менеджеров без фильтра ([routes.py:228](modules/sales/routes.py#L228)) — это «план отдела», а не «мой план».
2. **Периоды грубые**: хранится только дневная цель, а неделя/месяц/квартал/год = дневная × `PERIOD_MULT` (рабочих дней) ([routes.py:76](modules/sales/routes.py#L76)). Продавец не может задать реальный план именно на этот месяц/год.
3. **Нет процесса «поставил себе → согласовал с РОПом»** — цели зашиты сидом. А по процессу отдела: **каждый продавец ставит план себе сам и согласует его с РОПом**.

### Модель данных
**Новая таблица `sales.plan_target`** (личный план по периоду; `KpiTarget` остаётся справочником дефолтов-шаблонов):

| Поле | Тип | Прим. |
|------|-----|-------|
| id | int PK | |
| owner_id | int | мягкая ссылка на `hr.employee` (чей план) |
| metric | str(32) | ключ показателя: `revenue`/`shipment`/`calls`/`cold_calls`/`requests`… |
| period_type | str(8) | `day`/`week`/`month`/`quarter`/`year` |
| period_key | str(10) | конкретный период: `2026-06-11` / `2026-W24` / `2026-06` / `2026-Q2` / `2026` |
| target | Numeric(14,2) | цель, которую продавец поставил себе |
| status | str(16) | `draft` → `pending_approval` → `approved` / `rejected` |
| approved_by | str(128) \| null | кто согласовал (РОП) |
| approved_at | datetime \| null | |

Уникальность: `(owner_id, metric, period_type, period_key)`.

### Согласование с РОПом (через `core.services.approvals` — тот же движок, что договоры)
- Продавец ставит/редактирует цели (`draft`) → **отправляет на согласование** → `approvals.request(route="РОП", entity="plan:{id}")`, статус `pending_approval`.
- РОП **одобряет/отклоняет** → `approvals.decide` → `approved` / `rejected` (+ `approved_by/at`). Эскалация — штатным `_background_loop` ядра.
- Пока не `approved`, план показывается как «на согласовании»; факт считается всегда.

### API (префикс `/sales`)
- `GET /sales/plan?period_type=&period_key=&owner_id=` — личный план/факт за период (`owner_id` по умолчанию — текущий пользователь).
- `POST /sales/plan` — продавец задаёт/обновляет свою цель (`draft`); право `sales.plan.write`.
- `POST /sales/plan/{id}/submit` — отправить план на согласование РОПу (`approvals.request`); emit `sales.plan.submitted`.
- `POST /sales/plan/{id}/decide` — РОП согласует/отклоняет; право `sales.plan.approve`; emit `sales.plan.approved` / `sales.plan.rejected`.
- `GET /sales/kpis?period=&owner_id=` (доработка существующего): **факт — по текущему менеджеру**; **план — approved-цель** за период из `plan_target` (fallback: дефолт `KpiTarget` × `PERIOD_MULT`, если личной нет).
- `POST /sales/activities` — отметка факта атрибутируется текущему менеджеру (`owner_id` из сессии).

### UI (в блоке сделок, место не меняем)
- Секция «План / Факт» остаётся вверху доски; переключатель периода управляет и планом, и фактом; цифры — **личные** для залогиненного продавца.
- Кнопка **«Мой план»** → редактирование целей на выбранный период → **«Отправить РОПу на согласование»**.
- Бейдж статуса: `черновик / на согласовании / согласовано / отклонено`.
- Кнопка «+1» (лог активности) пишет факт текущему продавцу.
- *Сторона РОПа* (массовое согласование, сводка план/факт по всем) — **отдельная вкладка РОПа в другом окне**; здесь только данные и действие `decide` по праву.

### RBAC / события
- Права: `sales.plan.write` (Менеджер + РОП), `sales.plan.approve` (РОП).
- События (→ audit): `sales.plan.submitted`, `sales.plan.approved`, `sales.plan.rejected`.

### Зависимости
SALES-42 (owner→сотрудник, текущий пользователь → `hr.employee`) и `core.services.approvals` (есть). До SALES-42 работает как сейчас (глобально, без персонализации).

### Критерии приёмки
- [ ] Продавец задаёт себе план продаж на **день/неделю/месяц/год** (реальные значения, не дневная×коэффициент).
- [ ] План уходит на согласование РОПу и получает статус `approved`/`rejected`; статус виден в блоке сделок.
- [ ] «План / Факт» в сделках показывает **личные** план/факт продавца за выбранный период.
- [ ] Отметка активности «+1» засчитывается текущему продавцу.

## SALES-49 — Сворачиваемая панель чатов + счётчик непрочитанных

### Контекст / проблема
Панель «Чаты и дела» ([chats-panel.tsx:26](frontend/src/components/chats-panel.tsx#L26)) — всегда раскрытая колонка `w-80` (320px), занимает место постоянно. Счётчика непрочитанных нет: в `ChatOut` ([routes.py `/chats`](modules/sales/routes.py#L516)) нет поля `unread`, а у `Message` нет признака «прочитано».

### Модель данных
- `Message.read_at: datetime | null` — когда входящее сообщение прочитано менеджером (`null` = непрочитано). Альтернатива — `is_read: bool`.

### API
- `ChatOut` → добавить `unread: int` — число входящих (`direction="in"`) сообщений по сделке без `read_at`.
- `GET /sales/chats` → отдаёт `unread` по каждому диалогу (общий счётчик агрегируется на фронте).
- `POST /sales/deals/{id}/messages/read` (или при открытии диалога) — пометить входящие прочитанными (`read_at = now`); опц. emit `sales.message.read`.

### UI (правая панель в блоке сделок)
- **Свёрнуто (по умолчанию):** узкая рейка ~68px — только аватарки контрагентов + красный бейдж количества непрочитанных.
- **По наведению:** панель плавно раскрывается (~300px) **поверх доски** (overlay, канбан не раздвигается) — показывает название, последнее сообщение, счётчик.
- Поведение — чистый CSS `:hover` (без JS); бейдж непрочитанных виден и в свёрнутом состоянии. *(Реализовано в прототипе `mockup_Сделки_2.0.html`.)*

### Критерии приёмки
- [ ] В свёрнутом виде панель показывает только аватарки + счётчик непрочитанных.
- [ ] По наведению раскрывается полностью поверх доски и сворачивается при уходе курсора.
- [ ] `unread` считается из непрочитанных входящих; открытие диалога обнуляет счётчик (`read_at`).

## 8. Порядок внедрения (рекомендация РОПа)

**Фаза 1 — «перестать терять» (S, максимальная отдача):**
SALES-40 (проигрыш+причины) → SALES-43 (история+`created_at`) → SALES-44 (вероятность + взвешенная сумма).
Это дешёвые правки (поля + миграция), но они сразу включают конверсию, висяки и взвешенный pipeline по сделкам.

**Фаза 2 — «личный контроль продавца» (M):**
SALES-42 (owner→сотрудник+видимость) → SALES-41 (задачи+просрочка) → SALES-47 (личный план продаж + согласование с РОПом).
Появляется владелец-сотрудник, видимость «свои/все», операционные задачи на сделке и личный план, который продавец согласует с РОПом.

**Фаза 3 — точечные улучшения:**
SALES-46 (speed-to-lead, сумма из позиций, антидубль, перенос при конвертации) и SALES-49 (сворачиваемая панель чатов + счётчик непрочитанных) — по мере необходимости.

> **Сводная** аналитика по всем менеджерам (план/факт отдела, рейтинги, конверсия отдела) питается полями и событиями из фаз 1–2, но рендерится **отдельной вкладкой РОПа в другом окне** — вне этого ТЗ. Личный план продавца (постановка + согласование) — наоборот, **в блоке сделок** (SALES-47).

## 9. Риски и заметки
- **Submodule:** все правки `sales` — коммит в репозиторий модуля + bump указателя в суперпроекте; CI/клон — с `--recurse-submodules`.
- **Кросс-схемные ссылки** держим мягкими (`*_id` без FK) — иначе ломаем dev-режим `schema_translate_map` (SQLite).
- **Согласованность win:** установка `won` идёт из двух мест (ручное закрытие и `logistics.shipment.delivered`) — обязательно через единый хелпер, иначе `closed_date`/событие разъедутся.
- **Auth — заглушка:** правило видимости «свои/все» нужно протестировать на dev-логине (вход под сотрудником, роль из сессии) — это уже частично есть (см. недавний dev-логин), но маппинг `username → employee` надо добавить.
- **Дефолты вероятности** — согласовать проценты с реальной статистикой воронки после накопления данных (первый месяц — экспертные, дальше калибровать по факту).
