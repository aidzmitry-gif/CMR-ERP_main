# Безопасность — стратегия и модель угроз

> **Статус:** черновик v4, 2026-06-15. 3 раунда deep-research + точечный WebFetch офиц. карточек
> моделей. Закрыто: AuthN/AuthZ-паттерны, Cerbos+PyCasbin, LiteLLM-маршрутизация, retention
> провайдеров, локальные модели по железу, supply-chain `.claude`. Остаток (§6) — инженерный
> выбор периметра/IdP/сканера при внедрении. Владелец: команда платформы.
> **Зачем этот файл:** до сих пор безопасность была устно отложена в «часть 5» без срока
> и не значилась в `coordination/STATUS.md`. Этот документ делает её явной: фиксирует
> текущее состояние, модель угроз и поэтапный план. Обновлять при закрытии каждой задачи.

## TL;DR (если читать одну строку)

Реальной аутентификации и авторизации в бэкенде **нет**. Личность и роли берутся из
подделываемых HTTP-заголовков `X-User` / `X-User-Roles`, при отсутствии заголовка система
выдаёт роль **«Админ»**. Прод доступен публично через `belakb.by` (выделенный статический
IP, проброшенный порт). Единственная реальная защита прода сейчас — внешний Basic-Auth на
Caddy/Cloudflare. Зрелость процессов безопасности — **1 из 5**.

Это нормально для стадии прототипа, но **публичная экспозиция превращает дыры из
теоретических в эксплуатируемые**. Поэтому план начинается с «затычек» (дни), а не с
полноценного Keycloak (недели).

## 1. Контекст и охват

- **Что защищаем:** коммерческие данные ERP — контрагенты, сделки, цены, landed cost,
  переписка с клиентами, телефония (записи звонков), реквизиты, ЗП/payroll, платежи.
- **Деплой:** `/opt/cmr-erp` на сервере (Ubuntu/CasaOS, Tailscale `100.70.224.109`),
  docker compose. Прод опубликован под доменом `belakb.by` на выделенном статическом IP.
- **Стадия:** прототип, ~42–45% готовности (`coordination/STATUS.md`). Сейчас — одна
  организация (внутренняя система компании). **Позже — SaaS / мультитенант для всех
  компаний** → решения по изоляции данных закладываем уже сейчас, чтобы не переписывать.

### Профиль доверия (как есть)

| Граница | Сейчас | Должно быть |
|---|---|---|
| Интернет → прод | Basic-Auth (внешний, Caddy/CF) | OIDC-сессия + TLS + WAF-минимум |
| Внутри Tailscale → API | ничего (порт 8000 голый) | проверенный JWT на каждом запросе |
| Пользователь → данные | всё видят всё | RBAC + ownership + (позже) tenant |
| Сервис → внешние API (1С/Bitrix/Google/Asterisk) | env-секреты, без vault | секрет-менеджер + ротация |

## 2. Модель угроз (кратко, STRIDE-облегчённо)

| Угроза | Сценарий | Текущая защита | Риск |
|---|---|---|---|
| **Spoofing личности** | `curl -H 'X-User-Roles: Админ'` → суперюзер; без заголовка → тоже Админ | нет (только внешний Basic-Auth) | **Критич.** |
| **Tampering данных** | прямой `POST /system/mdm/merge`, правка справочников, чужие сделки по `id` (IDOR) | нет | **Критич.** |
| **Repudiation** | действие без `actor` в аудит-логе; 401/403 не логируются | частично (outbox→AuditLog) | Высокий |
| **Information disclosure** | чтение всех данных без авторизации; `.env` запечён в Docker-образ | нет | **Критич.** |
| **Elevation of privilege** | mass-assignment `stage`/`owner` в теле запроса; роль из cookie без подписи | нет | Высокий |
| **DoS / abuse** | открытый Telegram-webhook без secret-token → подделка `/approve` | нет | Средний |
| **Prompt injection** | клиентский текст → LLM-агент с сессией БД и event bus (когда AI включат) | mock-режим | Средний (латент.) |

**Самое опасное допущение:** что Basic-Auth на Caddy/Cloudflare закрывает весь трафик.
Если фронт ходит к API в обход Basic-Auth, или порт 8000 проброшен отдельно — прод открыт
**прямо сейчас**. Это задача P0-0 (проверить руками).

## 3. Поэтапный план

### P0 — Затычки (дни). Цель: прод перестаёт быть открытым

Дёшево, без большой переделки. Делается в текущем спринте.

- [ ] **P0-0. Проверить фактическую экспозицию прода.** Убедиться, что Basic-Auth
      (Caddy/Cloudflare) закрывает **и фронт, и API**, а порты 8000/8080/5432/6379 **не
      проброшены** наружу мимо прокси (только localhost/Tailscale). Если API доступен в
      обход — это активный инцидент. _(проверка на сервере, без правок кода)_
- [x] **P0-1. Убрать дефолт-Админ.** ✅ 2026-06-16. `core/services/auth.py` и
      `core/runtime/access.py`: без заголовка → бесправный **«Гость»** (не «Админ»). «Гость»
      нет в матрице/супер-ролях → 403 на защищённых модулях, публичное/системное доступно
      (фронт жив до Keycloak). `has_permission` выровнен с матрицей: супер-роли
      (Админ/director/commercial) — суперюзеры и для прав. Тесты: 420 зелёных.
      _Полноценный 401 на проверенном токене — в P1 (Keycloak)._
- [x] **P0-2. Закрыть `/system/*`.** ✅ 2026-06-16. Не трогая `OPEN_PREFIXES` (он по
      префиксу, не различает методы), навесил `Depends(require_permission("system.write"))`
      на 6 мутирующих ручек: `POST /system/mdm/merge|unmerge` + `POST/PATCH/DELETE
      /system/refs/*` (create/update/archive/add_version). Право `system.write` есть только у
      супер-ролей → Гость/обычная роль = 403, GET-мета (`/system/access|modules|users|
      references|audit|events`) остаётся открытым (фронт читает без роли). Тест защиты
      добавлен; 421 тест зелёный. ⚠️ Следствие: экран справочников/merge во фронте теперь
      работает только под супер-ролью (Админ/director/commercial) — правка master-данных
      стала привилегированной, как и должно быть.
- [x] **P0-3. `.dockerignore`.** ✅ 2026-06-16. Создан: исключает `.env`, `*.db`, `.git`,
      `data/`, ключи, `.claude/`, тесты, `frontend/node_modules`. `Dockerfile` `COPY . .`
      больше не запекает секреты в слои образа.
- [ ] **P0-3.5. SOPS + age для секретов.** Зашифровать секреты в git через **SOPS**
      (шифрует значения внутри YAML/JSON/ENV, ключи — plaintext) с ключом **age**. Не нужен
      always-on vault-сервер — ровно под маленькую команду. Дешифровка → инъекция в runtime,
      а не plain `.env` в образе. _(подтверждено первичным источником getsops.io)_
- [ ] **P0-4. Ротация засвеченных секретов.** Telegram bot token (`.env`, живой), при
      сомнении — пароль Postgres `aios` и Keycloak `admin`. Прод **не должен** жить на
      dev-дефолтах `aios/aios` / `admin/admin` из `docker-compose.yml`.
- [x] **P0-5. Прод-дефолты.** ✅ 2026-06-16. `config/settings.py`: `debug=False`,
      `environment="prod"` по умолчанию; `model_validator` падает на старте, если прод-режим
      несёт dev-креды `aios:aios`. ⚠️ Локальная разработка/тесты теперь требуют явного
      `AIOS_ENVIRONMENT=dev` (выставлено в `tests/conftest.py`).
- [ ] **P0-6. Telegram webhook secret-token.** Передать `secret_token` (1–256 симв.) в
      `setWebhook`; Telegram добавляет заголовок `X-Telegram-Bot-Api-Secret-Token` в **каждый**
      запрос. Сервер: constant-compare заголовка с ожидаемым → 401 при несовпадении. Иначе
      любой может подделать `/approve <id>`. _(подтверждено офиц. Telegram Bot API)_
- [ ] **P0-7. Bind на localhost.** uvicorn `--host 127.0.0.1`, наружу — только через
      TLS-прокси; ограничить host-порты (5432/6379/8000/8080) на localhost/Tailscale.

**Definition of done P0:** анонимный запрос к любому не-публичному роуту получает 401;
`/system` мутации требуют авторизации; образ не содержит `.env`; прод на уникальных
секретах; порты не торчат в интернет голыми.

### P1 — Настоящий AuthN/AuthZ (недели). Это и есть «часть 5»

- [ ] **P1-1. Keycloak OIDC/JWT.** Заменить header-trust на проверку подписи токена
      (Keycloak уже в стеке, код к нему не подключён). Валидировать JWT **локально** через
      кэш JWKS (`PyJWKClient`, TTL ~1ч) — не дёргать introspection на каждый запрос.
      Библиотека — **PyJWT** (не `python-jose`: не поддерживается, FastAPI ушёл с него в
      2024). **Обязательно проверять `iss` и `aud`** — без проверки issuer токен из другого
      realm/OIDC молча принимается и ломает tenant-изоляцию (RFC 8725). Короткий TTL +
      refresh-ротация, т.к. локальная валидация не видит отзыв токена до истечения.
      _Keycloak оставить (уже в стеке) — допилить, не мигрировать. Кандидат Zitadel ослаб:
      подтверждено, что с **v3.0 (март-2025) он перешёл на AGPL-3.0** — copyleft/network-use
      обязательства, **аргумент против** для будущего SaaS. Полное сравнение IdP (Authentik/
      Ory/Logto) исследованием не закрыто — см. §6; решать прямым сравнением доков при нужде._
- [ ] **P1-2. RBAC/ABAC реально на роутах.** Повесить проверку прав на роутеры/ручки всех
      модулей. Сейчас проверка стоит на 3–4 ручках из десятков; `declare_permissions` — пока
      только метаданные. Нужны **тонкие ABAC-правила** (доступ по сумме/региону/статусу/
      владельцу/отделу/времени). Рекомендованный движок — **Cerbos** (рек. №1, подтверждено
      первичными источниками): Apache-2.0, self-host, отдельный stateless-PDP-контейнер
      (политики отделены от кода), настоящий ABAC через CEL-условия, есть **офиц. пример
      FastAPI + async SQLAlchemy**. Цена — один лишний stateless-контейнер в docker compose.
      Встраиваемый fallback (если PDP-контейнер нежелателен) — **PyCasbin** (Apache-2.0,
      in-process, ABAC через атрибуты, async + SQLAlchemy-адаптер). ⚠️ Но **PyCasbin НЕ
      заменяет Cerbos** для row-level фильтрации: ни одна in-process Python-библиотека не
      умеет SQL-pushdown (`PlanResources`). Если фильтрация в SQL — жёсткое требование (а для
      IDOR это так), Cerbos остаётся основным PDP, PyCasbin — только `check()`-fallback.
      Oso-OSS (deprecated, именно из-за слабого data-filtering) и vakt (мёртв с 2023) —
      исключены. _(подтверждено первичными источниками, 3-0)_
- [ ] **P1-3. Ownership-скоупинг (BOLA/IDOR — OWASP API #1).** `owner` — из залогиненного
      субъекта, не из тела/query. Проверка доступа к объекту — в **каждой** функции, которая
      читает запись по client-supplied ID (path/query/header/body). Наивного
      `session_user == id_param` **недостаточно** — нужен механизм по политике/иерархии.
      Механизм row-level фильтрации: Cerbos **`PlanResources` API + адаптер `cerbos-sqlalchemy`**
      превращает ABAC-условие в `WHERE`-клаузу SQLAlchemy → «видит сделки только своего региона
      и до суммы X» становится фильтром на уровне БД, не ручной проверкой в каждой ручке.
      ⚠️ AST→SQL делает адаптер-библиотека (отслеживает версии ORM), не ядро PDP.
- [ ] **P1-4. Анти-mass-assignment.** Разделить write-схемы: серверные поля
      (`stage`/`status`/`owner`/audit) ставятся в коде, не из тела. Начать с `DealCreate`
      (`modules/sales/schemas.py:9`).
- [ ] **P1-5. CORS + TrustedHost.** Явный allowlist origin'ов (никогда `*` с credentials),
      `TrustedHostMiddleware` с прод-доменом.
- [ ] **P1-6. Аудит для безопасности.** `actor` инжектится автоматически из субъекта;
      логировать 401/403 и попытки эскалации; добавить IP. (before/after — по возможности.)
- [ ] **P1-7. Security в CI.** Минимальный эффективный набор под маленькую команду:
      - **OSV-Scanner** (Google, Apache-2.0) — один заменяет pip-audit + npm audit, покрывает
        и Python, и JS; офиц. reusable Action валит PR на **новых** уязвимостях, SARIF в
        GitHub Security. _(подтверждено первичным источником)_
      - **gitleaks** — secret-scan. **Semgrep/Bandit** — SAST. _(инженерное суждение,
        отдельно не верифицировано)_
      - Dependabot/Renovate для апдейтов; закрепить версии (Python — lock-файл).
      - **Сканировать `.claude/` и `.cursor/` config-файлы** как новый supply-chain-вектор —
        см. раздел «AI-разработка» ниже.

### P2 — Мультитенант и комплаенс (перед выходом «для всех компаний»)

- [ ] **P2-1. Tenant-изоляция (Postgres RLS).** `tenant_id` в shared kernel + сквозной
      скоупинг. Рекомендуется **Postgres Row-Level Security**: tenant-контекст пробрасывается
      per-request установкой session-переменной, RLS-политика читает её через
      `current_setting()`. ⚠️ Использовать **`SET LOCAL` / транзакционный scope** (не
      session-scope), иначе tenant-контекст течёт между pooled-соединениями (PgBouncer).
      **Заложить модель сейчас**, даже при одной организации — чтобы не переписывать.
- [ ] **P2-2. Шифрование чувствительного** (реквизиты, записи звонков) at-rest; TLS
      end-to-end; secret-менеджер вместо plain env, с ротацией (см. P0-3.5 — SOPS).
- [ ] **P2-3. Tamper-resistance аудита** (append-only на уровне БД / hash-chain),
      ретеншн-политика, экспорт под комплаенс.
- [ ] **P2-4. MFA** (через Keycloak), парольные политики, управление сессиями.
- [ ] **P2-5. Prompt-injection защита** перед включением AI-агентов: недоверенный ввод —

      отправкой, логирование промптов.

## 3.5. Безопасная AI-разработка (агенты редактируют проект)

Отдельная threat-модель: проект быстро редактируется AI-агентами (Claude Code и др.) на
гибриде «локальные модели + облако». Источник — deep-research, факты проверены состязательно
(3-0), опора на офиц. документацию Anthropic, OWASP, Google. **Главный принцип:** изоляция и
приватность — **две разные стены**, одна не заменяет другую.

### Две независимые задачи

1. **Изоляция выполнения** (чтобы агент не сломал/не слил проект разрушительной командой).
2. **Маршрутизация по чувствительности** (чтобы код и данные клиентов не уехали в облако).

> ⚠️ **Ключевой факт (Anthropic docs, 3-0):** изоляция/sandbox **НЕ меняет того, что
> отправляется в модель** — промпты и читаемые агентом файлы уходят в облачный API с
> песочницей или без. Сетевой allowlist sandbox всегда включает endpoint модели. Значит
> «всё чувствительное — только локально» песочницей **не решается** — это задача №2.

### AID-1. Маршрутизация по чувствительности (LiteLLM) — задача №2

LiteLLM = единственная точка выхода к моделям. **Proxy-паттерн** (Anthropic рекомендует
прямо): прокси вне периметра агента сам подставляет ключ — агент ключ **никогда не видит**,
при prompt-injection нельзя вытащить ключ или слить на чужой хост (egress-allowlist).

Гарантия «код + данные клиентов → только локально» строится **тремя слоями** (все
подтверждены офиц. LiteLLM docs, 3-0) — структурно, не на доверии:

1. **Per-key/per-team `models` allowlist — ЖЁСТКАЯ гарантия.** Виртуальный ключ с
   `"models": ["local-qwen","ollama-..."]` **физически отклоняется** при вызове любой другой
   модели → ключ для данных клиентов **структурно не способен** дойти до облака. ⚠️ Footgun:
   пустой `[]` / отсутствие параметра = НЕТ ограничений (разрешено всё) — список заполнять явно.
2. **Tag-based routing — выбор бэкенда.** `router_settings.enable_tag_filtering: True`; один
   `model_name` маппится на локальный бэкенд (тег `sensitive`) и облачный (`anonymized`).
   ⚠️ team-tag matching — Enterprise; но allowlist (п.1) в open-source и его **достаточно**.
   ⚠️ tag_regex по User-Agent — спуфится, НЕ использовать для контроля доступа.
3. **Presidio PII-guardrail (`mode: pre_call`) — defense-in-depth.** Маскирует/блокирует PII
   по типам (`CREDIT_CARD: MASK`, `EMAIL_ADDRESS: BLOCK`) **до** облачного egress. ⚠️ Сам
   Microsoft: автодетект даёт ложные пропуски — **не единственный** контроль, только поверх п.1.

**Дизайн:** ключ для данных клиентов → local-only allowlist (структурно) + tag routing
(выбор) + Presidio (подстраховка). Provider-независимо.

**Облачный провайдер** (для обезличенного слоя) — все дают no-train + zero/low-retention на
**платном** tier (подтверждено офиц. доками, 3-0):

| Провайдер | Обучение | Abuse-логи | ZDR |
|---|---|---|---|
| **Anthropic** | нет без разрешения | 7 дней (дефолт) | контрактный (Messages/TokenCounting) |
| **OpenAI API** | нет с 2023 (opt-in) | 30 дней | контрактный, по апруву |
| **Gemini (paid)** | нет на платном ⚠️ **free/AI Studio — обучают** | ~55 дней | per-project, по апруву |
| **OpenRouter** | зависит от провайдера за ним | у каждого своё | **только** при `zdr=true` / `data_collection=deny` |

Рекомендация: чистейшие контрактные опции — **Anthropic / OpenAI ZDR / Gemini paid-ZDR**
(один контрагент). **OpenRouter — только с явными privacy-флагами на каждом запросе**, на
дефолты не полагаться. ⚠️ Gemini free-tier обучают — для обезличенного слоя обязателен paid.
⚠️ Харденить/обновлять LiteLLM (была SQLi CVE-2026-42208).

### AID-2. Изоляция агента — задача №1

- Claude Code даёт OS-изоляцию из коробки: sandboxed Bash (Seatbelt на macOS, bubblewrap на
  Linux) — запись только в рабочую директорию, prompt на новый сетевой домен, **без Docker**.
  `@anthropic-ai/sandbox-runtime` оборачивает весь процесс (tools, hooks, MCP), deny-by-default.
- Для команды 2–5 чел Anthropic рекомендует **sandbox-runtime или Docker**, не gVisor/VM
  (те — для мультитенанта/недоверенного контента; избыточны здесь).
- Permission-allowlist — это **«ворота, а не песочница»**: не понимает опасность по цели
  команды. Allowlist **+** изоляция вместе. Под `--dangerously-skip-permissions` — только
  внутри контейнера/sandbox-runtime, иначе единственная граница снята.
- ⚠️ `sandbox-runtime` — beta, формат конфига может меняться.

### AID-3. Supply-chain через config-файлы агентов (новый класс угроз)

`.claude/` коммитится в этот репозиторий → прямой риск. Сканировать `.claude/`/`.cursor/`
в CI как `package.json`:
- **CVE-2025-59536** — вредоносный hook в `.claude/settings.json` → RCE **до** диалога
  «доверяете папке?». Открытие чужого репо запускает чужие команды. Фикс — Claude Code
  **≥ v1.0.111**.
- **CVE-2026-21852** — `.claude/settings.json` переопределяет `ANTHROPIC_BASE_URL` → трафик
  на прокси атакующего → **кража API-ключа** из заголовка. Фикс — **≥ v2.0.65**.
- Правила: держать клиент обновлённым (≥ v2.0.65), не открывать недоверенные репо без
  изоляции, ревью изменений в `.claude/`/`.cursor/` наравне с кодом.
- **CI/pre-commit гейт** должен флагать ровно 4 паттерна (это «allowlist» для сканера):
  (1) `hooks` в `.claude/settings.json` (особенно `SessionStart`+`startup` matcher —
  авто-exec до диалога доверия); (2) `enableAllProjectMcpServers: true` или
  `enabledMcpjsonServers` (авто-апрув `.mcp.json` до доверия); (3) `ANTHROPIC_BASE_URL`
  override; (4) прочие env-override, перенаправляющие ключ/Authorization.
  ⚠️ Зрелого готового сканера под `.claude` исследование **не нашло** — defensible путь —
  свой semgrep-rule / pre-commit под эти 4 паттерна. _(модель угроз и паттерны подтверждены
  Check Point + публичный PoC, 3-0)_

### AID-4. Локальные модели (гибрид) — первичные данные, июнь 2026

Все SWE-bench Verified и параметры — **из официальных карточек моделей** (HuggingFace/блоги
вендоров), не из вторичных блогов. Оценки памяти, где помечены _(оценка)_ — выведены из
параметров/квантизации, проверить на момент внедрения.

| Модель | SWE-bench Verified | Параметры | Влезает |
|---|---|---|---|
| **Devstral Small 2 (24B)** | **68.0%** | 24B dense, FP8/BF16, 256k | **24GB GPU / Mac 32GB** (офиц.) |
| **Qwen3-Coder-30B-A3B** | н/д на карточке¹ | 30.5B MoE / 3.3B активных, 256k | ~24-32GB в 4-bit _(оценка)_; OOM на 256k-контексте — резать до 32k |
| **GLM-4.6** | н/д на карточке² | 357B MoE, MIT, 200k | **4-bit MLX = 199 GB → НЕ влезает в 192GB Mac Studio** (офиц. размер) |
| **Kimi K2.6** | **80.2%** | **1T** MoE / 32B активных | block-fp8 ≫ 192GB → **локально не для вашего железа** |

¹ Qwen говорит «SoTA среди open на SWE-bench без test-time scaling», но число на карточке не
указано. ² GLM-4.6 карточка даёт SWE-Bench **Pro** 9.67, не Verified.

**Распределение ролей по железу (рекомендация):**
- **Сервер 24GB GPU** и **ноут 128GB** — рабочая лошадка агентного кодинга: **Devstral Small 2
  (24B, FP8)** — единственная с офиц. подтверждением «влезает в 24GB / Mac 32GB» И сильным
  SWE-bench 68%. Это дефолт для редактирования вашего стека локально.
- **Mac Studio 192GB** — для более крупных, но НЕ флагманских MoE: целятся модели, чей 4-bit
  ≲ ~140-150GB (запас на контекст). **GLM-4.6 4-bit (199GB) и Kimi K2 (1T) НЕ влезают** —
  это и есть тот случай, где блог-обещания «флагман на Mac Studio» ложны. Реально на 192GB
  идут модели класса ~100-235B в 4-bit (проверять размер квантизации перед загрузкой).
- **Облако (Anthropic)** — для задач, где локальные модели не тянут, **только на обезличенном
  контексте** (см. AID-1: ключ для данных клиентов в облако не ходит структурно).

⚠️ Поле движется неделями. Перед внедрением: брать SWE-bench с офиц. карточки, **размер
конкретной квантизации проверять в GB** (как GLM-4.6: «4-bit» ≠ «влезет»).

## 4. Принципы (чтобы не плодить дыры дальше)

1. **Fail closed.** Нет валидной личности → 401, не «Админ по умолчанию».
2. **Никогда не доверять клиенту** в вопросах привилегий: роль/owner/tenant — с сервера.
3. **Авторизация на бэкенде, а не в UI.** `access-admin` сейчас — мокап на demo-данных;
   он не охраняет ничего и создаёт ложное ощущение контроля. Пока бэк-проверок нет — это
   только прототип экрана.
4. **Секреты — из окружения/vault, не из репозитория и не из образа.**
5. **Tenant-готовность с первого дня** даже при одной организации.
