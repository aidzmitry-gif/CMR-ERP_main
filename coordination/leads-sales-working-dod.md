# DoD — «Лиды и Продажи рабочие» (цель Cursor · критерии верификации координатора)

> **Владение:** Cursor пишет `modules/leads` + `modules/sales` + их фронт. Координатор (эта сессия) —
> **верифицирует** (адверсариально по швам), держит карту/миграции/хотспоты, кормит активами. В код
> leads/sales координатор НЕ пишет (два писателя = дрейф HEAD). Дата: 2026-07-17.

## Что значит «рабочие» — end-to-end денежный путь
Под РЕАЛЬНЫМ входом (`AIOS_AUTH_MODE=oidc`) и на сид/реальных данных, без ошибок в консоли/логах.

### Лиды
- **L1 Приём.** Заявка (web/email/телефония webhook) создаёт лид → виден на `/crm/leads`.
- **L2 Скоринг+SLA.** Авто-скоринг, срок первого ответа, целевой/нецелевой.
- **L3 Разбор+маршрутизация.** Конвейер «разобрать целевых» → передача закрывающему.
- **L4 Конвертация.** Лид → сделка (+ КП/счёт из лида); связь сделка↔лид не теряется.
- **L5 План лидоруба** (если в скоупе Cursor). Экран планирования (обратная воронка) собирается → РОПу.
- **L6 RBAC.** Роли `sales_head`/`sales`/`sales_cli` видят своё; гость → 403.

### Продажи
- **S1 Доска.** `/crm/deals` грузится, сделки по стадиям, фокус-очередь, план/факт.
- **S2 Движение.** Смена стадии, next-step, dnd, «Выиграна» через `POST /win`.
- **S3 Документы.** Счёт+договор, печать/факсимиле, пакет клиенту, запись в 1С (или honest 503).
- **S4 Маржа.** Реальная (`price_cost` из 1С + метка «из 1С»/«демо»), НЕ `DEMO_MARGIN_RATE`.
- **S5 Планирование.** `/crm/deals/planning` — конструктор + согласование РОП.
- **S6 Оплата→офис.** `finance.payment.received` двигает офис-документ в «Оплачено» (шов по `deal_id`).

## Смоук (проверяемо; Bearer реального юзера)
- Каждый экран leads/sales: **200**, без ошибок в консоли, без вечной загрузки (регресс `be2c8ce`).
- Роуты под Bearer: `GET /leads`, `/sales/board`, `/sales/journal`, `/office/board` → **200**;
  без валидного Bearer (только `X-User-Roles`) → **401/403** (header-trust выключен).
- Сквозной сценарий: лид → qualify → route → convert → сделка на доске → счёт → (оплата) → офис «Оплачено».
- Гейты: `pytest` зелёный · `ruff` · **один** alembic head · фронт `tsc`+`vitest`.

## Швы, где координатор ловит баги (адверсариальный фокус)
1. **leads→sales (конвертация):** `deal_id`/counterparty-связь; не потерять КП при конвертации.
2. **sales→finance→office:** цепочка счёт→оплата→«Оплачено». Шов по `deal_id` уже чинён
   (`office_doc.deal_id`, мигр. 0105) — **проверить, что линия Cursor его не откатила**.
3. **OIDC×SSR:** SSR-фетчи несут Bearer (`0a8f7d8`) — экраны leads/sales под oidc НЕ должны 401.
4. **RBAC-слаги:** `Role()` под UI-слаги (`config/access.py`), иначе право только у супер-роли.
5. **Миграции:** голова **0105**; новая миграция (план лидов и пр.) — согласовать номер, не дубль-head.
6. **Деньги:** `Decimal(str())`/BYN; `price_cost` честный (`None`, не `0`).

## Активы от координатора (готовое — не переоткрывать)
- **Обратная воронка планирования лидов:** `modules/leads/planning.py` + 15 unit-тестов (у координатора
  локально, зелёные, ruff чист) — `reverse_funnel` + `capacity_check`. Отдам по слову.
- **Спека планирования лидов:** `leads-planning-plan.md` (9 блоков, цикл согласования) + мокап `leads-planning-preview.html`.
- **Паттерн шва:** `office.deal_id` (мигр. 0105) — как связывать модули по сделке, а не по строке-номеру.
- **RBAC:** роли = UI-слаги (иначе право только супер-роли); sales-роли уже получили `sales.deal.read` (`572f696`).

## Как это работает процессно
- Cursor пушит leads/sales в `main` → координатор `git fetch` + адверсариальное ревью коммита по швам
  выше → вердикт (баг/чисто) оператору. Оператор — мост между координатором и Cursor.
- Голову миграций и хотспоты (`config/settings.py`, `core/services/__init__.py`, `api.ts`) координатор
  держит в `ACTIVE-SESSIONS`; при новой миграции Cursor — сверка номера ДО пуша.
