# Двунаправленный синк справочников с 1С — план (на согласование)

> Статус: **черновик на сверку с владельцем**. Реализация после согласования.
> Память: `onec-bidirectional-erp-truth`. Связано: `spravochniki-mdm-decision`,
> `invoice-1c-reserve-shipment` (склад остаётся за 1С).

## 1. Видение и фазы

> **Подтверждено владельцем 2026-06-16:** «сначала из 1С, потом двусторонний обмен».
> Фаза 1 работает сейчас; модель и UI-каркас закладываем под двусторонний уже сейчас.

- **Фаза 1 (сейчас, операционно):** мастер-данные тянем **только из 1С** (1С → ERP).
  Идемпотентный импорт по УНП уже работает (`reference_import.upsert_counterparty` + alias).
- **Фаза 2 (позже):** **ERP — система-истина** мастер-данных. Контрагенты и номенклатура
  **создаются в ERP** и выгружаются **в 1С** (ERP → 1С) — двусторонний обмен.
- **Сейчас:** закладываем **каркас и поля** под исходящую, без реальной отправки.
  Цель — не переделывать модель и экраны в фазе 2.

### Разделение владения (важно, чтобы не было конфликта истин)
| Домен | Истина | Поток |
|-------|--------|-------|
| Контрагенты, номенклатура (мастер-данные) | **ERP** | создаём в ERP → выгрузка в 1С |
| Остатки/склад, движения, деньги/факт | **1С** | читаем из 1С |

## 2. Что уже заложено (переиспользуем, не плодим)

- `OneCGateway` (core/services/onec.py) — Protocol; уже есть `fetch_counterparties`,
  `fetch_stock`, **`post_document(doc_type, payload)`** → исходящий примитив готов.
- `CounterpartyAlias(counterparty_id, source, external_ref)` — `source` уже включает
  `"erp"` и `"1c"`; фактически это уже «ссылка на запись в 1С» (`external_ref=Ref_Key`).
- Транзакционный outbox + `event_bus.emit` — готовый механизм поставить событие
  «нужно выгрузить в 1С» в той же транзакции, что и создание записи.
- Экран импорта уже подписан «1С — временный входной адаптер, владелец — ERP».

## 3. Модель данных — что добавить (главное решение)

Сейчас нет: **происхождения** и **статуса выгрузки** записи. Две опции:

- **Опция A (точечно):** колонки на `counterparty` и `sku`: `origin` (`erp`/`1c`/`bitrix`,
  default `erp`), `sync_state` (`local`/`pending`/`synced`/`error`), `synced_at`, `sync_error`.
  Просто, но дублируется на каждую сущность; для номенклатуры alias-таблицы вообще нет.
- **Опция B (обобщённо, РЕКОМЕНДУЮ):** одна таблица-реестр синка под все мастер-данные:

  ```
  sync_link(
    id, entity_type ("counterparty"|"sku"),  entity_id,
    system ("1c"),  external_ref (Ref_Key в 1С, NULL пока не выгружено),
    origin ("erp"|"1c"|"bitrix"),
    state ("local"|"pending"|"synced"|"error"),
    direction ("in"|"out"),
    last_synced_at, error_text
  )
  ```
  Одно место для статуса и внешнего id по любой сущности и любой внешней системе
  (1С сегодня, другие завтра). `CounterpartyAlias` остаётся для MDM-провенанса и дедупа
  (Bitrix/merge), а роль «ссылка в 1С + статус» переезжает в `sync_link`.

> Решение A vs B — за владельцем. B дороже на старте (1 миграция + перенос 1С-ref из alias),
> но не упрётся при добавлении номенклатуры и вторых систем. A быстрее, но к фазе 2 разрастётся.

## 4. Блоки UI «на предусмотреть» (каркас сейчас, логика в фазе 2)

1. **Направление синка** — на `/erp/spravochniki/import`: переключатель
   `← Импорт из 1С` (активен) ↔ `→ Выгрузка в 1С` (каркас/заглушка с пометкой «фаза 2»).
2. **Происхождение + статус на записи** — бейдж в каталоге и на карточке контрагента:
   «создано в ERP / из 1С» + «выгружено ✓ / ожидает ⏳ / только локально / ошибка».
   Берётся из `sync_link.origin`/`state`.
3. **«Создать здесь»** — кнопка `+ Создать` контрагента/номенклатуры в ERP.
   ⚠️ Пересматривает недавнее lookup-only-решение каталога: read-only — это фаза 1;
   под фазу 2 нужна форма создания (новый эталон `origin=erp, state=local`).
4. **Журнал/очередь выгрузки** — зеркало журнала импорта: «что и когда ушло в 1С»,
   статусы, ошибки, ручной повтор. Питается событиями `counterparty.sync.queued/sent/failed`.

## 5. Механизм исходящей (фаза 2, проектируем сейчас)

1. Создание/правка эталона в ERP → запись `sync_link(state=pending, direction=out)` +
   `event_bus.emit("counterparty.sync.requested", {...})` в той же транзакции.
2. Фоновый relay (уже есть `_background_loop`) подбирает pending → вызывает
   `OneCGateway.post_document("counterparty", payload)` → получает `Ref_Key` →
   `sync_link.external_ref=Ref_Key, state=synced, last_synced_at`.
3. Идемпотентность: повторная выгрузка ищет существующий `external_ref` → update, не вставку.
   Натуральный ключ для матчинга в 1С — УНП (как и на входе).
4. Ошибка 1С → `state=error, error_text`; видно в журнале, ручной повтор.

## 6. Что делаем «сейчас» vs «в фазе 2»

| Сейчас (предусмотреть) | Фаза 2 (включить) |
|------------------------|-------------------|
| `sync_link` (или колонки) + миграция | реальный `post_document` в 1С |
| бейджи происхождения/статуса (на demo-данных) | фоновая обработка очереди выгрузки |
| переключатель направления (каркас) | конфликт-резолв при двусторонних правках |
| форма «создать здесь» (пишет в ERP, `state=local`) | автонумерация/маппинг полей ERP↔1С |
| журнал выгрузки (пустой каркас) | повтор/алерты по ошибкам |

## 7. Открытые вопросы к владельцу

1. **Модель: A (колонки) или B (`sync_link`-реестр)?** Рекомендую B.
2. **Кто «рождает» контрагента в фазе 2** — каталог справочников, карточка, или CRM-сделка
   (сейчас контрагент часто заводится из сделки)? Где кнопка «Создать»?
3. **Номенклатуру** тоже создаём в ERP и выгружаем, или она пока только из 1С/закупок?
4. **Конфликты:** если запись правят и в ERP, и в 1С между синками — чья берёт?
   (Предлагаю: ERP-истина по мастер-полям, последняя правка по timestamp как tie-break.)
5. **Что именно выгружаем** в фазе 1-наборе полей: УНП, наименование, контакты, реквизиты?
