# Задание Cursor: Лиды и Продажи — рабочие, с дисциплиной выката

> Самодостаточно. Цель — end-to-end рабочие `leads`+`sales` на проде под OIDC. Приоритеты платформы:
> 1) деньги собственнику 2) безопасность 3) функциональность 4) эстетика.

## 🔴 Дисциплина выката — ОБЯЗАТЕЛЬНО (иначе теряем откат, повторяемость и внешнюю проверку)

1. **Пуш в `origin/main` ДО или вместе с деплоем. Git — источник истины: прод обязан = `origin/main`.**
   Не редактируй-и-выкатывай на сервере без пуша — иначе прод дрейфует от origin, следующий
   `git pull`-деплой затрёт серверные правки, а откат становится невоспроизводимым.
2. **Перед каждым деплоем — точка отката:** запиши серверный `git rev-parse HEAD` + `git submodule status`
   + `alembic current`; бэкап `.env`/`docker-compose.override.yml`; при миграции — `pg_dump` БД.
3. **Деплой детерминированный:** `git pull --recurse-submodules && git submodule update --init --recursive
   && docker compose up -d --build` (или `deploy-belakb.sh`). Миграции применяются на старте app.
4. **Один head Alembic.** Новая миграция — следующий свободный номер (текущая голова **0105**), НЕ дубль.
   Проверь `alembic heads` = одна строка ПЕРЕД пушем и на сервере после деплоя.
5. **Не сломай OIDC** (уже работает): `AIOS_ENVIRONMENT=dev`, `AIOS_AUTH_MODE=oidc`; SSR-фетчи и API-прокси
   несут `Authorization: Bearer`. Любой новый экран leads/sales под oidc НЕ должен отдавать 401.
6. **После деплоя — смоук** (self-check эндпоинтов + `printenv` режим + один alembic head) → записать
   в `coordination/ACTIVE-SESSIONS.md` §Деплой-состояние: задеплоенный SHA, режим, head. Прислать координатору.

## Что сделать (критерии готовности)

### Лиды
- **L1 Приём:** заявка (web/email/телефония webhook) создаёт лид → виден на `/crm/leads`.
- **L2 Скоринг+SLA:** авто-скоринг, срок первого ответа, целевой/нецелевой.
- **L3 Разбор+маршрутизация:** конвейер «разобрать целевых» → передача закрывающему.
- **L4 Конвертация:** лид → сделка (+ КП/счёт из лида); связь сделка↔лид не теряется.
- **L5 Планирование лидов** (если берёшь): экран обратной воронки → согласование РОП.
- **L6 RBAC:** роли `sales_head`/`sales`/`sales_cli` видят своё; гость → 403.

### Продажи
- **S1 Доска** `/crm/deals`: грузится, сделки по стадиям, фокус-очередь, план/факт.
- **S2 Движение:** смена стадии, next-step, dnd, «Выиграна» через `POST /win`.
- **S3 Документы:** счёт+договор, печать/факсимиле, пакет клиенту, запись в 1С (или honest 503).
- **S4 Маржа:** реальная (`price_cost` из 1С + метка «из 1С»/«демо»), НЕ `DEMO_MARGIN_RATE`.
- **S5 Планирование** `/crm/deals/planning`: конструктор + согласование РОП.
- **S6 Оплата→офис:** `finance.payment.received` двигает офис-документ в «Оплачено» (шов по `deal_id`).

Приоритет — денежный путь: приём → конвертация → сделка → счёт → **оплата → «Оплачено»** + реальная маржа.

## Швы, которые ты и координатор проверяете (тут per-lane тесты слепы)
1. **leads→sales:** не потерять КП/связь при конвертации лида в сделку.
2. **sales→finance→office:** цепочка счёт→оплата→«Оплачено» — шов `office_doc.deal_id` (0105); не откатить.
3. **OIDC×SSR:** экраны leads/sales под Bearer не должны 401.
4. **RBAC-слаги** (см. активы).
5. **Миграции:** один head, номер после 0105.
6. **Деньги:** `Decimal(str())`/BYN; `price_cost` честный (`None`, не `0`).

## Петля координации
Ты пушишь в `origin/main` → координатор `git fetch` + адверсариальное ревью по швам → вердикт оператору.
После деплоя оператор шлёт координатору смоук. Прод-состояние (SHA/режим/head) — в `ACTIVE-SESSIONS`.
Вопросы/блокеры — строкой оператору; координатор отвечает и держит карту миграций/хотспотов.
