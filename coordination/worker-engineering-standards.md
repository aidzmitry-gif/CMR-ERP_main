# Worker Engineering Standards (обязательно для каждого воркера)

Контракт, по которому работает каждый спавнутый воркер этого проекта (CRM ERP / AI-First OS).
Оркестратор препендит ссылку на этот документ к первому сообщению каждого воркера.
Адаптировано из канона job_ghost_stalker под Windows + FastAPI/SQLAlchemy-стек CRM ERP.

---

## 1. Karpathy 5-step — это ЦИКЛ, а не последовательность

Каждая итерация — пять шагов ПО ПОРЯДКУ:

1. **Think** — назови допущения, путь отката, набросай тест-кейсы. План ДО кода. Подними неясности и tradeoffs.
2. **Test** — сначала тест (TDD). Для аудита — какие команды/запросы выполнишь и какое доказательство ждёшь.
3. **Validate** — прогони тест на реальных данных. Для аудита — докажи гипотезу (код/логи/запрос).
4. **Wire** — минимальное изменение. Без scope creep, без «раз уж я здесь».
5. **Review** — проверь критерии успеха, задокументируй в status-файле. Если ХОТЬ один пункт acceptance-gate КРАСНЫЙ — **ВЕРНИСЬ** к падающему шагу.

**Условие выхода из цикла**: `STATE: COMPLETE` только когда на ОДНОМ чистом прогоне:
- все пункты acceptance-gate ЗЕЛЁНЫЕ;
- `pytest` (или `pytest tests/<твой-скоуп> -x`) возвращает 0;
- импорты резолвятся (`import main` не падает);
- six-layer присутствует в теле коммита;
- роли STR задокументированы (для нетривиальной отладки).

Single-pass РЕДЖЕКТ. Лечи болезнь, а не симптом: если Review показал симптом-патч — вернись к Think с более глубокой причиной.

Каждую итерацию цитируй в status-файле:
```markdown
## Loop iteration 1
- Think: [гипотеза + допущения + путь отката]
- Test: [тесты, число RED]
- Validate: [доказательство из кода/логов/запросов]
- Wire: [файлы, строки]
- Review: [матрица acceptance-gate; N/M GREEN; → LOOP / DONE]
```

## 1.6 Loop Contract (фреймворк Boris Cherny)

Скоуп-файл воркера ДОЛЖЕН содержать блок `LOOP CONTRACT`:

```yaml
## LOOP CONTRACT
scope:
  include:                 # что воркер МОЖЕТ трогать
    - modules/sales/**
    - tests/unit/test_sales_*.py
  exclude:                 # что воркер НЕ ДОЛЖЕН трогать
    - core/**
    - config/**
permissions:
  repo: write-branch       # read-only / write-branch / write-main (ЗАПРЕЩЕНО)
  db: read-only            # read-only / write
  llm: enabled
model: sonnet              # тир: haiku=механика / sonnet=код / opus=архитектура / inherit
mcp: none                  # none (по умолчанию) / serena — семантич. навигация по символам
budget:
  max_iterations: 5
  max_runtime_minutes: 30
  max_files_changed: 10
  max_consecutive_test_failures: 3
stop:                      # обязательные условия остановки
  - same_failure_seen_twice
  - acceptance_gate_red_after_3_iters
  - file_touched_outside_scope
  - test_contradiction_detected
  - product_behavior_ambiguous
  - merge_conflict_requires_orchestrator_decision
report:
  destination: coordination/<your-name>-status.md
```

Когда срабатывает любое stop-условие — СТОП, пиши blocker в status-файл. Не пытайся обойти.

## 2. Принципы Karpathy (жёсткие правила)

См. установленный скилл `karpathy-guidelines`.

| Принцип | Смысл |
|---------|-------|
| **Think Before Coding** | Назови допущения. Неясно — пиши NEEDS-ORCHESTRATOR-ANSWER. Подними tradeoffs. |
| **Simplicity First** | Минимум кода. Без спекулятивных фич/абстракций. 200 строк → если можно 50, перепиши. |
| **Surgical Changes** | Трогай только нужное. Не «улучшай» соседнее. Не переименовывай чужое. Каждая строка диффа = из ТЗ. |
| **Goal-Driven Execution** | Критерии успеха заранее. Доказательство до «готово». Никаких «вроде работает». |

## 3. STR-протокол — обязателен для нетривиальной отладки

Три изолированные роли:
- **Lead** — владеет вопросом, синтезирует, решает.
- **Troubleshooter** — ставит эксперименты, собирает доказательства, отсекает гипотезы.
- **Interrogator** — адвокат дьявола: ищет confirmation bias, контр-гипотезы.

Для правок в 1-3 строки STR избыточен — достаточно Karpathy 5-step.
Для гонок состояний, регрессий производительности, дрейфа схемы — STR ОБЯЗАТЕЛЕН.

```markdown
## STR debugging session
### Lead's hypothesis
### Troubleshooter findings (с доказательствами)
### Interrogator pushback
### Resolution
```

## 4. Six-layer дисциплина (обязательна в теле коммита)

Каждый нетривиальный коммит трассирует шесть слоёв:
```
SYMPTOM:    <наблюдаемое поведение — лог, метрика, репорт>
DISEASE:    <проксимальная причина на слой ниже>
ROOT CAUSE: <архитектурная причина — класс A/B/C/D/E>
EVIDENCE:   <логи, строки БД, grep, file:line>
PATTERN:    <назови паттерн явно>
SOLUTION:   <хирургическое изменение>
UX IMPACT:  <что чувствует пользователь после фикса>
```

Классы багов: **A** — отсутствующая проводка; **B** — хрупкая эвристика; **C** — архитектурный дрейф; **D** — дрейф контракта; **E** — тихий сбой.

---

## 5. Audit-first

Для любого баг-клейма — сначала аудит, потом фикс:
1. Воспроизведи симптом (лог/строка БД/запрос).
2. Протрассируй путь кода от симптома назад.
3. Определи класс бага (A/B/C/D/E).
4. Процитируй EVIDENCE (file:line, timestamp, результат запроса).
5. ТОЛЬКО ПОТОМ предлагай фикс.

Симптом-фиксы запрещены без явного одобрения как stop-gap.

---

## 6. Логирование

Каждый фикс улучшает наблюдаемость. Для класса E: повысь `log.debug` → `log.warning` + структурный лог исключения. Конвенция: `<verb>_<noun> key1=val1 key2=val2`.

## 7. Status-файл воркера

Файл `coordination/<name>-status.md` заканчивается одним из состояний с ТОЧНЫМ баннером (по нему оркестратор грепает):

```
================================================================
STATE: COMPLETE
================================================================
```
(либо `STATE: BLOCKED` / `STATE: NEEDS-ORCHESTRATOR-ANSWER` тем же форматом.)

НЕ пиши `STATE: COMPLETE`, пока не отмечены ВСЕ пункты acceptance-gate — преждевременный COMPLETE = false-COMPLETE, оркестратор откажется интегрировать.

Обязательные секции: State (сверху) · Karpathy 5-step compliance · Six-layer · STR-роли (если нетривиально) · Deliverables (по скоупу, каждый отмечен) · Out-of-scope findings (отдельно).

## 8. Жёсткие ограничения (CRM ERP / Windows)

- **НЕ** `git add -A` / `git add .` — `.env` содержит секреты. Только явный список файлов.
- **НЕ** деструктивные in-place правки (массовые замены вслепую) на исходниках.
- Python только через `.venv\Scripts\python.exe` из корня репозитория.
- Dev-БД: `$env:AIOS_DATABASE_URL = "sqlite+aiosqlite:///./dev.db"; $env:PYTHONPATH = "."`. Источник истины схемы Postgres — миграции Alembic, не autocreate.
- Тесты: `pytest` (БД-тесты на SQLite в памяти, Postgres не нужен). Линт: `ruff check .` (line-length 100, py312).
- **9 модулей — git submodules** (sales, procurement, production, wms, logistics, finance, marketing, service, hr). Правка модуля = коммит в его репозиторий + обновление указателя. Если твой скоуп внутри submodule — отметь это в status.
- Модули общаются только через `core`/события — НЕ лезь во внутренности соседнего модуля.
- Путь проекта содержит пробелы и кириллицу — **всегда заключай пути в кавычки**.
- Прочитай scope-файл ПЕРВЫМ. Не угадывай намерение. Неясно → NEEDS-ORCHESTRATOR-ANSWER.

## 9. Анти-паттерны (реджект сразу)

- «Вроде работает» без доказательства → РЕДЖЕКТ. Покажи тест/grep/данные.
- Спекулятивный рефактор («раз уж я здесь») → РЕДЖЕКТ.
- Симптом-фикс без трассировки корня → РЕДЖЕКТ. Audit-first.
- Тихое исключение (`except Exception: pass`) → РЕДЖЕКТ без явного обоснования.
- Нет тестов для нетривиального фикса → РЕДЖЕКТ. TDD = шаг 2 Karpathy.
- Тело коммита без six-layer → РЕДЖЕКТ.
- `git add -A` → РЕДЖЕКТ.

## 11. Acceptance gate (само-проверка до STATE: COMPLETE)

- [ ] Все 5 шагов Karpathy задокументированы в status-файле
- [ ] Six-layer в теле коммита (для кодовых правок)
- [ ] STR-роли (для нетривиальной отладки)
- [ ] Доказательства с точностью до file:line
- [ ] Класс бага определён (A/B/C/D/E)
- [ ] Out-of-scope находки вынесены отдельно
- [ ] Тесты добавлены (или N/A обосновано)
- [ ] Нет `git add -A`, нет деструктивных операций
- [ ] Все требования scope-файла выполнены

Если хоть один пункт не отмечен → `BLOCKED` или `NEEDS-ORCHESTRATOR-ANSWER`, не COMPLETE.

## 12. Машинный acceptance-гейт (JSON) — обязателен перед COMPLETE

Чеклист §11 — для людей; объективную проверку делает машинный гейт
`coordination/acceptance/<name>.json` (детали: `coordination/acceptance/README.md`).

- Оркестратор/инициализатор сидирует гейт из acceptance-матрицы scope-файла; каждый критерий
  стартует `passes:false`.
- Ты меняешь **только** поле `passes` и прикладываешь `evidence`. **Нельзя** править/удалять
  сами критерии или их `cmd` — «It is unacceptable to remove or edit tests».
- Критерий с `cmd` (ruff/tsc/pytest) проверяется ОБЪЕКТИВНО: гейт сам запускает команду и
  перезаписывает `passes` её результатом — оптимистичный флаг не выживает.
- Критерий `manual` (браузерный E2E и т.п.) засчитывается только при `passes:true` **и**
  непустом `evidence` (скрин Playwright / лог). Браузер гони через MCP, как реальный юзер.
- Перед `STATE: COMPLETE` сам прогони
  `& ".\.venv\Scripts\python.exe" acceptance_gate.py check <name>` — нужен **exit 0 (ЗЕЛЁНЫЙ)**.
  `integrate` повторит проверку и откажет при красном.
