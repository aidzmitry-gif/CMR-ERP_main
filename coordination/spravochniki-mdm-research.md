# Справочники (Master Data / Reference Data) — исследование и решение

> Источник: deep-research (24 источника, 25 проверенных утверждений, 18 подтверждено / 7 опровергнуто)
> + скан shared-kernel проекта + мнение из параллельного чата (registry pattern).
> Дата: 2026-06-14. Стек на момент: PostgreSQL 16 + pgvector (не используется), FastAPI + async SQLAlchemy 2, SQLite для dev.

## TL;DR (вердикт)

1. **«Реестр + доступ, а не второе хранилище» (registry pattern) — верно.** Совпадает с golden record (единый источник истины) и вашим plugin-паттерном.
2. **Опровергнуто:** деление «master data меняется редко / reference data часто» — НЕВЕРНО (верификаторы 0-3). Граница не по частоте.
3. **Для AI: структурный доступ (SQL/tool-calling по golden records), НЕ эмбеддинги.** pgvector — вторичный путь (нечёткий поиск по названиям/дублям), не первоисточник точных значений.
4. **Историчность (цены, курсы, НДС, версии BOM) = SCD Type 2 вручную**, т.к. нативные temporal-таблицы Postgres — это PG18/19, а у нас **PG16**.

## 1. Каталог справочников по доменам

### Общесистемные (reference data) → shared-kernel / public
Единицы измерения (+ коэффициенты пересчёта), валюты + **курсы (историчные)**, страны/регионы/города,
ставки **НДС / налоги (историчные)**, языки, часовые пояса, банки (БИК/SWIFT).

### Master data (крупные операционные) → shared-kernel
- **Контрагенты** (`Counterparty`, есть, УНП) — клиенты+поставщики+перевозчики, единая запись
- **Контакты** (`Contact`, есть)
- **Номенклатура** (`Sku`, есть) + категории/иерархия + характеристики (JSONB) + единицы
- **Сотрудники/пользователи** (`User`, есть; кадровая карточка — в hr)
- **Банковские счета** контрагентов и свои
- **Договоры** (рамочные — как справочник ссылок; позиции — в модулях)

### Модуль-специфичные классификаторы → владеет модуль (своя схема)
| Домен | Справочники |
|---|---|
| sales | стадии воронки, причины отказа, типы сделок, источники лида, прайс-листы |
| procurement | типы поставщиков, условия оплаты (Net 30/60), lead time, сертификации, инкотермс |
| production | BOM/спецификации (версионные), маршруты/операции, нормы (есть), центры обработки |
| wms | склады, зоны, ячейки (иерархия), типы операций, статусы партий |
| finance | план счетов, статьи затрат/доходов, ЦФО, проекты/направления, типы документов |
| hr | должности, оргструктура, типы начислений, причины увольнения |
| logistics | перевозчики, тарифы, типы ТС, маршруты доставки |
| service | типы обращений, SLA, категории неисправностей |
| marketing | каналы, кампании, сегменты, UTM-источники |

**Расширенные атрибуты поставщика** (условия оплаты, lead time, сертификации, parent-child) — в схему `procurement` как обогащение поверх мягкой ссылки на `Counterparty`, НЕ дублируя запись контрагента. (Verdantis 3-0)

## 2. Как хранить (проверенные паттерны)

- **Характеристики номенклатуры: JSONB, не EAV** ✓ (3-0). EAV даёт раздувание (~27 байт оверхеда/строку, дублирование entity-id); JSONB ~10× быстрее, ~3× меньше хранение. Cybertec: «EAV — don't do it!». Типизированные классификаторы — нормализованные таблицы.
- **Историчность: SCD Type 2 вручную** ✓ (3-0). Схема: `surrogate_key(PK) | natural_key | <атрибуты> | start_date | end_date`. Текущая = `end_date IS NULL`. Для прайсов, курсов, ставок НДС, версий BOM. Источник: Kimball Group.
  - ⚠️ Нативные temporal (`PRIMARY KEY (..., valid_at WITHOUT OVERLAPS)`) — PG18 GA(2025)/PG19. У нас PG16. Заложить модель под будущий апгрейд без переписывания. В SQLite-dev temporal нет.
- **Иерархии (категории, ЦФО, ячейки, parent-child): ВОПРОС ОТКРЫТ** ⚠️. Дефолт adjacency-list опровергнут (0-3), альтернатива доказательно не выбрана. Практически (вне верифицированной базы): `ltree` или closure table для read-heavy справочников. Нужен отдельный точечный ресёрч.

## 3. Доступ для AI (ключевой вывод)

Грундить агента на **структурированные верифицируемые данные**, НЕ на параметрическую память LLM ✓.
Оговорка: «RAG+KG значительно лучше baseline» — ОПРОВЕРГНУТО (0-2), есть контр-литература о шуме GraphRAG. **Не переусложнять.**

| Задача AI | Чем решать | Не чем |
|---|---|---|
| Точный lookup (контрагент по УНП, ставка НДС, склад по коду, цена на дату) | Структурный SQL / tools (MCP) по golden records | ❌ не эмбеддинги |
| Нечёткий поиск, дедуп похожих названий | pgvector (семантика по названиям/описаниям) | — |
| Связи между сущностями | денормализованные read-models / materialized views | ❌ не обязателен real-time KG |

Опровергнуто как избыточное: «golden context из 5 слоёв», обязательный real-time KG.
**Registry-контракт справочников = semantic layer для AI** (саморегистрирующиеся метаданные → машинный каталог «что есть и как точно запросить»).

## 4. Раскладка под нашу архитектуру

**Отдельный тяжёлый MDM-модуль НЕ нужен** (избыточен для модульного монолита с 1С как источником). Вместо:

1. **shared-kernel (public)** владеет: reference data (единицы, валюты+курсы, страны, НДС, банки) + master data (Counterparty, Contact, Sku, User, банк.счета) — реальные таблицы.
2. **Модули** владеют классификаторами в своих схемах. Мягкие ссылки по коду.
3. **Вкладка «Справочники» = registry-витрина** поверх (1)+(2). Не хранилище. Новый контракт ядра:

```python
core.register_reference(
    key="sales.reject_reasons",
    title="Причины отказа", department="Продажи",
    owner_schema="sales", endpoint="/sales/refs/reject-reasons",
    columns=[{ "name":..., "type":..., "label_i18n":... }],   # типизированные
    permissions=["sales.refs.view", "sales.refs.edit"],        # через access-admin RBAC
    archivable=True, versioned=False,    # versioned=True → SCD2 effective-dated
    ai_exposed=True,                     # каталог для AI
)
```
Один контракт = UI-вкладка + RBAC + каталог для AI. Системные справочники ядро регистрирует на себя тем же механизмом.

### 1С как система-источник ⚠️ (инженерное решение, не из верифицированных источников)
- Направление: **1С → ERP** для golden record контрагентов (1С + ЕГР по УНП; УНП — сильный natural key для матчинга/дедупа ✓ 3-0).
- Синк через `integrations` gateway, конфликты по УНП, изменения в `outbox` → подписчики.
- 1С мастерит контрагентов/номенклатуру/остатки (read-mostly в ERP); ERP мастерит стадии/причины/нормы.

## 5. Что делать по шагам

1. Зафиксировать контракт `register_reference` в `core/runtime/contract.py` + реестр в ядре.
2. Завести общесистемные reference data в public: единицы, валюты+**курсы (SCD2)**, страны, **НДС (SCD2)**, банки.
3. Добавить JSONB-колонку характеристик на `Sku` (без EAV).
4. Вкладка «Справочники»: дерево по отделам + универсальная таблица (код/наименование/статус/версия/кто менял/права), архив вместо удаления, аудит через `AuditLog`.
5. AI: tool/MCP-слой поверх golden records + materialized views; pgvector — позже для нечёткого поиска.
6. При апгрейде PG16→18+ — перевести историчные справочники на нативные temporal-периоды.

## Оговорки по достоверности
- Primary-источники: только Postgres temporal-tables (postgresql.org), частично SCD2/JSONB/EAV. MDM — vendor-блоги (Profisee/Verdantis/Tamr), но устоявшиеся определения (Gartner/Kimball).
- **Опровергнуто:** master-vs-reference «по частоте», adjacency-list как дефолт деревьев, «golden context 5 слоёв», обязательный real-time KG, «RAG+KG >> baseline».
- **Открыто:** хранение деревьев в Postgres (нужен ресёрч), пороги pgvector vs SQL, детали 1С-синка.
