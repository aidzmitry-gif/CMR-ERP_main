# Решение: как идти к «только наша система вместо Bitrix24 и 1С»

> **Статус документа:** стратегическая рекомендация владельцу. Везде ниже разделено **«реально сейчас» (проверено по коду)** и **«цель/намерение»**. Приоритеты — по конституции платформы (PLATFORM.md): 1) деньги собственнику → 2) безопасность → 3) функциональность → 4) эстетика.
>
> Источник: многоагентный воркфлоу `replace-bitrix-1c-strategy` (15 агентов: 4 ground-truth по коду + 5 reference-models (Odoo/enterprise-split/MDM/1С-РБ/Bitrix) + 3 adversarial + синтез→критика→финал). Ключевые код-факты повторно проверены вручную 2026-06-27.

---

## 1. Прямой честный ответ

**Заменить оба продукта целиком одним проектом — нельзя и не нужно. Это две разные задачи с разным риском, их нужно физически разнести.**

- **Bitrix24 (CRM / вовлечение) — заменяемо реально, цель достижима на горизонте 6–18 месяцев.** CRM-ядро уже воспроизведено на живой БД: в `modules/sales/routes.py` **55 декораторов `@router`** под `/sales`, воронка/канбан/карточка/задачи/история стадий/план-факт — всё на async SQLAlchemy, не mock. Bitrix — система ВОВЛЕЧЕНИЯ: ошибка в воронке = неудобство, не штраф. Коннектор `connectors/bitrix.py` живой. Здесь DIY оправдан: дифференциация (AI-агенты, маржа Китай→Минск, досье 360) — то, чего в коробке нет.

- **1С в части регулируемого учёта — заменять НЕЛЬЗЯ ни скоро, ни безопасно. И сегодня этой замены не существует даже на скелете.** Факты из кода (проверено):
  - `finance` = **173 строки всего**. Одна таблица `Payment`. Это список платежей, а не бухгалтерия. Нет проводок, двойной записи, регистров, ОСВ, закрытия периода, расчёта НДС.
  - **Ноль строк под ЭСЧФ** во всём `core+modules`. План счетов РБ (`reference.py:133 Account`) есть только как read-only справочник, а не движок проводок.
  - `core/services/onec.py` = **20 строк пустого Protocol** (`post_document` = `...`). Реальной записи в 1С нет в коде вообще.
  - `core/services/landed_cost.py` = **27 строк протокола без реализации**, `last_landed_cost → None`. Маржа продавцу сейчас считается из demo-cost mock-1С (хардкод 70/92/1230 в `modules/integrations/client.py`, демо-маржа ≈22%) — **главная денежная цель пока показывается на фейковых числах**.

- **Регуляторный замок неустраним кодом.** ЭСЧФ обязателен для всех плательщиков НДС РБ, это единственное основание для вычета НДС, грузится XML+ЭЦП на портал vat.gov.by не позднее 20-го числа. Камеральный контроль МНС автоматически сверяет декларацию со всеми ЭСЧФ — расхождение «наш ledger ↔ портал» = доначисление. Бьёт в приоритет №1 (деньги) и №2 (безопасность). За ошибку отвечает живой главбух персонально — он не подпишет отчётность из неаудированной самописи, и юридически будет прав.

- **Bus-factor = 1.** Стать собственным ERP-вендором = взять пожизненно: миграции под ежегодные изменения форм МНС, патчи безопасности, 24/7 саппорт учёта. У 1С это делает экосистема франчайзи. У вас — один человек. **Тот же bus-factor=1 относится и к частям, которые вы забираете в самопись (CRM, MDM, landed cost) — после ухода с Bitrix выручку несёт именно ваш код. План преемственности для НИХ нужен отдельно (§6).**

**Честная формулировка цели:** не «заменить и Bitrix, и 1С», а **«вытеснить Bitrix как CRM/операционный слой (можно и нужно) + стать системой-истиной мастер-данных и операций поверх 1С (можно), оставив 1С регуляторным учётным ядром на годы (нужно)»**. Полная замена 1С-ledger — отдельный многолетний проект с бухгалтером-в-команде и параллельным прогоном, либо «никогда» — и это нормальный, а не проигрышный исход.

## 2. Целевая архитектура: карта владения system-of-record

Разделять надо **роли** (вовлечение / мастер-данные / операции / ledger), а не продукты. Модульный монолит может держать всё в одном процессе/БД — это законно, **пока внутри ledger-модуля соблюдены инварианты системы-записи** (append-only проводки, запрет ретро-правок, maker≠approver).

> ⚠️ **Честность диаграммы.** Блоки `telephony (zruchna)` и `messaging` — **целевое состояние, не наличный актив**. Каркас телефонии есть; **бэкенд-модуля `messaging` НЕ существует вовсе** (`modules/messaging` отсутствует — проверено), сегодня есть только внутренний лог. Омниканал = строить с нуля (Фаза 3). Помечено `[цель]`.

**Что наша система забирает как источник истины:**

| Домен | Статус сейчас (проверено) | Забираем когда |
|---|---|---|
| Мастер-данные (контрагенты УНП, номенклатура) | MDM-движок готов (golden record, survivorship, SCD2, provenance); **но в живой БД репо — только demo-контрагенты, реальные 4766 ещё не загружены** | **Первым** — после загрузчика inbox + чистки 531 без-УНП + 41 конфликт-УНП + иерархии филиалов |
| CRM-вовлечение (сделки, лиды, звонки, задачи) | Реально на БД, 55 эндпоинтов под `/sales` | После паритета+истории из Bitrix |
| Операции (закупка, заявки, резерв-проекция) | CRUD-каркасы, маржа на demo | По мере наполнения |
| Маржинальный движок landed cost | **Пустой протокол (→None) — блокер цели №1** | Это ваш реальный продукт, строить рано (Фаза 2) |
| Омниканал (messaging) | **Бэкенд-модуля нет вовсе** — только внутренний лог | Строить с нуля (Фаза 3) |

**Что остаётся за 1С и КАК ДОЛГО:**

| Домен | Почему 1С | Горизонт |
|---|---|---|
| Ledger (двойная запись, ОСВ, баланс, закрытие периода) | Регуляторный, нулевая дифференциация | Годы / возможно навсегда |
| НДС + ЭСЧФ + декларации МНС | Гос-обязательство с дедлайном и санкциями | Только после сертифицируемого модуля + параллельного прогона |
| Истина складских остатков | Доктрина + данные ещё не выгружены | До построения учётного движка остатков |
| Payroll РБ (ФСЗН/подоходный) | Коммодити под штрафами | Не трогать, `hr` = 46 строк |

## 3. Какие образцы берём (и где не изобретаем коммодити)

- **Из Odoo — механику, не код.** Odoo доказывает, что наш паттерн (тонкое ядро + плагины + одна БД + ORM) — мейнстрим ERP, а не самодеятельность. Берём: (1) единую модель контрагента с ролями-флагами (клиент=поставщик=одна запись) — у нас уже `Counterparty`; (2) их `stock_landed_costs` как **прямой чертёж** распределения фрахта/пошлины на партию по весу/объёму — это наша методика «наценка от landed cost»; (3) их двойную запись + журналы как образец будущего finance. **Урок Odoo 19:** не писать проводку на КАЖДОЕ движение склада (раздувает ГК/аудит) — агрегировать на уровне документа. Наш outbox должен проецировать в finance по документу, а не по событию склада.
- **НЕ строим на Odoo.** Локализации РБ (план счетов, НДС, ЭСЧФ, УНП) Odoo из коробки не даёт — писать всё равно руками поверх чужого монолита, борясь с дорогими апгрейдами кастома. Экономия «взять готовое» испаряется. И мы НЕ копируем Odoo monkey-patch чужих моделей — наша изоляция «только через core/события» это осознанное улучшение.
- **Из enterprise-split — разделение РОЛЕЙ, не топологию.** «Salesforce+NetSuite раздельно» обманчив: их разделяет покупка двух чужих SaaS, а не закон. Берём принцип: ledger = система-запись (иммутабельность, maker≠approver), CRM = система-вовлечения (мягкая консистентность). Можно держать в одном монолите.
- **Из MDM-паттернов (Informatica/Reltio).** Наш MDM-слой — **реальное преимущество, не оверинжиниринг**: survivorship **на уровне поля**, provenance-alias по источнику, SCD2. Попадает в исключение «платформенный каркас» CLAUDE.md — лестница лени его НЕ упрощает.
- **Где AI — законное преимущество:** маржа продавцу В МОМЕНТ сделки + next-best-action под рост валовой прибыли (Bitrix CoPilot структурно не может — нет landed cost); скоринг на РЕАЛЬНОЙ марже; S&OP спрос→план→закупка; досье 360 по УНП. **Где НЕ изобретать:** транскрипция+резюме звонка — уже коммодити.

## 4. Фазовая дорожная карта (strangler fig)

Снимаем по **сущностям**, не по модулям. Ledger — последним. Каждая фаза = свой go/no-go. **Оценки усилий — порядковые (T-shirt), для go/no-go, не сметные.**

### Фаза 0 (сейчас → 2–4 нед): MDM-governance + ПДн-основание
- **Цель:** превратить «мост 1С→MDM доказан» в чистый golden record на живой БД — легально.
- **Строим:** **загрузчик `data/inbox/*.json` → rows** (его НЕТ; `import_counterparties` в `reference_import.py:122` УЖЕ ЕСТЬ); **расширить `_IMPORT_FIELDS`** (сейчас буквально `("name",)`, строка 23) на адрес/телефон/КПП; поле иерархии (`ГоловнойКонтрагент_Key`) в `Counterparty`; арбитражная очередь для **41 конфликт-УНП и 531 без-УНП** (запрет авто-merge).
- **ПДн (параллельно, обязательно):** правовое основание обработки ПДн 4766 контрагентов (Закон РБ №99-З), политика, реестр обработки, **договоры поручения с zruchna и хостингом**. Это документы и решения владельца — блокируют легальный забор контактов как SoR.
- **Готово к переключению:** 100% контрагентов с разрешённым ключом, 0 авто-склеек филиалов, дедуп прошёл ревью человеком, **правовое основание ПДн оформлено**.

### Фаза 1 (1–3 мес): достроить Bitrix-коннектор до полноты переезда
- **Строим (3 недостающих вызова):** `crm.deal.productrows` (товары→маржа, их НЕТ в `deal.list`), `userfield/userfieldconfig` (кастом-поля), `crm.activity.list`+timeline (история). Режим **дельт** по `>DATE_MODIFY` (курсор по `>ID` не ловит правки старых сделок). Batch до 50 команд.
- **Готово:** 17207 сделок + товары + история в ERP, дельты идут, мультиполя в `Counterparty` с `provenance=bitrix`.

### Фаза 2 (3–6 мес): landed cost + маржа на РЕАЛЬНЫХ данных. **Деньги №1**
- **Строим:** реализовать `LandedCostGateway` в procurement (инвойс+фрахт+пошлина ТН ВЭД+брокер → распределение по образцу `stock_landed_costs`); подключить к карточке сделки вместо demo-cost.
- **⚠️ Комплаенс ВНУТРИ денежной фазы:** методика завязана на ввозной НДС и таможню. Если маржа из landed cost разойдётся с тем, как 1С проводит НДС/пошлину — продавец примет ценовое решение на цифре, расходящейся с налоговой. **Бухгалтер-методолог нужен уже здесь** (триггер найма — старт Фазы 2).
- **Готово:** маржа на доске = посчитанный landed cost, не mock; **методику подписал методолог**; сверка с 1С по 5 эталонным позициям до копейки.

### Фаза 3 (параллельно, 3–6 мес): телефония + омниканал — паритет с Bitrix
- **Строим:** подключить живую zruchna (URL+токен) — каркас готов; **построить messaging-модуль С НУЛЯ** (бэкенда нет): коннекторы каналов (WhatsApp/Telegram/Viber приём+отправка) + хранение/маршрутизация. Резолв owner со строки-имени на `Counterparty.id`.
- **Готово:** входящие/исходящие реально уходят и приходят; screen-pop по УНП.

### Фаза 4 (после 1–3): переключение владения CRM + Bitrix → read-only
- **Процедура флипа (не дата) — см. §5:** правило in-flight документов, разрешение коллизий двоевластия, кто переводит `origin`.
- **Откат + точка невозврата:** до точки невозврата (напр. +30 дней после флипа) держим возможность вернуть Bitrix в роль SoR; сделки, заведённые в ERP за двоевластие, экспортируются обратно скриптом (обязан существовать ДО флипа). После точки невозврата откат закрыт — явное решение владельца.
- **Готово (go/no-go):** обе системы дают одинаковую воронку; маржа/досье 360 на данных команды; reconciliation harness (§5) зелёный; дата заморозки (за 2 нед) и дата невозврата объявлены; обратный экспорт протестирован; Bitrix → read-only + 30 дней.

### Фаза 5 (последней, горизонт лет): ledger/НДС/ЭСЧФ — ТОЛЬКО при бизнес-кейсе
- **Строим:** `core.services.tax` (XML по версионной XSD + ЭЦП ГосСУОК + POST на vat.gov.by); finance с двойной записью; **бухгалтер-методолог в команде**.
- **ЭЦП/ГосСУОК — отдельный орг-юрид. процесс:** владелец ключа подписи робота, регламент ротации, кто персонально отвечает за подпись авто-выгрузки.
- **Готово:** 2–3 параллельно закрытых периода со сходимостью до копейки + подпись главбуха + внешний аудит. До этого 1С НЕ выключается.

## 5. Data/MDM backbone (+ процедура флипа, сверка, откат)

Всё опирается на golden record — сильнейшая готовая часть (survivorship 4 стратегии, fuzzy-дедуп, SCD2, обратимый merge с аудитом). Доделать под реальный переход:

- **Ключ.** УНП **не может быть жёстким unique** — 531 (11%) без УНП, 41 значение дублируется на разных юрлицах, 87 записей с не-9-символьным ИНН. Делаем: суррогатный PK + УНП как атрибут с коллизиями + явная иерархия голова→филиал (105 филиалов несут УНП головы — авто-merge их СХЛОПНЕТ, потеряв договоры/адреса).
- **Survivorship по полю, явный source-priority.** УНП←1С, имя/телефон возможно←Bitrix. Без явного приоритета грязные имена Bitrix перезапишут чистые из 1С — тихая порча.
- **Provenance + SCD2** уже есть — канон; `reference_import` пишет `{source, at}` per-field.

**Процедура переключения владения (флип, а не дата):**
- **Что переключает.** Поле `origin/state` в `sync_link` на УРОВНЕ ЗАПИСИ: `origin=1c` → legacy, истина за 1С; `origin=erp` → наша истина. Пер-записевый strangler вместо «рубильника на всё».
- **(а) In-flight документы.** Флип записи разрешён только когда нет незакрытого документа (открытый счёт/резерв). Если есть — `flip_pending`, флип после закрытия документа фоновым циклом.
- **(б) Коллизия двоевластия.** Пока `origin=1c` — 1С выигрывает по умолчанию (кроме полей MDM по source-priority). Пока `origin=erp` — выигрывает ERP, входящая 1С-дельта по тем же полям → конфликт в арбитражную очередь, НЕ перезаписывает молча.
- **(в) Кто переводит origin.** Явное действие data-steward по зелёному отчёту сверки для пакета записей, не авто-по-таймеру. Фиксируется в аудите.
- **Идемпотентность по `external_ref` — ГЕЙТ.** Любой поток ERP→1С включается ТОЛЬКО после реализации+теста идемпотентности по `external_ref` на повторную доставку. Отдельная предварительная задача перед `post_document`.

**Reconciliation harness — обязательный артефакт с владельцем и порогом:**
- **Что:** сверка по named-полям (УНП-матч, landed cost, маржа, остатки, суммы счетов) с tolerance и списком объяснённых расхождений — НЕ по row-count.
- **Владелец:** data-steward готовит, **бухгалтер-методолог подписывает** «расхождение объяснено».
- **Частота:** перед каждым пакетным флипом + ежедневно в двоевластие + полный закрывающий цикл (месяц НДС + квартал) перед любой ledger-фазой.
- **Stop-go порог:** расхождение по денежным полям выше tolerance и **без письменного объяснения = STOP**. Неденежное с объяснением = go с фиксацией. Tolerance задаёт методолог.
- **Dual-write/CDC:** Kafka/Debezium НЕ нужен — объём (4766+17207) не big-data, а **transactional outbox уже решает dual-write**. Фаза 2 (ERP→1С) — через outbox + `sync_link(state=pending)`.

## 7. Что делать СЛЕДУЮЩИМ (ранжировано: деньги→безопасность→функции)

1. **[Деньги №1] Реализовать `LandedCostGateway` в procurement + подключить к карточке сделки.** Сейчас `core/services/landed_cost.py` = пустой протокол (→None), маржа на mock-cost (70/92/1230 в `modules/integrations/client.py`). Прямой блокер цели «рост валовой прибыли». Образец — Odoo `stock_landed_costs`. **Параллельно — подключить бухгалтера-методолога** (методика завязана на ввозной НДС/пошлину).

2. **[Деньги/данные] Дописать загрузку `data/inbox` → MDM + расширить поля + governance-очередь.** ⚠️ `import_counterparties` УЖЕ существует (`reference_import.py:122`) — писать НЕ надо. Недостающее: (а) загрузчик `data/inbox/*.json → rows`, (б) расширить `_IMPORT_FIELDS` за `("name",)` (строка 23), (в) поле иерархии филиалов в `Counterparty`, (г) арбитражная очередь для 41 конфликт-УНП / 531 без-УНП. **Плюс ПДн-основание до реального забора 4766 записей.**

3. **[Безопасность №2] Закрыть AuthN/AuthZ (Keycloak/OIDC) вместо ролей из заголовка `X-User-Roles`.** Пока система — кандидат на единственного носителя денег и ПДн, она не аутентифицирует пользователя. Блокирует расширение владения данными.

4. **[Функции] Достроить Bitrix-коннектор:** `crm.deal.productrows` + `crm.activity.list`/timeline + дельты по `>DATE_MODIFY`. Без товаров нет маржи; без истории команда не уйдёт из Bitrix.

5. **[Функции — СНАЧАЛА ВЕРИФИЦИРОВАТЬ] Рассинхрон пути лидов.** Код показывает: бэк отдаёт лиды под `/sales` (`routes.py:1364`), фронт `api.ts:891` бьёт в `${BASE}/leads`, рядом часть вызовов через Next-прокси `/api/leads`. **По памяти фронт-роуты лидов уже чинились 2026-06-26 — НЕ заявлять как подтверждённый P0.** Сначала проверить прод. Отдельно: справочник менеджеров захардкожен под «металл/прокат» (`modules/sales/leads.py:18`) — заменить на аккумуляторы.
