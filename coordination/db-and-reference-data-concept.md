# Концепция: База данных и Справочники

> Концептуальный документ (не реализация). Сводит воедино: текущую архитектуру БД,
> модель мастер-данных/справочников и доступ для AI. Опирается на:
> - `coordination/spravochniki-mdm-research.md` — исследование + проверенные тезисы.
> - `coordination/spravochniki-register-reference-spec.md` — техническая спека к вживлению.
> Статус: проект концепции. Реализацию начинаем отдельно по согласованию.

---

## 0. Зачем этот документ

Разные блоки системы (продажи, закупки, производство, склад, финансы, HR…) должны
ссылаться на **общие справочные данные** — номенклатуру, контрагентов, контакты,
сотрудников, склады, единицы, валюты и десятки классификаторов. Без единой концепции
возникает главная болезнь: **второй источник данных, который разъезжается с модулями**
(та же природа, что «двойная продажа» по остаткам).

Цель концепции — зафиксировать: какие справочники нужны, кто ими владеет, как они
хранятся, как переживают изменения во времени, как к ним получают быстрый и точный
доступ люди и AI-агенты — **не ломая изоляцию модулей**.

---

## 1. Базовые принципы (инварианты, уже действующие в системе)

Концепция справочников НЕ вводит новую архитектуру — она ложится на существующие правила ядра:

1. **Модульный монолит: тонкое ядро + модули-плагины.** Ядро знает только про `ModuleContract`; модули не лезут в внутренности друг друга — только через `core` и события.
2. **Схема на модуль.** `public` — у ядра (shared kernel); каждый модуль — своя Postgres-схема (`sales`, `wms`, …). Сейчас: 14 схем.
3. **Мягкие межмодульные ссылки.** Между схемами НЕТ cross-schema FK; ссылки по стабильному коду/строке, резолвятся на чтении.
4. **События — transactional outbox.** Связь между модулями — доменными событиями (`outbox_event` → relay → подписчики + проекция в `audit_log`).
5. **Источник истины схемы Postgres — миграции Alembic.** Схема едет как код; БД на любом окружении воспроизводится `alembic upgrade head`. SQLite-dev — только для локальной отладки.
6. **Репозитории не коммитят** — границей транзакции владеет вызывающий код (роут/workflow).

**Вывод для справочников:** справочники подчиняются тем же правилам — владелец хранит данные у себя, остальные ссылаются мягко по коду, изменения расходятся событиями, история схемы — в миграциях.

---

## 2. Слои данных

Концепция различает четыре логических слоя (физически — это схемы и таблицы Postgres):

| Слой | Что лежит | Где | Владелец |
|---|---|---|---|
| **Shared kernel** | общие сущности всех модулей | схема `public` | ядро |
| **Reference data** | мелкие системные справочники-стандарты | схема `public` (внутри shared kernel) | ядро |
| **Модульные классификаторы** | справочники конкретного домена | схема модуля | модуль |
| **AI read-models** | денормализованные витрины для агентов | `public`/материализованные представления | ядро, наполняется по событиям |

> Ключевая идея: **«Справочники» как вкладка ≠ слой хранения.** Вкладка — это
> **реестр-витрина** (registry pattern) поверх слоёв 1–3, а не пятое хранилище. См. §6.

## 3. Классификация справочников по владению

Граница проходит **НЕ по частоте изменений** (это деление исследование опровергло, 0-3),
а по **природе данных и владельцу**:

### 3.1 Reference data (системные стандарты) → shared kernel / `public`
Мелкие, общие для всех, часто внешний стандарт. Владеет ядро, физически — реальные таблицы.
- Единицы измерения (+ коэффициенты пересчёта)
- Валюты + **курсы валют** (историчные)
- Страны, регионы, города
- Ставки **НДС / налоги** (историчные)
- Банки (БИК/SWIFT)
- Языки, часовые пояса

### 3.2 Master data (крупные операционные сущности) → shared kernel / `public`
Большие, операционные, нужен жизненный цикл и дедуп. Уже частично есть в ядре.
- **Контрагенты** (`Counterparty`, с УНП) — клиенты + поставщики + перевозчики, единая запись
- **Контакты** (`Contact`)
- **Номенклатура** (`Sku`) + категории/иерархия + характеристики + единицы
- **Сотрудники / пользователи** (`User`; расширенная кадровая карточка — в `hr`)
- **Банковские счета** (свои и контрагентов)
- **Договоры** (рамочные — как справочник-ссылки; позиции — в модулях)

### 3.3 Модульные классификаторы → схема модуля
Узкие справочники конкретного домена, владеет и правит модуль.

| Домен | Справочники |
|---|---|
| sales | стадии воронки, причины отказа, типы сделок, источники лида, прайс-листы |
| procurement | типы поставщиков, условия оплаты (Net 30/60), lead time, сертификации, инкотермс |
| production | BOM/спецификации (версионные), маршруты/операции, нормы, центры обработки |
| wms | склады, зоны, ячейки (иерархия), типы операций, статусы партий |
| finance | план счетов, статьи затрат/доходов, ЦФО, проекты/направления, типы документов |
| hr | должности, оргструктура, типы начислений, причины увольнения |
| logistics | перевозчики, тарифы, типы ТС, маршруты доставки |
| service | типы обращений, SLA, категории неисправностей |
| marketing | каналы, кампании, сегменты, UTM-источники |

> **Расширенные атрибуты поставщика** (условия оплаты, lead time, сертификации, parent-child)
> — обогащение в схеме `procurement` поверх мягкой ссылки на `Counterparty`, БЕЗ дублирования
> самой записи контрагента (исследование: golden record поставщика консолидирует налоги/адреса/
> валюту/parent-child, иначе теряется переговорная сила между юрлицами).

## 4. Модель хранения (как именно хранить)

### 4.1 Единый источник истины — golden record
Для дублирующихся сущностей (особенно контрагенты) — один авторитетный golden record.
Матчинг/дедуп: комбинация детерминированного + вероятностного + fuzzy. **УНП — сильный
natural key** для контрагентов РБ (плюс ЕГР-lookup и 1С как система-источник, см. §7).

### 4.2 Историчность — датированные версии, а не «активен/архив»
Часть справочников нельзя моделировать флагом статуса: **курс валюты, ставка НДС, прайс,
версия BOM** должны помнить, что действовало на дату документа.

- Паттерн: **SCD Type 2** — `surrogate_key | natural_key | <атрибуты> | start_date | end_date`; текущая версия = `end_date IS NULL`; интервалы half-open `[start, end)`.
- ⚠️ **Ограничение стека:** нативные temporal-таблицы Postgres (`PRIMARY KEY (... WITHOUT OVERLAPS)`) — это PG18/19; у нас **PG16** → пока ручной SCD2. Модель закладывать так, чтобы при апгрейде перейти на нативные периоды без переписывания.
- Простым справочникам (единицы, страны, причины отказа) достаточно `is_active` + архив.

### 4.3 Переменные характеристики — JSONB, не EAV
Динамические атрибуты номенклатуры (цвет/размер/упаковка/тех.параметры) — в **JSONB-колонку**
на сущности, НЕ в мега-таблицу «сущность-атрибут-значение». EAV даёт раздувание хранения и
метаданных; JSONB быстрее и компактнее, сохраняя гибкость. Типизированные классификаторы
(единицы, валюты, статусы) — наоборот, нормализованные таблицы.

### 4.4 Иерархии (категории, ЦФО, ячейки, parent-child) — вопрос открыт ⚠️
Деревья нужны во многих справочниках. Дефолт «adjacency list + recursive CTE» исследование
**опровергло** (0-3), доказательной альтернативы не зафиксировано. Кандидаты: `ltree`
(пути + GiST-индекс) или closure table для read-heavy справочников. **Требуется отдельное
точечное исследование перед выбором.**

### 4.5 Общие правила для всех справочников
- **Код + наименование + статус.** Стабильный код — основа мягких межмодульных ссылок.
- **Архив вместо удаления.** Значение, использованное в документах, нельзя жёстко удалять — только архивировать.
- **Аудит изменений.** Правка справочника влияет на много модулей → запись в `audit_log` (через outbox-проекцию).
- **Мультиязычные подписи** (i18n) — где требуется (подписи колонок и значений).
- **Права на каждый справочник** — кто видит/правит (см. §8, RBAC через access-admin).

## 5. Доступ AI к справочникам

Главный принцип: **грундить агента на структурированные верифицируемые данные**, а не на
память LLM. При этом — **не переусложнять** (тезис «RAG+KG значительно лучше baseline» и
«golden context из 5 слоёв» исследование опровергло).

| Задача AI | Чем решать | Не чем |
|---|---|---|
| Точный lookup (контрагент по УНП, ставка НДС на дату, склад по коду, цена) | структурный SQL / предопределённые tools (MCP) по golden records | ❌ не эмбеддинги |
| Нечёткий поиск («синий клапан 1/2"»), дедуп похожих названий | pgvector (семантика по названиям/описаниям) | — |
| Связи между сущностями | денормализованные read-models / материализованные представления | ❌ не обязателен real-time knowledge graph |

**Реестр справочников = semantic layer для AI.** Если каждый справочник саморегистрируется с
машинно-читаемыми метаданными (ключ, отдел, типизированные колонки с семантикой, эндпоинт,
права), агент получает **каталог «что существует и как точно запросить»** — без галлюцинаций
и без эмбеддингов для большинства lookup'ов. pgvector подключается точечно и вторично.

## 6. Реестр справочников (вкладка «Справочники»)

**Концепция:** вкладка — это **витрина-агрегатор (registry pattern)**, а не хранилище.

- Модуль (или ядро) **регистрирует** свой справочник в `core`, отдавая метаданные:
  ключ, заголовок, отдел, схема-владелец, эндпоинт CRUD, типизированные колонки, права,
  признаки `archivable` / `versioned` / `ai_exposed`.
- Вкладка рисует **дерево по отделам** (Продажи / Склад / Финансы / Производство…) и
  **универсальную таблицу-редактор**, читая данные из модуля-владельца.
- **Данные остаются у владельца — дублей нет.** Реестр хранит только метаданные.
- Один и тот же контракт регистрации обслуживает сразу три потребителя:
  **UI-вкладку, RBAC и каталог для AI** (§5).

> Технические сигнатуры (`Reference`, `core.register_reference`, роут-каталог) —
> в `spravochniki-register-reference-spec.md`. Здесь — только концепция.

**Чего избегаем:** единой «мега-таблицы EAV» на все справочники — гибко, но теряются
целостность и типизация. Вместо этого — типизированные таблицы у владельцев + реестр-метаданные.

## 7. Интеграция с 1С (система-источник)

- **1С — авторитетный источник** master data контрагентов и номенклатуры; ERP получает
  golden record (1С + ЕГР-lookup по УНП). УНП — natural key для матчинга/дедупа.
- Направление по умолчанию: **1С → ERP** для того, что мастерится в 1С (контрагенты,
  номенклатура, остатки) — в ERP это read-mostly. Что рождается в ERP (стадии, причины,
  нормы, классификаторы) — мастерится в ERP.
- Транспорт — через модуль `integrations` (gateway), изменения расходятся `outbox`-событиями;
  разрешение конфликтов матчинга — по УНП.
- ⚠️ Детали (двусторонность, частота, конфликты) — инженерное решение, не закрыто
  верифицированными источниками; проектируется отдельно.

## 8. Управление и governance

- **Права на справочник** — каждый справочник несёт RBAC-коды (view/edit), управляются
  через [[access-admin-area]]. Кто видит и кто правит — задаётся на уровне справочника.
- **Аудит** — любая правка справочника проецируется в `audit_log` (append-only) через outbox.
- **Версионность значений** — для `versioned`-справочников (курсы/НДС/цены) хранится история
  (SCD2); для прочих — активность/архив.
- **Жизненный цикл значения:** создать → использовать → архивировать (не удалять, если есть ссылки).

---

## 9. Окружения и перенос

- **Схема едет как код.** Любое окружение (локальное, сервер) воспроизводит схему через
  `alembic upgrade head`. Переносить схему вручную не нужно.
- **Локально:** Postgres 16 + pgvector в Docker (один-в-один с сервером). На текущей машине —
  host-порт 5433 (5432 занят сторонним контейнером). См. [[local-postgres-setup]].
- **Данные** переносятся отдельно (`pg_dump`/restore) и только по явному согласию — это
  деструктивно для целевой БД.
- **pgvector** включается (`CREATE EXTENSION vector`) при первом использовании семантического слоя.

## 10. Открытые вопросы (требуют решения до реализации)

1. **Хранение иерархий** в Postgres (ltree vs closure table vs nested set) — не закрыто исследованием, нужен точечный ресёрч (§4.4).
2. **Граница shared-kernel ↔ потенциальный reference-data модуль** — концепция кладёт системные справочники в `public`; вынос в отдельный модуль-справочник пока не требуется (отдельный тяжёлый MDM-модуль признан избыточным).
3. **Детали 1С-синка** — направление, частота, разрешение конфликтов (§7).
4. **Пороги pgvector vs SQL/tool-calling** для конкретных справочников — когда оправданы эмбеддинги (§5).
5. **Апгрейд PG16 → PG18+** — когда переходить на нативные temporal-таблицы вместо ручного SCD2 (§4.2).

## 11. Резюме (одним абзацем)

Справочники — это **витрина-реестр поверх данных, которыми владеют ядро и модули**, а не
второе хранилище. Системные стандарты (единицы, валюты+курсы, страны, НДС, банки) и крупная
мастер-дата (контрагенты, номенклатура, контакты, пользователи) — в shared kernel (`public`);
доменные классификаторы — в схемах модулей; межмодульные ссылки — мягкие по коду. Историчные
значения версионируются (SCD2, с заделом под нативные temporal в PG18+), переменные атрибуты —
в JSONB, не EAV. AI получает точный доступ через структурный SQL/tools по golden records, а
не через эмбеддинги; pgvector — вторично, для нечёткого поиска. 1С — авторитетный источник
контрагентов/номенклатуры, синк через outbox по УНП. Всё это не ломает изоляцию модулей и
совпадает с действующим plugin-паттерном ядра.
