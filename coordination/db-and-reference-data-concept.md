# Концепция: База данных и Справочники

> Концептуальный документ (не реализация), **версия v3**. Сводит воедино: текущую архитектуру БД,
> модель мастер-данных/справочников и доступ для AI. Опирается на:
> - `coordination/spravochniki-mdm-research.md` — исследование + проверенные тезисы.
> - `coordination/db-concept-devils-advocate.md` — проверка «адвокатом дьявола» (раунды 2–3); v3 вобрал его 12 дельт.
> - `coordination/spravochniki-register-reference-spec.md` — техническая спека к вживлению.
> Статус: проект концепции. Реализацию начинаем отдельно по согласованию.

---

## 0. Зачем этот документ

Разные блоки системы (продажи, закупки, производство, склад, финансы, HR…) должны
ссылаться на **общие справочные данные** — номенклатуру, контрагентов, контакты,
сотрудников, склады, единицы, валюты и десятки классификаторов. Без единой концепции
возникает главная болезнь: **второй источник данных, который разъезжается с модулями**
(та же природа, что «двойная продажа» по остаткам).

Цель концепции — зафиксировать: какие справочники нужны, кто ими владеет, как они
хранятся, как переживают изменения во времени, как к ним получают быстрый и точный
доступ люди и AI-агенты — **не ломая изоляцию модулей**.

---

## 1. Базовые принципы (инварианты, уже действующие в системе)

Концепция справочников НЕ вводит новую архитектуру — она ложится на существующие правила ядра:

1. **Модульный монолит: тонкое ядро + модули-плагины.** Ядро знает только про `ModuleContract`; модули не лезут в внутренности друг друга — только через `core` и события.
2. **Схема на модуль.** `public` — у ядра (shared kernel); каждый модуль — своя Postgres-схема (`sales`, `wms`, …). Сейчас: 14 схем.
3. **Ссылки между модулями — двухрежимные (v3, уточнено по PVLDB).** Мы в **одной** Postgres-БД, где cross-schema FK **технически поддерживаются** → «нет FK» — это **конвенция о границах на будущее, а не ограничение движка**. Поэтому:
   - **Ссылки на shared-kernel (`public`)** — контрагент, SKU, единица, валюта — делаем **обычным DB-level FK сейчас** (бесплатная целостность, ядро не выносится в отдельный сервис).
   - **Мягкие ссылки по коду** оставляем **только там, где модуль — реальный кандидат на вынос** в отдельную БД/сервис. Иначе отказ от FK достоверно порождает записи-сироты (PVLDB, анализ 9 приложений).
   - Где ссылка мягкая — обязательны **гарды:** валидация существования перед созданием, события владельца, **reconciliation/orphan-detection jobs**, soft-delete+архив, read-only view как «контролируемый public API».
4. **События — transactional outbox.** Связь между модулями — доменными событиями (`outbox_event` → relay → подписчики + проекция в `audit_log`). **Eventual consistency — исключение, не дефолт:** внутри модуля «одна команда = одна ACID-транзакция»; outbox/saga — только для настоящих кросс-модульных операций. Доставка — **at-least-once** (не exactly-once) → **потребители идемпотентны**.
5. **Источник истины схемы Postgres — миграции Alembic.** Схема едет как код; БД на любом окружении воспроизводится `alembic upgrade head`. SQLite-dev — только для локальной отладки.
6. **Репозитории не коммитят** — границей транзакции владеет вызывающий код (роут/workflow).

**Вывод для справочников:** владелец хранит данные у себя; ссылки на shared-kernel — через FK, на выносимые модули — мягко по коду с гардами; изменения расходятся событиями; история схемы — в миграциях.

## 2. Слои данных

Концепция различает четыре логических слоя (физически — это схемы и таблицы Postgres):

| Слой | Что лежит | Где | Владелец |
|---|---|---|---|
| **Shared kernel** | общие сущности всех модулей | схема `public` | ядро |
| **Reference data** | мелкие системные справочники-стандарты | схема `public` (внутри shared kernel) | ядро |
| **Модульные классификаторы** | справочники конкретного домена | схема модуля | модуль |
| **AI read-models** | денормализованные витрины для агентов | `public`/материализованные представления | ядро, наполняется по событиям |

> Ключевая идея: **«Справочники» как вкладка ≠ слой хранения.** Вкладка — это
> **реестр-витрина** (registry pattern) поверх слоёв 1–3, а не пятое хранилище. См. §6.

**Сквозные (кросс-модульные) чтения — через read-models, не ad-hoc join (v3).** Доказано (PVLDB),
что последовательная выборка по нескольким модулям **не даёт транзакционной консистентности** и
может вернуть неполный результат. Поэтому кросс-модульные представления для UI и AI обслуживаем
**event-fed read-models (CQRS) или read-only view в `public`**, а не произвольными cross-schema
join'ами на лету.

**Границы усиливаем технически, а не дисциплиной (v3):** на каждую схему-модуль — **отдельная роль
БД** с привилегиями только на свою схему (дёшево при <~20 схемах), чтобы модуль физически не мог
прочитать чужую схему в обход контракта.

## 3. Классификация справочников по владению

Граница проходит **НЕ по частоте изменений** (это деление исследование опровергло, 0-3),
а по **природе данных и владельцу**:

### 3.1 Reference data (системные стандарты) → shared kernel / `public`
Мелкие, общие для всех, часто внешний стандарт. Владеет ядро, физически — реальные таблицы.
- Единицы измерения (+ коэффициенты пересчёта)
- Валюты + **курсы валют** (историчные)
- Страны, регионы, города
- Ставки **НДС / налоги** (историчные)
- Банки (БИК/SWIFT)
- Языки, часовые пояса

### 3.2 Master data (крупные операционные сущности) → shared kernel / `public`
Большие, операционные, нужен жизненный цикл и дедуп. Уже частично есть в ядре.
- **Контрагенты** (`Counterparty`, с УНП) — клиенты + поставщики + перевозчики, единая запись
- **Контакты** (`Contact`)
- **Номенклатура** (`Sku`) + категории/иерархия + характеристики + единицы
- **Сотрудники / пользователи** (`User`; расширенная кадровая карточка — в `hr`)
- **Банковские счета** (свои и контрагентов)
- **Договоры** (рамочные — как справочник-ссылки; позиции — в модулях)

### 3.3 Модульные классификаторы → схема модуля
Узкие справочники конкретного домена, владеет и правит модуль.

| Домен | Справочники |
|---|---|
| sales | стадии воронки, причины отказа, типы сделок, источники лида, прайс-листы |
| procurement | типы поставщиков, условия оплаты (Net 30/60), lead time, сертификации, инкотермс |
| production | BOM/спецификации (версионные), маршруты/операции, нормы, центры обработки |
| wms | склады, зоны, ячейки (иерархия), типы операций, статусы партий |
| finance | план счетов, статьи затрат/доходов, ЦФО, проекты/направления, типы документов |
| hr | должности, оргструктура, типы начислений, причины увольнения |
| logistics | перевозчики, тарифы, типы ТС, маршруты доставки |
| service | типы обращений, SLA, категории неисправностей |
| marketing | каналы, кампании, сегменты, UTM-источники |

> **Расширенные атрибуты поставщика** (условия оплаты, lead time, сертификации, parent-child)
> — обогащение в схеме `procurement` поверх мягкой ссылки на `Counterparty`, БЕЗ дублирования
> самой записи контрагента (исследование: golden record поставщика консолидирует налоги/адреса/
> валюту/parent-child, иначе теряется переговорная сила между юрлицами).

## 4. Модель хранения (как именно хранить)

### 4.1 Единый источник истины — golden record
Для дублирующихся сущностей (особенно контрагенты) — один авторитетный golden record.
**Система-источник мастер-данных — сам ERP** (golden record живёт в `public`), а не 1С;
1С — лишь временный входной адаптер (см. §7). Матчинг/дедуп: комбинация детерминированного +
вероятностного + fuzzy — выполняет **MDM-сервис в ядре** (§7.2). **УНП — сильный natural key**
для контрагентов РБ (внешний стандарт, не зависит от 1С), плюс ЕГР-lookup. Идентификаторы 1С
хранятся как вторичный alias, а не как первичный ключ.

### 4.2 Историчность — датированные версии, а не «активен/архив»
Часть справочников нельзя моделировать флагом статуса: **курс валюты, ставка НДС, прайс,
версия BOM** должны помнить, что действовало на дату документа.

- Паттерн: **SCD Type 2** — `surrogate_key | natural_key | <атрибуты> | start_date | end_date`; текущая версия = `end_date IS NULL`; интервалы half-open `[start, end)`.
- ⚠️ **Ограничение стека:** нативные temporal-таблицы Postgres (`PRIMARY KEY (... WITHOUT OVERLAPS)`) — это PG18/19; у нас **PG16** → пока ручной SCD2.
- **Важно (v3):** PG18 (релиз 25.09.2025) даёт только **темпоральные ОГРАНИЧЕНИЯ** (WITHOUT OVERLAPS / PERIOD FK), а **НЕ** полноценные bitemporal-таблицы SQL:2011 (они ещё в разработке, возможно PG19+). То есть **ручной SCD2 не заменится «из коробки» даже на PG18** — для аудит-критичных доменов он (или event sourcing / CQRS) остаётся актуальным дольше, чем мы рассчитывали. Миграцию планировать поэтапно.
- Простым справочникам (единицы, страны, причины отказа) достаточно `is_active` + архив.

### 4.3 Переменные характеристики — JSONB, не EAV (но гибрид на масштабе)
Динамические атрибуты номенклатуры (цвет/размер/упаковка/тех.параметры) — в **JSONB-колонку**
на сущности, НЕ в мега-таблицу «сущность-атрибут-значение». EAV даёт раздувание хранения и
метаданных; JSONB быстрее и компактнее, сохраняя гибкость. Типизированные классификаторы
(единицы, валюты, статусы) — наоборот, нормализованные таблицы.

**Пределы JSONB и гибридный паттерн (v3):**
- Конкретный обрыв производительности — **~2 КБ (TOAST-порог)**: значение крупнее сжимается и
  выносится out-of-line; чтение **одного** поля детостит **весь** документ (типично 2–10×, в
  пределе ~40× медленнее), а апдейт любого поля = **полная перезапись всего значения** (рост WAL).
- Поэтому на масштабе каталога (сотни тыс.–млн SKU) — **гибрид:** «горячие» (часто фильтруемые/
  сортируемые) атрибуты выносим в **типизированные / generated-колонки** (с обычными индексами),
  длинный хвост атрибутов — в **JSONB** (GIN-индекс). JSONB-блоб на SKU держать небольшим.
- **Настоящий фасетный поиск** при млн SKU — не на JSONB, а на **внешнем search-движке**
  (Elasticsearch/OpenSearch) или расширении (ParadeDB `pg_search`/BM25). Это уже search-слой, не основное хранилище.

### 4.4 Иерархии (категории, ЦФО, ячейки, parent-child) — РЕШЕНО

Деревья нужны во многих справочниках. Решение по итогам точечного ресёрча (источники —
первичные: postgresql.org/docs/16, docs.sqlalchemy.org; ⚠️ adversarial-верификация в ресёрче
упала на сбое API `403`, поэтому опираемся на качество первоисточников, а не на голосование):

**Основной паттерн (source of truth) — adjacency list** (`parent_id` self-reference в той же таблице):
- добавление узла не меняет другие строки; перенос поддерева = правка одной строки; целостность — обычным FK **внутри той же таблицы/схемы** (не cross-schema, проблемы мягких ссылок нет — родитель в той же таблице);
- обход поддеревьев/предков — `WITH RECURSIVE` (есть в Postgres и **в SQLite** → переносимо в dev);
- запрет циклов — `CYCLE`-клауза рекурсивного CTE (или триггер);
- каскад архивации — рекурсивным `UPDATE`.

**Производный индекс для чтения (Postgres-only, опционально, где read-heavy/AI) — ltree (materialized path):**
- денормализованная колонка-путь `Top.Категории.Европа`, GiST-индекс (`gist_ltree_ops`) ускоряет ancestor/descendant/`lquery`;
- **это вторичный слой, derived из adjacency list**, а не источник истины; пересобирается при изменении структуры. Минусы: перенос поддерева = апдейт путей всех потомков; ограничение размера сигнатуры GiST для очень глубоких деревьев.

**Когда что:** большинство справочных деревьев ERP (категории, ЦФО, ячейки) — **мелкие, shallow,
редкие правки** → достаточно чистого adjacency list + recursive CTE. ltree-путь добавлять только
там, где доказанно нужна скорость чтения поддеревьев или удобная подача пути AI-агенту.

> Разрешение прошлого противоречия: ранний ресёрч «опроверг» adjacency list **как дефолт** (0-3) —
> но он отвергал абсолютную формулировку «лучший по умолчанию, потому что прост». Уточнённая
> позиция (adjacency list = истина + ltree = производный индекс) снимает противоречие.

**SQLAlchemy 2 + Alembic:** self-referential relationship c `remote_side`; ltree — через тип
(`sqlalchemy-utils` LtreeType или кастомный); миграция требует `CREATE EXTENSION ltree`.
**SQLite-dev:** adjacency list + recursive CTE работают; ltree в SQLite НЕТ → ltree-слой только
Postgres, dev держится на adjacency-list-истине (ещё один довод за этот выбор как переносимый).

**Граница графов (v3):** adjacency+ltree закрывают **иерархии** (категории, ЦФО, ячейки, оргструктура —
мелкие/средней глубины). Но для **глубокой граф-аналитики** (сети связей контрагентов, большие BOM с
обходом по миллионам узлов) Postgres+AGE недостаточно (нет index-free adjacency, рекурсивные CTE
деградируют/OOM на масштабе) — там на горизонте 5 лет вероятен **полиглот: выделенная graph DB**.
Не закладывать тяжёлую граф-аналитику на рекурсивные CTE.

### 4.5 Общие правила для всех справочников
- **Код + наименование + статус.** Стабильный код — основа мягких межмодульных ссылок.
- **Архив вместо удаления.** Значение, использованное в документах, нельзя жёстко удалять — только архивировать.
- **Аудит изменений.** Правка справочника влияет на много модулей → запись в `audit_log` (через outbox-проекцию).
- **Мультиязычные подписи** (i18n) — где требуется (подписи колонок и значений).
- **Права на каждый справочник** — кто видит/правит (см. §8, RBAC через access-admin).

## 5. Доступ AI к справочникам

Главный принцип: **грундить агента на структурированные верифицируемые данные**, а не на
память LLM. При этом — **не переусложнять** (тезис «RAG+KG значительно лучше baseline» и
«golden context из 5 слоёв» исследование опровергло).

| Задача AI | Чем решать | Не чем |
|---|---|---|
| Точный lookup (контрагент по УНП, ставка НДС на дату, склад по коду, цена) | структурный SQL / предопределённые tools (MCP) **поверх semantic-слоя** по golden records | ❌ не эмбеддинги, ❌ не сырая схема |
| Метрики/агрегаты («выручка по менеджеру за месяц») | предопределённые метрики semantic-слоя | ❌ не свободный text-to-SQL по сырой схеме |
| Нечёткий поиск («синий клапан 1/2"»), дедуп похожих названий | pgvector (семантика по названиям/описаниям) | — |
| Связи между сущностями | денормализованные read-models / материализованные представления | ❌ не обязателен real-time knowledge graph |

**Явный semantic/metrics-слой между AI и данными (v3, medium-доказательность).** Свежий бенчмарк
(dbt 2026) показывает: семантический слой точнее свободного text-to-SQL по сырой схеме (98–100% vs
84–90%). Поэтому MCP-tools строим **поверх слоя определений метрик/измерений** (свой metrics-слой
или dbt Semantic Layer / Cube), а не над голой схемой — иначе риск **тихих галлюцинаций в числах**.
⚠️ Доказательность medium (вендор-самобенчмарк, малый объём; громкие проценты из др. источников опровергнуты) — но направление надёжно.

**Реестр справочников = часть semantic-слоя для AI.** Если каждый справочник саморегистрируется с
машинно-читаемыми метаданными (ключ, отдел, типизированные колонки с семантикой, эндпоинт,
права), агент получает **каталог «что существует и как точно запросить»** — без галлюцинаций
и без эмбеддингов для большинства lookup'ов.

**pgvector — вторичен, и знать его границы (v3).** Для нечёткого поиска по названиям/дедупа pgvector
достаточен. Но у него документированы слабые места под **фильтрацией по метаданным** (recall-cliff
post-filter, неоптимальные планы оптимизатора). **Выделенная vector DB** (Qdrant/Milvus/Weaviate)
оправдана при **высоком QPS, тяжёлой фильтрации или крупном RAG** — но она **не авто-победитель**
(преимущество по filtered-recall не доказано). Конкретный порог — рабочий, проверять при росте нагрузки.

## 6. Реестр справочников (вкладка «Справочники»)

**Концепция:** вкладка — это **витрина-агрегатор (registry pattern)**, а не хранилище.

- Модуль (или ядро) **регистрирует** свой справочник в `core`, отдавая метаданные:
  ключ, заголовок, отдел, схема-владелец, эндпоинт CRUD, типизированные колонки, права,
  признаки `archivable` / `versioned` / `ai_exposed`.
- Вкладка рисует **дерево по отделам** (Продажи / Склад / Финансы / Производство…) и
  **универсальную таблицу-редактор**, читая данные из модуля-владельца.
- **Данные остаются у владельца — дублей нет.** Реестр хранит только метаданные.
- Один и тот же контракт регистрации обслуживает сразу три потребителя:
  **UI-вкладку, RBAC и каталог для AI** (§5).

> Технические сигнатуры (`Reference`, `core.register_reference`, роут-каталог) —
> в `spravochniki-register-reference-spec.md`. Здесь — только концепция.

**Чего избегаем:** единой «мега-таблицы EAV» на все справочники — гибко, но теряются
целостность и типизация. Вместо этого — типизированные таблицы у владельцев + реестр-метаданные.

## 7. Система-источник, MDM-сервис и 1С

### 7.1 ERP — система-источник мастер-данных (с первого дня)
Golden record контрагентов/номенклатуры живёт в `public` ERP **всегда**, независимо от 1С.
ERP — владелец и источник истины; внешние системы — лишь поставщики/потребители.
- **Natural keys — собственные:** УНП для контрагентов (внешний стандарт, не зависит от 1С),
  собственный код ERP для номенклатуры. Идентификаторы 1С — **вторичный alias**.
- Цель — чтобы **отказ от 1С в будущем был безболезненным**: данные уже в ERP, ссылки уже
  по кодам ERP, MDM уже в ядре. Отключение 1С = выключить один адаптер, структурно ничего не меняется.

### 7.2 MDM — сервисный слой в ядре (не отдельный модуль)
Раз ERP сам мастерит данные (а с уходом 1С — полностью), функции качества данных живут в
**`core/services` рядом с golden record в shared kernel**, а НЕ в отдельном плагин-модуле
(отдельная схема под общие данные противоречила бы паттерну «модуль владеет своим, не общим»).
MDM-сервис отвечает за:
- дедупликацию и **матчинг** (детерминированный по УНП/коду + вероятностный/fuzzy);
- **survivorship**-правила (какое значение «победитель» при слиянии);
- **merge / unmerge** записей (склейка и расклейка дублей);
- валидацию и качество данных.
Включается постепенно: старт — простой матчинг по УНП (уже есть через ЕГР), далее fuzzy/survivorship.

**MDM = rule-based + ML гибрид (v3).** Ядро — детерминированные правила (УНП/код) + вероятностный/
fuzzy-матчинг; ML — в помощь, не вместо. **НЕ закладываться на маркетинговое «AI замастерит 95%
сам»** — это утверждение и «мульти-агентный RAG для матчинга» в исследовании **опровергнуты** (0-3).
Человек-в-контуре (approval) на спорных merge — остаётся.

### 7.3 1С — временный входной адаптер
- 1С подключается как **inbound source-adapter** через модуль `integrations` (gateway):
  поставляет/обновляет записи `outbox`-событиями. **Не владелец данных.**
- Направление: **1С → ERP** для того, что сейчас мастерится в 1С (контрагенты, номенклатура,
  остатки). По мере переноса мастерства в ERP адаптер выключается по сущностям.
- ⚠️ Детали (частота, разрешение конфликтов) — инженерное решение, проектируется отдельно;
  конфликты матчинга — по УНП через MDM-сервис (§7.2).

## 8. Управление и governance

- **Права на справочник** — каждый справочник несёт RBAC-коды (view/edit), управляются
  через [[access-admin-area]]. Кто видит и кто правит — задаётся на уровне справочника.
- **Аудит** — любая правка справочника проецируется в `audit_log` (append-only) через outbox.
- **Версионность значений** — для `versioned`-справочников (курсы/НДС/цены) хранится история
  (SCD2); для прочих — активность/архив.
- **Жизненный цикл значения:** создать → использовать → архивировать (не удалять, если есть ссылки).

## 9. Окружения, перенос и OLTP↔OLAP

- **Схема едет как код.** Любое окружение (локальное, сервер) воспроизводит схему через
  `alembic upgrade head`. Переносить схему вручную не нужно.
- **Локально:** Postgres 16 + pgvector в Docker (один-в-один с сервером). На текущей машине —
  host-порт 5433 (5432 занят сторонним контейнером). См. [[local-postgres-setup]].
- **Данные** переносятся отдельно (`pg_dump`/restore) и только по явному согласию — это
  деструктивно для целевой БД.
- **pgvector** включается (`CREATE EXTENSION vector`) при первом использовании семантического слоя.

### 9.1 Разделение OLTP и OLAP (v3 — самый ранний риск пересмотра)
Postgres силён в OLTP, но **на аналитике в масштабе проседает** (строковое хранение; потолок
Postgres-only OLAP ~100 GB или когда аналитика конкурирует с OLTP-трафиком). Колоночные движки
дают 10–100× на агрегациях.
- **Сейчас (interim):** денормализованные read-models / materialized views в том же Postgres — ОК.
- **Целевое при росте аналитики/AI-агрегаций:** отдельный **колоночный слой** — расширение
  (Citus columnar / TimescaleDB) или **внешний движок (ClickHouse/DuckDB) через CDC** (Debezium из outbox).
- **Правило:** тяжёлую аналитику и AI-агрегации **не строить на OLTP-таблицах**; заложить путь к
  колоночному чтению заранее, чтобы read-models мигрировали туда без переписывания потребителей.
- ⚠️ Отдельный **lakehouse-в-Postgres** (типа pg_analytics) — тупиковый путь (вендор закрыл в 03.2025); выбирать проверенные колоночные расширения или внешний движок.

## 10. Статус вопросов

**Закрыто (раунды исследования + проверка «адвокатом дьявола»):**
- ✅ **Хранение иерархий** — adjacency list (истина) + опциональный ltree-путь (§4.4); глубокая граф-аналитика → возможный полиглот.
- ✅ **MDM** — rule-based+ML сервис в ядре, не отдельный модуль и не «AI сам» (§7.2).
- ✅ **Роль 1С** — временный входной адаптер; ERP — система-источник с первого дня (§7.1, §7.3).
- ✅ **Ссылки/FK** — в одной БД держим DB-level FK на shared-kernel; мягкие ссылки только под вынос модуля + гарды (§1).
- ✅ **Сквозные чтения** — через read-models/view, не ad-hoc join (§2).
- ✅ **Доступ AI** — semantic-слой + MCP-tools поверх него; pgvector вторичен (§5).
- ✅ **JSONB** — гибрид (типизир. горячие + JSONB хвост), внешний search для фасетов (§4.3).
- ✅ **OLTP↔OLAP** — заложено разделение, колоночный слой при росте (§9.1).

**Остаются только рабочие пороги (тюнинг при реализации, не концептуальные дыры):**
1. Точное число SKU / сложность фасетов, где нужен внешний search-движок (§4.3).
2. Конверт pgvector (QPS/recall/фильтрация), за которым нужна выделенная vector DB (§5).
3. Cadence и дизайн reconciliation/orphan-detection jobs для мягких ссылок (§1).
4. Апгрейд PG16 → PG18+ и момент частичного перехода с ручного SCD2 (§4.2).
5. Детали 1С-адаптера — частота синка, порядок вывода сущностей (§7.3).
6. Когда golden-record/entity-resolution всё же требует централизованного материализованного хаба, а не registry (§6).

## 11. Резюме (одним абзацем)

Справочники — это **витрина-реестр поверх данных, которыми владеют ядро и модули**, а не
второе хранилище. Системные стандарты (единицы, валюты+курсы, страны, НДС, банки) и крупная
мастер-дата (контрагенты, номенклатура, контакты, пользователи) — в shared kernel (`public`);
доменные классификаторы — в схемах модулей. **Ссылки на shared-kernel — обычным DB-level FK
(мы в одной БД); мягкие ссылки по коду — только там, где модуль кандидат на вынос, и с гардами
(валидация, события, reconciliation-jobs); сквозные чтения — через read-models/view, не ad-hoc
join.** Историчные значения версионируются (ручной SCD2 — он остаётся актуальным дольше PG18,
который дал лишь темпоральные ограничения, а не полный bitemporal); переменные атрибуты — в JSONB,
не EAV, **с гибридом** (горячие — в типизированные колонки, ~2 КБ TOAST-обрыв) и внешним search для
фасетов; иерархии — adjacency list (истина) + ltree-путь для чтения, глубокая граф-аналитика → полиглот.
**ERP — система-источник мастер-данных с первого дня; MDM (rule-based+ML, не «AI сам») — сервис в
ядре. 1С — временный входной адаптер, не владелец: отказ = выключить адаптер** (natural keys свои:
УНП и коды ERP; id 1С — alias). AI получает доступ через **semantic-слой + MCP-tools поверх него**
(не сырая схема, не эмбеддинги для точных значений); pgvector — вторично. **Аналитику разводим OLTP↔OLAP:
read-models в PG сейчас, колоночный слой/внешний движок через CDC при росте.** Всё это не ломает
изоляцию модулей и совпадает с действующим plugin-паттерном ядра.
