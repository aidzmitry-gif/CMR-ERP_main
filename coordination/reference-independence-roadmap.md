## 0. TL;DR — где вы сейчас и что отделяет от независимости

**Фундамент уже не «копия 1С».** В коде есть то, чего нет ни в 1С, ни в Битрикс и что и
делает ERP кандидатом на роль системы-истины:

- golden record контрагента (`Counterparty.unp` как natural key) + **обратимый merge/unmerge**
  (`core/services/mdm.py`);
- **provenance** через `CounterpartyAlias(source, external_ref)` — «эта запись пришла из 1С/Битрикс»;
- **структурный AI-доступ** (`reference_query.query` — точные значения, не эмбеддинги);
- **SCD2-историчность** курсов и НДС (`core/services/scd2.py`);
- **реестр-витрина** `/system/references` (один контракт обслуживает UI + RBAC + AI).

**Что отделяет от «1С и Битрикс не нужны» — ровно три разрыва** между концепцией и кодом:

| # | Разрыв | Что держит зависимость | Веха |
|---|--------|------------------------|------|
| **A** | Provenance — на уровне записи, не поля; survivorship захардкожен | Обратный синк 1С затрёт ваш эталон → 1С остаётся «главным» психологически | **M2** |
| **B** | Поток только 1С → ERP (`post_document` — заглушка) | 1С остаётся владельцем мастер-данных по факту | **M3** |
| **C** | Номенклатура в коде = `code/title/unit`; партии/landed cost/ячейки/срок — только в HTML-макете | Товар с себестоимостью и партиями — главное, ради чего держат 1С | **M4** |
| **+** | История касаний (звонки/письма/сделки) не сходится на карточке контрагента | Битрикс держат ради 360°-общения | **M5** |

Дальше — вехи по порядку отдачи. Каждая самостоятельна: можно остановиться на любой и получить
законченный прирост, не оставив систему в полу-состоянии.

## M1. Базовая гигиена данных (closing the cheap gaps) — 1–2 дня

Дешёвые вещи, без которых остальные вехи стоят на песке. Всё — расширения существующего, не новое.

1. **Fuzzy-матчинг по имени (`pg_trgm`).** Сейчас `mdm.match_candidates` — только exact по УНП
   (`core/services/mdm.py:49`). Контрагент без УНП или с опечаткой пройдёт как новый → дубль.
   Добавить вероятностный матч по имени (`pg_trgm`, порог similarity) **как кандидата на approval**,
   не авто-merge (человек-в-контуре — концепция §7.2). SQLite-dev: `pg_trgm` нет → fuzzy только под Postgres,
   фолбэк на exact (как ltree-слой).
2. **ЕГР-lookup реквизитов** (`GET /integrations/egr/{unp}` — контракт уже есть). Довести до
   реального запроса: реквизиты приходят из госреестра, а не из 1С. Это **обрезает зависимость
   от 1С по самому ценному** (точность реквизитов) у первоисточника. Где недоступно — деградирует
   в ручной ввод.
3. **Аудит правок справочников реально пишется.** Инфраструктура есть (`AuditLog` + relay), но
   CRUD-роуты справочников (units/currencies/…) emit'ят ли событие правки? Проверить и, где нет,
   добавить `event_bus.emit("reference.<key>.changed", …)` в PATCH/DELETE — иначе «кто менял
   справочник» пусто, а это governance-требование концепции §8.

**Критерий готовности M1:** дубль с опечаткой ловится в кандидаты; реквизиты тянутся из ЕГР;
любая правка справочника видна в аудите с actor.

## M2. Field-level provenance + survivorship как данные — ⭐ наивысшая отдача/стоимость

> ✅ **РЕАЛИЗОВАНО (2026-06-25).** `Counterparty.provenance` (JSON, миграция 0044), модель
> `SurvivorshipRule`, движок `core/services/survivorship.py` (4 стратегии), встроен в
> `reference_import`. Макеты `spravochniki-card-provenance.html` + `spravochniki-merge-rules.html`.
> Хвост: provenance/правила для `Sku` (вместе с M4), fuzzy-матч `pg_trgm` (M1), ЕГР-lookup (M1).

**Зачем первым.** Самая дешёвая по коду веха с самым сильным эффектом: после неё **обратный
синк 1С перестаёт быть страшным**, и ERP психологически становится истиной. Без неё первый же
синк из 1С затрёт ваши правки — и вы остаётесь в положении «1С главный».

### M2.1 Provenance на уровне поля, а не записи
Сейчас источник — на всю запись (`CounterpartyAlias`). Нужно: каждое поле знает источник и время.
- «Наименование → 1С, 02.06» · «УНП → ЕГР, эталон» · «Телефон → Битрикс, переопределён здесь».
- Модель: таблица `field_provenance(entity_type, entity_id, field, source, value_at, trust)` ИЛИ
  JSONB-колонка `provenance` на сущности (горячих полей немного — JSONB уместен, концепция §4.3).
  **Решение A/B — за владельцем** (отдельная таблица читается единообразно для всех сущностей;
  JSONB дешевле на старте). Рекомендация: JSONB на старте, вынос в таблицу при росте.
- UI: на карточке у каждого поля — микро-бейдж источника (📥1С / ✍ вручную / 🏛ЕГР / 🔵Битрикс),
  тултип «значение из X от ДД.ММ». Уже есть язык бейджей в макете карточки.

### M2.2 Survivorship-правила как данные, не хардкод
Сейчас `_SURVIVORSHIP_FIELDS = ("name", "unp")` + «непустое выигрывает» зашиты в `mdm.py:19,67`.
- Таблица правил по полю: `survivorship_rule(entity_type, field, strategy, source_priority)`.
  Стратегии: `most_recent` (телефон) · `source_priority` (УНП — только ЕГР) · `non_empty_wins` (дефолт) ·
  `manual_only` (эталон не трогаем).
- При синке/merge движок применяет правило поля → **1С больше не затирает то, что закреплено за ERP/ЕГР**.
- UI: экран «Правила слияния» в справочниках (читается из реестра; правят супер-роли).

### M2.3 Trust score источника
1С точен в УНП/деньгах, Битрикс врёт в названиях, ЕГР — абсолют по реквизитам. Источник несёт вес;
поле показывает «уверенность». Это вход для survivorship `source_priority` и для UI-бейджа.

**Критерий готовности M2:** обратный синк из 1С НЕ затирает поля, закреплённые правилом за ERP/ЕГР;
на карточке видно, какому полю откуда верить; правила слияния редактируются, не кодом.

> ⚠️ Совместимость: `field_provenance`/`provenance` не ломает существующий `CounterpartyAlias` —
> alias остаётся для record-level MDM-провенанса и дедупа; field-level — слой поверх, не вместо.

## M3. Двунаправленный синк + журнал выгрузки — переворачивает поток

> ✅ **РЕАЛИЗОВАНО — каркас (2026-06-25).** Таблица `sync_link` (опция B, миграция 0045),
> сервис `core/services/sync_outbound.py` (`enqueue`/`flush_pending`/`journal`), фоновый
> `core.on_tick(tick_sync_out)`, роуты `/integrations/1c/sync-out · sync-journal · enqueue`,
> макет `spravochniki-sync-journal.html`. Выгрузка идёт через mock `post_document` за
> gateway-протоколом — реальный OData-POST подключается заменой в `OneCClient` (чтение OData
> уже работает в `connectors/`). Решения владельца: оба пути рождения (карточка+сделка),
> контрагенты+номенклатура. Хвост: врезка `enqueue` в sales-роут создания контрагента; реальный
> OData-write.

**Это и есть граница зависимости от 1С.** Пока поток только `1С → ERP`, 1С — владелец де-факто.
**Проектирование уже сделано** в [onec-bidirectional-sync-plan.md](onec-bidirectional-sync-plan.md) —
M3 = его реализация. Не пересматривать, исполнять.

1. **Модель направления синка** (план §3, **рекомендована опция B**): таблица `sync_link(entity_type,
   entity_id, system, external_ref, origin, state, direction, last_synced_at, error_text)` — одно место
   статуса/внешнего id под любую сущность и систему. `CounterpartyAlias` остаётся для MDM, роль
   «ссылка в 1С + статус» переезжает в `sync_link`. Миграция + перенос 1С-`Ref_Key` из alias.
2. **«Создать здесь» → outbox на выгрузку** (план §5): создание эталона в ERP → `sync_link(state=pending,
   direction=out)` + `event_bus.emit("counterparty.sync.requested", …)` в той же транзакции; фоновый
   `_background_loop` (уже есть) подбирает pending → `OneCGateway.post_document` → `external_ref=Ref_Key,
   state=synced`. Идемпотентность по УНП.
3. **Экран «Журнал выгрузки»** (план §4.4): зеркало журнала импорта — что/когда/куда ушло, подтверждено,
   упало, ручной повтор. Питается `counterparty.sync.queued/sent/failed`.
4. **Бейдж происхождения/статуса** на записи (план §4.2): «создано в ERP / из 1С» + «выгружено ✓ /
   ожидает ⏳ / локально / ошибка». Сейчас можно на demo; логика — по `sync_link`.

**Открытые вопросы к владельцу — в плане §7** (модель A/B; кто «рождает» контрагента; номенклатуру
тоже выгружаем?; разрешение конфликтов ERP↔1С; набор выгружаемых полей). **Они блокируют M3** —
ответить до старта.

**Критерий готовности M3:** контрагент, созданный в ERP, доезжает в 1С с подтверждением; журнал
выгрузки показывает статус и даёт повтор; при правке и там и там конфликт решается по правилу (M2).

## M4. Номенклатура как полноценный мастер — ⭐ главный кусок, ради которого держат 1С

**Самый большой незакрытый разрыв.** В коде `Sku` = `code/title/unit/category_id`. Богатый макет
([nomenclature-card-preview.html] + batch + movements) живёт **только в HTML — 0% бэкенда**. Именно
товар с себестоимостью и партиями — то, ради чего реально держат 1С. Спека частично есть в
[procurement-costing-handoff.md](procurement-costing-handoff.md).

Повехово (каждый под-шаг = самостоятельный прирост):

1. **Карточка SKU до уровня контрагента** — provenance (M2 применить к номенклатуре), golden record,
   архив-не-удаление. Горячие поля (вес, ТН ВЭД, ед.изм) — типизированные колонки; тех.хвост — JSONB
   (концепция §4.3, гибрид, ~2КБ TOAST-обрыв).
2. **Партии (lot/batch)** — модель `batch(sku_id, supplier_batch_no, mfg_date, expiry_date, qty, …)`.
   FEFO-срок годности с алертом <1 года (макет batch уже это рисует). Связь партия→машина→ГТД.
3. **Landed cost** — себестоимость партии (инвойс + фрахт + пошлина по ТН ВЭД + брокер). Методика —
   [pricing-methodology.md](pricing-methodology.md) / `cost-calc-china-methodology` (память). **Это
   блокер маржи** ([sales-margin-analysis] — продавец не видит себестоимость в момент сделки).
4. **Складское размещение (ячейка/стеллаж)** + движения (`nomenclature-movements-report.html` → регистр).
   ⚠️ Граница: **склад/остатки — истина 1С** (память `invoice-1c-reserve-shipment`), ERP показывает,
   1С владеет — до отдельного решения о переносе WMS.
5. **ТН ВЭД + пошлина из справочника** — связать с реестром (справочник ТН ВЭД), не строкой на карточке.

**Критерий готовности M4:** карточка номенклатуры в макете питается реальными моделями; landed cost
виден продавцу; срок годности по партиям с FEFO-алертом; движения — из регистра.

> Объём M4 большой — это под-дорожная-карта. Перед стартом разнести под-шаги 1–5 по приоритету
> отдельно (landed cost первым — он блокер денег).

## M5. Карточка контрагента → точка входа в 360° (чтобы выкинуть Битрикс)

Битрикс держат ради **общения/сделок/задач**. У вас есть `Contact`, MDM, провенанс — но история
касаний (звонки/письма/сделки) не сходится на карточке. Это смыкается с коннекторами
[client-360-bitrix-1c](#) и `bitrix-connector-call-kb` (память).

1. **История касаний на карточке** — звонки (`comm_call` из коннектора Bitrix/телефонии), письма,
   сделки в одном месте, по `entity_ref` контрагента. Read-model по событиям (CQRS — концепция §2),
   не ad-hoc join.
2. **Импорт из Битрикс как source-adapter** — по аналогии с 1С: `source="bitrix"` в alias уже
   поддержан. Импорт общения/сделок → провенанс → дедуп в существующий MDM.
3. **Карточка = вход в 360°** — реквизиты (M2 provenance) + контакты + история касаний + сделки + деньги
   (из 1С/финансов). Тогда Битрикс не нужен: всё в одном эталоне.

**Критерий готовности M5:** на карточке контрагента видна вся история общения и сделок; импорт из
Битрикс кладёт данные в тот же golden record без дублей.

## Порядок и зависимости

```
M1 (гигиена) ──┬─> M2 (field provenance + survivorship) ──> M3 (двусторонний синк)
               │                    │
               │                    └──> M4 (номенклатура: provenance применяется к SKU)
               │
               └─> M5 (360°: использует MDM/дедуп из M1)
```

- **M2 — первым** (наивысшая отдача/стоимость; разблокирует безопасный обратный синк).
- **M3 зависит от M2** (конфликт-резолв при двустороннем потоке = survivorship-правила).
- **M4 — самый большой**, частично независим (можно начать landed cost параллельно M2/M3).
- **M5 — параллельная ветка** (общение/Битрикс), опирается на дедуп.

## Что НЕ делаем (явные не-цели, чтобы не расползлось)

- ❌ Не выносим справочники в отдельный submodule — **решено** (концепция §6.1, idea-verifier единогласно).
- ❌ Не строим knowledge graph **как способ AI-доступа к мастер-данным и авто-мастеринга** —
  именно это опровергнуто (концепция §5, §7.2): для точного lookup (контрагент по УНП, цена,
  НДС на дату) — детерминированный SQL по golden record (`reference_query`), не вероятностный
  обход графа (риск тихих галлюцинаций в числах). **Граф НЕ запрещён** для настоящих граф-задач
  (сети связей/аффилированность контрагентов, большие BOM с разузлованием, genealogy партий) —
  он **отложен** до появления такой задачи и масштаба; тогда возможен полиглот (выделенная graph
  DB), а не рекурсивные CTE (концепция §4.4, «граница графов»). Для целей независимости граф —
  слой аналитики поверх уже консолидированных мастер-данных (после M2–M5), не на критическом пути.
- ❌ Не переносим склад/остатки из 1С в этой карте — истина склада остаётся за 1С до отдельного решения.
- ❌ Не делаем EAV-мега-таблицу атрибутов — JSONB-гибрид (концепция §4.3).
