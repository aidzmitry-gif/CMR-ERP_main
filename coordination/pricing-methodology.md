# Методика ценообразования и маржи (задача №0)

> Подготовлено 2026-06-24. Реализуемая спецификация поверх разбора [[sales-margin-analysis]]
> (анализ зафиксировал блокер; здесь — методика, на которую вешается код Горизонта-1).
> Цель платформы №1 — **рост валовой прибыли** = `цена продажи − landed cost`. Не оборот.
> Валюта продажи — **BYN**; закупка — USD/CNY. Денежные бизнес-правила (%, пороги) — за
> собственником (Харькович Д.С.), см. §7. Лестница лени соблюдена: §6 — минимальный первый срез.

---

## 1. Что эта методика отдаёт (контракт для остальных фич)

Любой экран/гардрейл, которому нужна маржа, получает по **строке SKU** три числа и вердикт:

```
unit_landed_cost   — себестоимость единицы в BYN на дату котировки (см. §3)
floor_price        — жёсткий минимум цены (ниже = стоп/эскалация РОП)
target_price       — ожидаемая цена (якорь плана и комиссии)
line_margin_byn    = (price − unit_landed_cost) × qty
line_margin_pct    = (price − unit_landed_cost) / price        # МАРЖА, не наценка
verdict            = green  если price ≥ target_price
                     yellow если floor_price ≤ price < target_price
                     red    если price < floor_price
```

Это единственный публичный контракт. Экраны (карточка, каталог, окно звонка, счёт) и
гардрейлы (give-get, апрув РОП) считают **только** из него — не дублируют формулы.

---

## 2. Определения (и где тут грабли)

- **Маржа ≠ наценка.** Наценка = `(price − cost)/cost`; маржа = `(price − cost)/price`.
  Наценка 50% → маржа 33%; наценка 100% → маржа 50%. **Везде в системе оперируем МАРЖОЙ** —
  цель сформулирована в марже, комиссия и floor — в марже. Наценку показываем только если
  попросят, рядом и подписью «наценка».
- **Margin-based, не cost-plus.** Цена считается обратно от целевой маржи:

  ```
  target_price = unit_landed_cost / (1 − target_margin_pct)
  floor_price  = unit_landed_cost / (1 − floor_margin_pct)
  ```

  Почему не «cost + фикс наценка»: при росте курса/фрахта фикс-наценка молча срезает маржу.
  Margin-based авто-поднимает пол при росте landed cost.
- **Три точки цены** (на SKU или категорию, §4):
  - **Floor** — `floor_margin_pct`, жёсткий минимум. Ниже — сделка не сохраняется без апрува РОП.
  - **Target** — `target_margin_pct`, плановый результат. Якорь pipeline-плана и комиссии.
  - **Aspirational** — потолок по ценности (опционально, для value-selling). На старте можно не хранить.

## 3. Landed cost — модель себестоимости

`unit_landed_cost` (BYN) — это закупочная стоимость единицы, доведённая до склада в Минске:

```
landed_cost = (purchase_price                # цена поставщика, USD/CNY
             + freight_alloc                 # фрахт, распределённый на единицу
             + customs_alloc                 # растаможка (пошлина + НДС невозмещаемый + сборы)
             + bank_other_alloc)             # банковские/брокерские/прочие
             × fx_rate                        # курс НБ РБ на дату фиксации (§3.2)
```

### 3.1 Источник истины
- **Источник cost — модуль закупок (procurement), read-only.** Последний закрытый PO по SKU →
  `unit_landed_cost` + `shipment_id` + дата. **Cross-schema soft ref** (без FK через схемы, §2.4 ядра):
  sales хранит снапшот значения, не джойнит таблицу закупок вживую.
- Если по SKU нет закрытого PO — `unit_landed_cost = null`, вердикт = `grey` («себестоимость неизвестна,
  цена вслепую»). Не подставлять 0 — это бы покрасило всё в зелёный и спрятало дыру.

### 3.2 FX и двухэтапность (P4 из анализа)
- Хранить **два курса**: на дату PO и на дату оплаты PO. `fx_rate` для котировки — текущий курс НБ РБ
  (общий модуль `sales-cur.js`/`currency_rate` уже есть, ведёт «Справочники»).
- **Estimated → Actual.** При приёмке landed cost = *estimated* (прайс поставщика + плановый фрахт/растаможка).
  По приходу счетов брокера/деммереджа (через 30–90 дн) → *actual*, маржа по уже котированным сделкам
  пересчитывается (снапшот на сделке остаётся как «маржа на момент продажи», рядом — «маржа по факту»).
- Если текущий курс ушёл от курса снапшота > **N%** (порог — §7) — флаг «себестоимость устарела, обнови
  перед ценой».

## 4. Data-модель (предложение — НЕ трогает общий `Sku`)

> ⚠️ Координация: поля целевой маржи логично было бы повесить на `core` `Sku`/категорию, но
> `core/domain/models.py::Sku` ведёт сессия **Справочники**. Чтобы не лезть в чужую полосу,
> **ценовая политика живёт в схеме `sales`** и ссылается на SKU/категорию мягко (по id, без FK).
> Если Справочники захотят — позже поднять `target_margin_pct` на уровень категории в reference;
> методика от этого не меняется (контракт §1 тот же).

### 4.1 `sales.pricing_policy` — целевые маржи
| Поле | Тип | Смысл |
|---|---|---|
| `id` | int pk | |
| `scope` | str(8) | `sku` / `category` / `default` (каскад: sku → category → default) |
| `ref_id` | int null | id SKU или категории (null для default) |
| `target_margin_pct` | numeric(5,4) | целевая маржа (0.30 = 30%) |
| `floor_margin_pct` | numeric(5,4) | минимальная маржа |
| `updated_by` / `updated_at` | | аудит правила (кто менял пол — деньги) |

Разрешение цены: ищем policy по sku → если нет, по category → если нет, default. Так не нужно
заводить строку на каждый SKU; собственник задаёт дефолт + переопределения по флагманам.

### 4.2 `sales.deal_margin_snapshot` — маржа на момент сделки (P3/единый источник)
Снимок на ключевых событиях (КП, счёт): `deal_id, sku_id, qty, price, unit_landed_cost,
target_price, floor_price, fx_rate, line_margin_byn, line_margin_pct, concession_type, ts`.
План маржи (`margin-by-month`, РОП-«Деньги») и факт тянутся **отсюда**, не из JSON-копий.

### 4.3 `landed_cost_snapshot` на документе (P1 реестра)
На счёте/КП фиксируется landed cost на момент выставления → документ становится доказательством
маржи; правка документа не теряет старую маржу (она в версии). См. [[sales-margin-analysis]] §5.

## 5. Алгоритм расчёта цены (псевдокод, чистая арифметика — без ML)

> **Ключ номенклатуры — `sku_code` (строка)**, не `sku_id`: так требует существующий шлюз
> `core.services.stock` и 1С (источник истины номенклатуры по коду). Подробности — [[procurement-costing-handoff]] §3.

```python
def quote_line(sku_code, qty, price):
    row = core.services.landed_cost.last_landed_cost(session, sku_code)  # read-only фасад ядра, BYN
    if row is None:                                    # нет закрытого PO — НЕ подставлять 0
        return Line(verdict="grey", reason="нет закрытого PO — себестоимость неизвестна")
    cost = row["unit_landed_cost_byn"]                 # + shipment_id/fixed_at/fx_* для снапшота
    pol = pricing_policy.resolve(sku_code)             # sku → category → default
    target_price = cost / (1 - pol.target_margin_pct)
    floor_price  = cost / (1 - pol.floor_margin_pct)
    margin_byn = (price - cost) * qty
    margin_pct = (price - cost) / price if price else 0
    verdict = ("green" if price >= target_price else
               "red"   if price <  floor_price  else "yellow")
    return Line(cost, target_price, floor_price, margin_byn, margin_pct, verdict)
```

Округление цены — по правилу собственника (§7); маржа считается до округления, отображается после.
Скидка/give-get и апрув РОП — отдельные фичи (P2), они вызывают `quote_line` и реагируют на `verdict`.

## 6. Минимальный первый срез (лестница лени — что строить №1)

Чтобы маржа стала видна продавцу **без** ожидания всей методики:
1. `sales.pricing_policy` только со `scope='default'` (один target%/floor% на всё) +
   `procurement.last_landed_cost(sku_id)` (read-only). ← минимум, чтобы `quote_line` заработал.
2. `quote_line` как чистая функция + юнит-тесты (маржа vs наценка, grey при null cost, пороги verdict).
3. Показ `line_margin_pct` + цветокод **по строке** на карточке сделки (P1). Один экран, один источник.

Всё остальное (per-category переопределения, estimated→actual, FX-флаг, give-get, комиссия) — поверх,
когда §7 даст числа. Снапшоты (`deal_margin_snapshot`) заводить сразу — иначе план/факт негде взять.

## 7. Решения за собственником (Харькович Д.С.) — без них методика не запускается

Методика — это формула; **числа и политики — бизнес-решения**, их нельзя выдумать:

1. **Дефолтная целевая маржа %** и **floor %** (анализ-ориентир: импорт из Китая 35–50% маржи; floor
   часто = точка безубыточности + минимальная отдача). Нужны конкретные числа на старт.
2. **Переопределения по категориям/флагманам** — где маржа выше/ниже дефолта (например, microchips.by).
3. **Состав landed cost** — что точно входит в «растаможку» и «прочее» (НДС возмещаемый исключаем?
   деммередж, СВХ, страховку, сертификацию — включаем?).
4. **Порог FX N%** для флага «себестоимость устарела» (например, 3%).
5. **Правило округления** цены продажи (до копейки / до рубля / прайс-лист «красивых» цен).
6. **Кто и как часто** правит `pricing_policy` (РОП? собственник? пересмотр floor — квартально?).
7. **Тиринг комиссии от маржи** (P5): ставки при ≥Target / Floor–Target / <Floor (ориентир 100/70/0%).

> До получения §7.1–7.3 первый срез (§6) можно собрать на **плейсхолдер-числах** (помеченных
> `# TODO(owner): подтвердить`), чтобы код и тесты были готовы — но в прод/демо с реальными
> сделками не выкатывать, пока числа не подтверждены.

## 8. Что НЕ строить (YAGNI)
- Эмбеддинги/ML для маржи — это арифметика `(price−cost)/price`.
- Price-waterfall дашборд (list→invoice→pocket) на старте — сначала видимость маржи на строке (§6).
- Хранить наценку как отдельную сущность — выводится из маржи.
- Строку `pricing_policy` на каждый SKU заранее — каскад sku→category→default закрывает это.
