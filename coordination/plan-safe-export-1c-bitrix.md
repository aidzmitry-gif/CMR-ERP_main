# План безопасной выгрузки 1С + Bitrix24

> **Статус:** утверждён к исполнению (обновлён 2026-07-07: каденция контактов с клиентами).  
> **Создан:** 2026-07-06.  
> **Контекст:** коннекторы `connectors/`, стратегия `coordination/erp-replace-bitrix-1c-strategy.md`.

---

## Цель

Безопасно выгрузить данные из **1С (OData)** и **Bitrix24 (REST)** в `data/inbox/*.json` (+ MP3 в `data/media/`), без бана API и с возможностью продолжить после сбоя.

**В scope данных:** контрагенты, CRM, номенклатура, продажи по SKU, закупки, цены, остатки — для маржи, оборачиваемости, min/max запасов и **каденции контактов** (когда звонить постоянному клиенту).

**Не в scope:** загрузка в ERP/MDM; готовые отчёты (маржа, min/max, **«пора связаться»**) — фаза 7 поверх inbox.

---

## Покрытие данных: маржа, номенклатура, объёмы

Ни Bitrix, ни 1С OData **не отдают готовое поле «маржа %»**. Маржа в ERP считается как:

```
маржа = цена продажи − landed cost (себестоимость с фрахтом/пошлиной)
```

## Покрытие данных: оборачиваемость и min/max запас

Целевые нормативы (решение владельца):

| Параметр | Значение | Смысл |
|----------|----------|-------|
| **Min запас** | **2–3 месяца** продаж | ниже — риск дефицита, срочный заказ |
| **Max запас** | **4–5 месяцев** продаж | выше — замороженные деньги, перезатар |

По умолчанию в расчёте: **min = 2,5 мес**, **max = 4,5 мес** (середина диапазона; настраивается).

### Методика расчёта (фаза 7, скрипт)

**Входные данные из inbox:**

1. `Document_РеализацияТоваровУслуг_Товары` — продажи по SKU за период
2. `AccumulationRegister_ТоварыНаСкладах` — текущий остаток (снапшот на дату выгрузки)
3. `Catalog_Номенклатура` — код, название, ед.изм.
4. *(опц.)* `Document_ЗаказПоставщику` / ERP procurement — «в пути» для нетто-потребности

**Окно анализа продаж:** последние **12 месяцев** (или весь доступный период в ka_copy с пометкой «укороченная база»).

```
среднемесячный_расход_шт = SUM(продано_шт за период) / кол_во_месяцев

min_шт = среднемесячный_расход × MIN_MONTHS     # MIN_MONTHS = 2…3 (дефолт 2.5)
max_шт = среднемесячный_расход × MAX_MONTHS     # MAX_MONTHS = 4…5 (дефолт 4.5)

оборачиваемость_раз_в_год = (среднемесячный_расход × 12) / средний_остаток_шт
оборачиваемость_дней       = 365 / оборачиваемость_раз_в_год
запас_дней                 = текущий_остаток / (среднемесячный_расход / 30)

нетто_к_заказу = max(0, max_шт − текущий_остаток − в_пути)
```

**Статус по SKU:**

| Условие | Статус |
|---------|--------|
| остаток < min_шт | `deficit` — дефицит |
| min_шт ≤ остаток ≤ max_шт | `ok` |
| остаток > max_шт | `overstock` — перезатар |
| продаж за период = 0 | `no_demand` — не считать min/max (или вручную) |

**Ограничения:**

- Сезонные SKU — при необходимости считать по тем же месяцам прошлого года (v2).
- Средний остаток: если нет истории остатков — для оборачиваемости использовать **текущий** остаток (грубо, пометить в отчёте).
- Связь с S&OP / окнами закупок: `coordination/DEPENDENCY-MAP.md` §2c — `sales.demand.requirement` = потребность − остаток − в пути + буфер.

## Покрытие данных: каденция контактов с клиентами

**Нет единого «раз в N дней для всех».** Частота — **индивидуальный цикл заказов** каждого постоянного клиента (макет SALES-48, `sales-regular-clients.html`).

### Нормативы касаний (решение владельца)

| Событие | Когда | Параметр |
|---------|-------|----------|
| **Пора связаться** | за **7 дней** до ожидаемого перезаказа | `CONTACT_LEAD_DAYS=7` |
| **Просрочка** | ожидаемая дата заказа прошла | эскалация РОПу |
| **После won** | **+7 дней** | контроль качества / доставки |
| **Перед перезаказом** | за lead-time до `next_expected_order` | подтверждение объёма |
| **Новый клиент** (нет истории) | ориентир **60–90 дней** | до накопления ≥2 заказов |
| **Активная сделка** | **5+ дней без действий** | сигнал РОПу (воронка, не постоянные) |

### Методика расчёта (фаза 7в, скрипт)

**Входные данные:**

1. `Document_РеализацияТоваровУслуг` — даты отгрузок по `Контрагент_Key` (или аналог)
2. `Catalog_Контрагенты` — имя, УНП
3. Bitrix: `voximplant.statistic.get` + `crm.activity.list` — `last_contact` по клиенту
4. *(опц.)* won-сделки Bitrix — дата последней победы

**Минимум заказов для расчёта цикла:** ≥ **2** реализации; иначе статус `new_client`, дефолт 75 дней.

```
даты_заказов[] = даты Document_Реализация по контрагенту (сортировка ASC)
интервалы[]    = разница между соседними датами (в днях)
cycle_days     = median(интервалы[])          # медиана, не среднее (устойчивее к выбросам)

last_order     = max(даты_заказов)
next_expected  = last_order + cycle_days
contact_from   = next_expected − CONTACT_LEAD_DAYS

дней_до_контакта = contact_from − сегодня
дней_просрочки   = сегодня − next_expected   # если > 0
```

**Статус клиента (для сортировки «кому звонить раньше»):**

| Условие | Статус | Цвет | Действие |
|---------|--------|------|----------|
| `дней_просрочки > 0` | `overdue` | 🔴 | Связаться срочно, передать РОПу при риске |
| `0 ≤ дней_до_контакта ≤ CONTACT_LEAD_DAYS` | `due_soon` | 🟡 | Позвонить, подтвердить объём, перезаказ |
| `дней_до_контакта > CONTACT_LEAD_DAYS` | `in_cycle` | 🟢 | В цикле, не срочно |
| заказов < 2 | `new_client` | — | Ручной режим / дефолт 60–90 дн |
| нет заказов за 24 мес | `churn_risk` | 🔴 | Реактивация |

**Сверка с фактом контакта:**

```
дней_с_контакта = сегодня − last_contact   # из Bitrix
если status=in_cycle и дней_с_контакта > cycle_days → пометка «давно не общались»
```

### Выход фазы 7в (отчёт по контрагентам)

| Колонка | Описание |
|---------|----------|
| `counterparty`, `unp` | клиент |
| `orders_count`, `last_order_date` | история |
| `cycle_days`, `cycle_label` | «~90 дн» |
| `next_expected_order` | ожидаемый перезаказ |
| `contact_from_date` | с какой даты пора звонить |
| `status` | overdue / due_soon / in_cycle / new_client / churn_risk |
| `last_contact`, `days_since_contact` | из Bitrix |
| `avg_check`, `trend` | опц., из сумм реализаций |
| `action` | Связаться / Перезаказ / — |

**Сортировка по умолчанию:** просрочка → пора связаться → в цикле (как в макете постоянных клиентов).

**Приёмник в ERP (позже):** экран «Постоянные клиенты» (SALES-48), авто-задачи `on_deal_won` (+7 дн, перезаказ), фасад `touch_history` уже есть — дополнить полями `cycle_days`, `next_expected_order`.

```

```

## Фаза 6 — Верификация (день, ~2–3 ч)

### Общее

| Проверка | Критерий |
|----------|----------|
| Полнота | count в inbox ≈ smoke `total` (±5%) |
| ID-диапазон | min/max ID в выгрузке = min/max на портале |
| Ошибки | 0 необработанных `QUERY_LIMIT_EXCEEDED` |
| State | курсоры в `state.json` актуальны |
| Дубли | `unit_id` уникален |
| Медиа | % звонков со скачанным MP3 |

### Товарная аналитика

| Проверка | Критерий |
|----------|----------|
| Номенклатура | count ≈ smoke `Catalog_Номенклатура` |
| Строки реализации | есть связка `Номенклатура_Key` → справочник |
| Поступления | закупочные суммы на те же SKU, что в реализациях (выборочно) |
| Productrows | ≥1 строка на большинство сделок с товарами |
| Цены | регистр цен не пустой за последний год |
| Остатки | снапшот `ТоварыНаСкладах` покрывает SKU из реализаций (выборочно) |
| Min/max (выборка) | для 5 SKU вручную: min ≈ 2,5× ср.месяц, max ≈ 4,5× ср.месяц |

### Каденция контактов

| Проверка | Критерий |
|----------|----------|
| Реализации с датой | ≥2 заказа у выборочных постоянных клиентов |
| Цикл (выборка) | медиана интервалов близка к макету (45–120 дн) |
| Статусы | есть overdue / due_soon / in_cycle |
| last_contact | звонки/активности привязаны к контрагенту (Bitrix) |

## Фаза 7 — Аналитика после выгрузки (опц., день, ~4–5 ч)

**Не коннектор** — скрипт(ы) поверх `data/inbox/` (CSV / загрузка в ERP).

### 7а. Маржа

| Метрика | Источник |
|---------|----------|
| Продано шт по SKU | `SUM(Количество)` из `Реализация_Товары` |
| Выручка по SKU | `SUM(Сумма)` |
| Себестоимость ед. | последнее поступление или landed cost |
| Маржа % | `(выручка − себестоимость) / выручка` |
| Топ маржинальных | сортировка по `маржа × объём` |

### 7б. Оборачиваемость и min/max запас

```bash
MIN_MONTHS=2.5    # диапазон 2–3
MAX_MONTHS=4.5    # диапазон 4–5
SALES_WINDOW_MONTHS=12
```

| Метрика | Формула |
|---------|---------|
| Min / Max шт | ср.месяц × 2,5 / 4,5 |
| Оборачиваемость | (ср.месяц × 12) / остаток |
| К заказу | `max(0, max − остаток − в_пути)` |

### 7в. Каденция контактов с клиентами

```bash
CONTACT_LEAD_DAYS=7       # за сколько дней до ожидаемого заказа звонить
DEFAULT_CYCLE_DAYS=75     # для new_client без истории (60–90)
MIN_ORDERS_FOR_CYCLE=2    # минимум заказов для медианы
CHURN_MONTHS=24           # без заказов → churn_risk
```

| Метрика | Формула / источник |
|---------|-------------------|
| `cycle_days` | median(паузы между реализациями) |
| `next_expected_order` | last_order + cycle_days |
| `contact_from` | next_expected − CONTACT_LEAD_DAYS |
| `status` | overdue / due_soon / in_cycle / new_client / churn_risk |
| `last_contact` | max(звонок, activity) из Bitrix |

**Приоритет отчёта:** 🔴 просрочка → 🟡 пора связаться → маржа×объём (кто важнее не потерять).

Согласовать: маржа — `pricing-methodology.md`; min/max — S&OP (`DEPENDENCY-MAP.md` §2c); каденция — РОП / SALES-48.

## Правила «не забанить»

| | Тест (Фаза T) | Полный прогон |
|---|---------------|---------------|
| **Bitrix** | ≤35 запросов, днём OK | 1 req/сек, 1 поток, batch ≤50 |
| **1С** | ≤10 запросов | `$top=500`, 3 сек между entity sets |
| **При 429/5xx** | стоп, разобраться | backoff 2→60 сек; пауза 30 мин (Bitrix) / 15 мин (1С) |
| **State** | отдельный `state.test.json` | не сбрасывать боевой state |
| **Окно** | любое | 22:00–07:00 МСК |
| **Запись** | только read | никаких add/update/delete |

### При блокировке

1. Немедленно остановить скрипт (state сохранён на последней записи).
2. Подождать 30 мин (Bitrix) / 15 мин (1С).
3. Продолжить с того же state — **не начинать заново**.
4. При повторе — снизить темп вдвое, перенести на следующую ночь.
5. При бане вебхука — создать новый (только read), старый не трогать.
