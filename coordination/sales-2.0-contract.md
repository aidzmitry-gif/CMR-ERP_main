## 2. Документооборот (ФАЗА 2, ядро ценности)

Принцип (из макетов, подтверждён заказчиком): **документы не удаляются — только помечаются**;
помеченный нельзя отправить; правка = новая версия (прежняя в историю); безвозвратное
удаление — в отдельном модуле вне CRM (право `doc_admin`).

**Модель — дельта к `DealDocument`:**
- `kind`: добавить `work_order` (заказ-наряд, ЗН-NNNN). Текущие: invoice|contract|order.
- `marked_for_deletion: bool` + `marked_at`/`marked_by`/`mark_reason`.
- `version: int` (текущая версия документа).

**Новая модель `DealDocumentVersion`** (история версий):
`id, document_id(FK), version, snapshot(JSONB/Text), label, created_at, marked_for_deletion`.

**Роуты (новые):**
- `POST /documents/{id}/mark` / `/unmark` — пометить/снять (пишет mark_*).
- `POST /documents/{id}/revise` — правка → архивирует текущую в version, version++.
- блокировка: send/decide помеченного → 409.
- `GET /docs-trash` + `POST /docs-trash/{id}/purge` — вне CRM, право `doc_admin`
  (заменяет localStorage-демку `sales-docs-purge.html`).

## 6б. Раскладка моделей и режимов исполнения (подтверждено 2026-06-15)

Принцип: **Опус** — где цена ошибки высокая и контекст широкий (архитектура, оркестрация,
миграции данных, тонкая логика). **Соннет** — где задача узкая и проверяемая (порт макета,
CRUD по образцу, тест по шаблону). **Воркеры всегда на Соннете** (дёшево, изолированный
scope + LOOP-контракт + node/Playwright-аудит ловят регресс). **Оркестратор — Опус**.

| Фаза | Задача | Режим | Модель | Почему |
|---|---|---|---|---|
| 0 | Контракт ТЗ | простая сессия | **Опус** | широкий контекст, решения на годы |
| 1 | Стадии 6→9 + dedup | простая сессия | **Опус** | завязки в чужих сессиях, маппинг |
| 1 | Миграция данных Alembic | простая сессия | **Опус** | необратимый UPDATE данных |
| 2 | Док-модель+версии+purge | оркестр.→воркеры | оркестр.**Опус** / воркеры **Соннет** | спроектировать на Опусе, разбить на ≤3 непересек. воркера |
| 3 | Порт макетов в Next.js | оркестр.→воркеры | оркестр.**Опус** / воркеры **Соннет** | 1 воркер = 1 экран (доска/карточка/звонок/постоянные) |
| 3 | CRUD задач (DealTask) | простая сессия | **Соннет** | модель готова, роуты по образцу |
| 4 | on_deal_won + постпродажа | простая сессия | **Опус** | межмодульная логика, дыра в событиях |
| 5 | Конструктор плана | оркестр.→воркеры | оркестр.**Опус** / воркеры **Соннет** | калькулятор-декомпозиция + согласование |
| 5 | Статус машины (read-only) | простая сессия | **Соннет** | только чтение чужого события |

Запуск воркеров на Соннете: `WORKER_*` / флаг модели в spawn_workers.py (по умолчанию
наследует; для Соннета указать явно). Оркестратор держит контекст на Опусе, отвечает на
блокеры воркеров, интегрирует. См. skill `orkestrator-lead`, [[orchestrator-integrate-gotcha]].

## 5б. Карточка номенклатуры (товара) — ВЛАДЕЕТ «Справочники» (МДМ), не sales

**Решение 2026-06-15:** UI-карточку номенклатуры (SKU) делает сессия «Справочники»
(модуль reference-data / МДМ), НЕ sales. Макет `sales-product-card.html` УДАЛЁН из
полосы sales (история в git `172bbe9`, при необходимости восстановить оттуда).
Поля карточки (фото товар/упаковка, цена прошлая→текущая + история, остатки по складам
с ячейкой и «в пути», габариты/вес/упаковка, проверка у поставщика, ТН ВЭД, ед.изм.,
группа, артикул, штрихкод, описание, спеки) — всё это атрибуты SKU, которыми владеют
«Справочники» (`Sku.attributes` JSONB, `category_id`, эндпоинты reference-data).
**sales только ССЫЛАЕТСЯ** на карточку: каталог-подбор (`sales-catalog-picker.html`)
по клику «ℹ карточка» ведёт в карточку «Справочников» (пока маршрута SKU-карточки нет —
честный toast-указатель). Продажная обёртка (цена клиенту — PriceQuote) остаётся в sales.

## 5в. Каталог-подбор + ИИ-подбор товара

Макет `sales-catalog-picker.html`. Каталог структурирован для быстрого поиска:
группы + чипы-фасеты со счётчиками, поиск по названию/артикулу/штрихкоду, фильтр
склад/наличие, теги-параметры (`tags`: тип техники, вольтаж, ёмкость, применимость).
**ИИ-подбор**: скрипт вопросов (техника/потребность/бюджет/срочность) — ответы
вводятся вручную ИЛИ подтягиваются из транскрибации разговора (кнопка «↓ из
разговора»); свободная строка запроса; при слабом сигнале ИИ задаёт уточнение.
Матчер ранжирует по совпадению тегов + бюджет + наличие, выдаёт рекомендации с
обоснованием и кнопкой «＋ в счёт». В макете — детерминированная эвристика; в
проде — LLM-шлюз `core.services.llm` (feature-flag `AIOS_AI_ENABLED`) поверх
read-only атрибутов SKU. Тот же подбор уместен в окне звонка (по ответам клиента).

## 6. Что НЕ дублировать (читать из чужих модулей)

- **Статус машины** — источник логистика (`shipment.status.changed`). Sales только читает.
- **Landed cost / ETA** — из закупок/логистики. План прибыли по месяцам берёт оттуда.
- **РОП-план** — база РОПа для согласования; конструктор плана продавца сверяется с ней.
