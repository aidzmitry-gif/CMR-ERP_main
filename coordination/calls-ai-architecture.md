# Звонки + AI: архитектура от сбора до помощи продавцу

> Исследование по итогам теста РИФТЭК (2026-06-23): 73 звонка, 69 записей скачаны
> (2019–2026, ротации НЕТ), 6 расшифрованы faster-whisper, инсайты извлечены AI.
> Цель: полная история клиента + помощь продавцу + скрипты звонков, интегрировано в ERP.

## 1. Конвейер (один фундамент — четыре продукта)

```
Bitrix телефония        Сбор            ASR              AI-извлечение        Хранилище        Продукты
────────────────        ─────           ───              ─────────────        ─────────        ────────
voximplant.statistic ─► звонок+метадан ─► faster-whisper ─► структура звонка ─► comm_call    ─► 1) История 360
RECORD_FILE_ID       ─► скачать mp3   ─► (GPU, large-v3) ─► (локальная LLM)  ─► comm_insight ─► 2) AI-переговоры
                        привязка к      ─► диаризация      ─► привязка к       ─► link:          3) Коучинг
                        клиенту по теле    (кто говорит)      Counterparty/Deal   Counterparty    4) Скрипты
```

**Стадии:**
1. **Сбор** — коннектор `bitrix.py` (`fetch_calls`): `voximplant.statistic.get` + `_download_record` (RECORD_FILE_ID → disk.file.get → mp3). Уже работает.
2. **Привязка к клиенту** — по `PHONE_NUMBER` → контакт → компания → УНП → `Counterparty`; либо по `CRM_ENTITY_ID/TYPE`. (Тест РИФТЭК: нашли 73 звонка по телефонам контактов.)
3. **ASR** — faster-whisper. Тест: `small/int8` на CPU хватило для коротких звонков. Прод: `large-v3` на **серверном GPU** (готовит пользователь). Желательна **диаризация** (кто менеджер, кто клиент) — pyannote/whisperx.
4. **AI-извлечение** — структура из речи (см. §3). Прод: **локальная LLM** (privacy-shield, LM Studio/Qwen) — звонки с PII НЕ уходят в чужое облако.
5. **Хранение** — таблицы `comm_call` + `comm_insight`, FK на `Counterparty`/`Deal`/`User` (ядро уже имеет эти сущности).

## 2. Интеграция в ERP (модуль)

- Новый модуль-плагин `communications` (или расширить существующий) по паттерну проекта (ModuleContract, схема БД, миграция).
- Таблицы (схема `communications`):
  - `comm_call`: id, source(bitrix), external_id, counterparty_id(FK), contact_id, user_id(менеджер), deal_id?, started_at, duration, direction, phone, record_path, transcript(text), transcript_status.
  - `comm_insight`: id, call_id(FK), category(target_client/supplier/...), value(high/med/low), summary, client_needs(jsonb), objections(jsonb), agreements(jsonb), next_steps(jsonb), rep_advice(text), risk(text), products(jsonb).
- Связи (через ядро, не в обход): `Counterparty` (golden record по УНП — см. [[client-360-bitrix-1c]]), `Deal`, `User`.
- Воркер-демон: периодический синк (звонки → скачать → очередь ASR → извлечение → запись). ASR-очередь отдельно (GPU-узел).

## 3. Схема извлечения (что AI достаёт из речи — чего НЕТ в полях CRM)

Подтверждено на РИФТЭК: из звонков извлекается то, что в CRM отсутствует:
- **Профиль закупок**: что покупает, модели, чувствительность к цене/качеству.
- **Паттерн**: РИФТЭК = «2 на пробу → тест → 60-100 при успехе». Это сигнал к апселлу.
- **Текущее состояние сделки**: статус оплаты, договорённости, сроки забора.
- **Риски/трения**: путаница в документах (счёт-протокол), реакция на текучку менеджеров, претензии к качеству образцов.
- **Совет продавцу (rep_advice)**: конкретные действия к следующему контакту.

## 4. Удобный просмотр по клиентам (UX)

- **Карточка клиента 360°** (прообраз — `riftek-360.html`): шапка (УНП, тип, LTV) → KPI → единая лента Bitrix×1С → AI-сводка → бриф продавцу → лента звонков с расшифровкой.
- В ERP это вкладка карточки контрагента: «История 360°». Данные из нашей БД (не live-запросы в 1С/Bitrix — см. решение об архитектуре: данные оседают у нас).
- Фильтры: по продукту, по менеджеру, по периоду; поиск по тексту расшифровок (full-text / RAG).

## 5. Помощь продавцам (4 сценария)

1. **Бриф перед звонком** — авто-сводка: кто клиент, что покупал, открытые сделки, риски, что предложить. (Показано в карточке РИФТЭК.)
2. **AI-ассистент в переговорах** — RAG по истории клиента + подсказки в реальном времени/после звонка.
3. **Коучинг** — скоринг звонка: выявил потребность? обработал возражение? назначил next step? Динамика по продавцу. Сравнение с эталоном.
4. **Скрипты из реальных звонков** — анализ корпуса «выиграл vs слил» → паттерны успешных реплик → генерация/обновление скриптов. Требует накопленного размеченного корпуса (делать после фундамента).

## 6. Масштаб (144 033 звонка на портале)

- НЕ транскрибировать всё подряд. Приоритет: целевые клиенты + свежие + с записью.
- Инкремент по курсору ID (коннектор уже умеет) — новые звонки добираются автоматически.
- Backfill: на этом портале записи НЕ ротируются (проверено на РИФТЭК 2019-2026) — срочности нет, но история доступна полностью.
- GPU-throughput определяет, как быстро разгребём корпус. На серверном GPU large-v3 — основной прогон.

## 7. Приватность (приоритет №2 конституции)

- Звонки = PII клиентов. ASR и извлечение — **локально** (свой сервер/GPU, локальная LLM), не в чужое облако.
- Для теста РИФТЭК извлечение делал Claude (по явной просьбе показать результат) — это исключение теста, не прод-режим.
- В проде — privacy-shield (см. [[olivia-privacy-shield-split]]): локальная модель детектит/заменяет PII, наружу уходят только плейсхолдеры, если вообще уходят.

## 8. Открытые решения (нужны от пользователя)

1. Диаризация (кто менеджер/клиент) — ставим pyannote/whisperx или достаточно без неё? (Без неё текст «слипается», но смысл извлекается — видно на РИФТЭК.)
2. Локальная LLM для извлечения в проде — Qwen на сервере (как у Оливии) или отдельная.
3. Когда переносим прототип в модуль `communications` ERP — после теста или сразу.
4. Объём первого боевого прогона на GPU (целевые клиенты — сколько).
