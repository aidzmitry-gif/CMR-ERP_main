# Шов сессий вокруг 1С/MDM + класс-разделение данных

> Назначение: чтобы сессии «Справочники», CRM/Сделки, Склад/WMS и интеграции имели
> ОДИН контракт на потоки 1С→MDM и не дрались за полосы. Дополняет (не заменяет):
> [onec-bidirectional-sync-plan.md](onec-bidirectional-sync-plan.md),
> [onec-contractors-audit.md](onec-contractors-audit.md),
> [spravochniki-mdm-research.md](spravochniki-mdm-research.md),
> [reference-independence-roadmap.md](reference-independence-roadmap.md).
> Память: `onec-bidirectional-erp-truth`, `spravochniki-mdm-decision`, `onec-cache-to-mdm-bridge`.

## TL;DR

**Один golden record — один адаптер на вход — много РАВНОПРАВНЫХ читателей.**
Справочники — это **витрина** над общим MDM, а НЕ хранилище и НЕ источник, из которого
«CRM копирует». CRM и Склад читают MDM **напрямую** (shared-kernel / `core.services`),
а не «через справочники». Никакого второго хранилища (анти-паттерн MDM).

## 1. Класс-разделение данных (половина успеха интеграции)

| | Мастер-данные | Операционные |
|---|---|---|
| Что | контрагенты, номенклатура | остатки, цены, себестоимость, резервы |
| Натуральный ключ | УНП / код SKU | (SKU, склад) на момент времени |
| Истина (фаза 1) | 1С → ERP (станет ERP в фазе 2) | **1С / Склад** |
| Слияние | survivorship + провенанс + SCD2 + **иерархия филиалов** | снимок, перезапись |
| Адаптер на вход | `reference_import.import_counterparties` (ядро) | `integrations.stock_item` |
| Витрина / чтение | **Справочники** (витрина), CRM (контрагент по УНП) | Склад (наличие), CRM (наличие в сделке) |
| Шлюз чтения | shared-kernel `Counterparty`/`Sku` | `core.services.stock` |

⚠️ **Остатки — НЕ мастер-данные.** Не класть их в «справочники»: другой жизненный цикл,
другой владелец (Склад/1С), высокая частота, без survivorship. Отдельная полоса.

## 2. Кто какой СЛОЙ владеет (шов по слою, не по папке)

| Слой | Владелец-сессия | Контракт-граница |
|------|-----------------|------------------|
| Коннектор 1С (`OneCClient`, `sync_1c`), проводка | **Справочники** (см. ACTIVE-SESSIONS стр. 36) | отдаёт `[{name,unp,id}]` в → |
| Адаптер MDM (`reference_import`, `mdm`, `survivorship`) | ядро (правит Справочники) | golden record по УНП + alias-провенанс |
| Витрина + governance (категории, SCD2, is_active, мердж дублей) | **Справочники** | `/system/references/query`, `/system/mdm/*` |
| Остатки/резервы | **Склад/WMS** + интеграции | `core.services.stock` (`StockGateway`) |
| Доска/карточка сделки | **CRM/sales** (submodule) | читает `Counterparty`/`Sku` + stock-шлюз |

**CRM в момент сделки = два РАЗНЫХ запроса:** «кто клиент» → MDM-контрагент по УНП;
«есть товар и какая маржа» → Склад/остатки через `core.services.stock`. Не через справочники.

## 3. Хэндофф: мост «кэш 1С → MDM» (готов, отдаю Справочникам)

Сессия CRM (хаб) реализовала и **доказала** мост чтения реального кэша 1С в MDM, но он
лёг в **полосу Справочников** + хотспот — поэтому отдаю на абсорбцию, не претендую:

- **Изменено 3 файла (uncommitted, в общем worktree):**
  `modules/integrations/client.py` (**ваша полоса**), `config/settings.py` (**хотспот крипто**),
  `modules/integrations/module.py`.
- **Что делает:** `OneCClient(cache_dir)` читает `data/inbox/onec_*.json`, проецирует
  `Catalog_Контрагенты` → `{name←Description, unp←ИНН, id←Ref_Key}` (пропуская пустой УНП и
  DeletionMark); аддитивно (пусто → старый mock). Включение: `AIOS_ONEC_CACHE_DIR=data/inbox` +
  `POST /integrations/1c/sync`.
- **Доказано:** прогон `sync_1c` на свежей SQLite → **4109** golden по УНП + **4228** alias,
  провенанс `1c`. Mock-тесты зелёные. Линт чист.
- ⚠️ **Внимание на правило склейки** ([onec-contractors-audit.md](onec-contractors-audit.md)):
  мой ридер честно отдаёт ВСЕ строки; схлопывание по УНП делает downstream `import_counterparties`
  (ядро). Сейчас оно **схлопывает в лоб**, что НЕВЕРНО для 27 семей «голова+филиалы»
  (их моделировать иерархией через `ГоловнойКонтрагент_Key`, не мерджить). Это ваш backlog по MDM —
  ридер ему не мешает, но включать массовый синк имеет смысл ПОСЛЕ иерархии филиалов.

**Решение по этим 3 файлам — за оператором:** (а) Справочники абсорбируют диф к себе и коммитят
в своей полосе, либо (б) CRM-сессия откатывает правки, отдав только эту спеку. По умолчанию — (а).

## 4. РЕШЕНИЯ ОПЕРАТОРА (2026-06-27, зафиксировано) — действуют для всех 4 сессий

> Принято после сверки §5 (хотспоты) + §7 п.2 (кто рождает контрагента) при 4 параллельных
> сессиях: Справочники, Синхронизация 1С/Битрикс, CRM/Sales, Закупки.

1. **`modules/integrations/*` (коннектор `OneCClient`, `sync_1c`, ридер кэша 1С `client.py`,
   Битрикс-коннекторы) — владеет СИНК-СЕССИЯ (1С/Битрикс).** Уточняет §2 (раньше проводка
   числилась за Справочниками) — теперь весь `integrations/*` за синк-сессией. Справочники
   коннектор НЕ трогают: только MDM-адаптер на вход в ЯДРЕ (`core.services.reference_import`,
   `mdm`, `survivorship`) + витрина/governance. Граница: синк отдаёт `[{name,unp,id}]` →
   `reference_import` (ядро, полоса Справочников).
   ⇒ Хэндофф из §3 (3 uncommitted-файла) **остаётся у синк-сессии**, Справочники их не абсорбируют.

2. **Контрагента «рождают» И Справочники, И CRM — но ТОЛЬКО через единый MDM-сервис ядра**
   (`reference_import`/`mdm`): golden record по УНП + дедуп/survivorship. Разные кнопки «Создать»
   в UI (каталог справочников И карточка сделки), но ОДИН путь записи в `Counterparty` — никто
   не пишет в shared-kernel `Counterparty` напрямую в обход MDM-сервиса. Это снимает гонку
   Справочники↔CRM за `core/domain/models.py:Counterparty` (хотспот §5).
   ⇒ CRM-сессия: кнопка «Создать» в сделке зовёт `core.services.mdm`/`reference_import`, не
   прямой `session.add(Counterparty(...))`.

**Счётчик миграций на момент решения:** актуальный head = **0054** (Справочники, поля группы
по умолчанию). Следующий свободный для любой сессии — **0055+** (брать от head, не угадывать, §6).

## 5. Backlog MDM-импорта 4766 контрагентов 1С — кавеаты и разделение (2026-06-27)

> Сверено с кодом (`core/services/reference_import.py`) и аудитом
> ([onec-contractors-audit.md](onec-contractors-audit.md), 4766 записей). Уточняет, что НЕ писать
> заново, что блокер, что чужая полоса. Массовый забор — ПОСЛЕ закрытия блокеров.

**Что УЖЕ есть (не писать заново, полоса Справочники/ядро):**
- `reference_import.import_counterparties(session, rows, source)` — пакетный идемпотентный upsert
  (`reference_import.py:122`); матч по УНП, alias-провенанс, survivorship по полям. Готово.
- `upsert_counterparty` — одна запись; требует УНП (`:86 raise` если пусто).
- `_IMPORT_FIELDS=("name",)` (`:23`) — расширять ТОЛЬКО вместе с моделью `Counterparty`
  (сейчас модель = `name/unp/provenance`; новые мастер-поля = миграция + хотспот `models.py`).

**Что ЧУЖОЕ (синк-сессия, `modules/integrations/*`):**
- Загрузчик `data/inbox/onec_*.json → rows[{unp,name,external_ref}]` — ридер кэша, НЕ моя полоса.
  Отдаёт строки в `import_counterparties` (граница). Уже прототип в `integrations/client.py` (синк-сессия).

**Блокеры массового забора (нельзя включать `sync` на 4766 до закрытия):**
1. **🔴 Иерархия филиалов.** `mdm.match_candidates` матчит по УНП в лоб → 105 филиалов (27 семей)
   схлопнутся в голову — НЕВЕРНО. Правило (audit §65): при совпадении УНП смотреть
   `ГоловнойКонтрагент_Key` — есть связь голова↔филиал ⇒ ИЕРАРХИЯ (1 golden + дети-филиалы, parent-ссылка),
   нет связи ⇒ реальный дубль ⇒ мердж. Нужно: поле parent/`head_key` на `Counterparty` (миграция, хотспот)
   + ветка в `upsert` «не мерджить если филиал». **Моя полоса, не сделано.**
2. **🔴 Арбитраж.** 41 группа дубль-УНП (27 семья / 14 дубли) + 531 без-УНП (`upsert` их роняет).
   Без-УНП — не падать, а в очередь на ручной арбитраж (human-in-the-loop, approvals). **Моя полоса, не сделано.**
3. **🔴 ПДн-основание.** До физического забора 4766 записей (ФИО/контакты/реквизиты) — правовое
   основание обработки ПДн. **Решение владельца, не код.** Блокирует включение массового синка.

**Порядок (когда разблокируют):** parent-поле+иерархия (миграция 0055+) → арбитраж без-УНП/дублей →
расширить `_IMPORT_FIELDS` под новые мастер-поля → только потом синк-сессия включает массовый забор.
