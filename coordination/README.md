# coordination/ — оркестрация воркеров

Рабочая папка для `spawn_workers.py` (Windows). Оркестратор дробит большую
задачу на маленькие подзадачи и под каждую запускает воркера (`claude` в своём
окне Windows Terminal) в отдельном git-worktree.

## Поток

1. **Оркестратор пишет под каждую подзадачу два файла:**
   - `first-msgs/<name>.md` — первое сообщение воркеру (что сделать, цель).
   - `<name>-scope.md` — ТЗ с блоком `LOOP CONTRACT` (границы, budget, stop-условия).
   - В `LOOP CONTRACT` обязательны поля `model:` И `effort:` (канон —
     `coordination/MODEL-TIERING.md`); дефолт харнеса для Sonnet 5 / Opus 5 = `high`, поэтому
     механическим воркерам effort понижают ЯВНО.
2. **Спавн:** `python spawn_workers.py spawn <name>` — создаёт worktree
   `../crm-worker-<name>` + ветку `<name>` от `main`, копирует стандарты + scope,
   пишет skeleton-status, гасит trust-модал и запускает окно с claude. В промпт
   автоматически вшивается контракт (`worker-engineering-standards.md` +
   принципы `karpathy-guidelines`).
3. **Наблюдение:** `status` (таблица), `tail <name>` (хвост транскрипта).
   Воркер пишет прогресс в `<name>-status.md`, заканчивая баннером
   `STATE: COMPLETE` / `BLOCKED` / `NEEDS-ORCHESTRATOR-ANSWER`.
4. **Интеграция:** `integrate <name>` — мёрж ветки в `main` + boot-smoke + отчёт.
5. **Уборка:** `cleanup <name>` — снос worktree + ветки (только если всё влито).

## Что выбрать: нативный фоновый сабагент или headless-воркер (ревизия 25.07.2026)

`spawn_workers.py` писался тогда, когда платформа этого не умела. С Claude Code 2.1.198–2.1.219
бо́льшую часть его работы делает сам Claude Code, поэтому выбираем осознанно:

**Нативный фоновый сабагент** — `Agent(subagent_type: …, run_in_background: true, isolation: "worktree")`.
Брать по умолчанию, когда:
- подзадача укладывается в одну сессию (scoped task: список файлов + критерий проверки);
- нужен изолированный worktree — платформа создаёт его сама и убирает, если агент ничего не менял;
- на вопрос агента отвечаем `SendMessage` по его id — агент **не умирает** (фоновые сессии умеют
  штатно запрашивать ввод, CC 2.1.216), в отличие от нашего `STATE: NEEDS-ORCHESTRATOR-ANSWER`;
- статус/вывод — `TaskList`/`TaskGet`/`TaskOutput`, остановка — `TaskStop` (не парсим JSONL руками);
- нужна двухуровневая оркестрация: вложенность сабагентов — 3 уровня (координатор → лид → воркеры);
- лимиты: 20 одновременных, 200 спавнов на сессию, бюджет `--max-budget-usd` реально глушит.

**`spawn_workers.py`** — когда нужно то, чего натив не даёт:
- отдельное окно Windows Terminal, за которым оператор наблюдает и может вмешаться руками;
- воркер должен пережить смерть координаторской сессии (многочасовая полоса, ночной прогон);
- инъекция `memory/pitfalls.md` в промпт каждого воркера и `integrate` с boot-smoke + отчётом;
- отдельный процесс = отдельная сессия, а не одна из 20 сабагентских внутри координатора.

**Дублируется нативом** (не развивать в скрипте): создание/уборка worktree, опрос статуса через
парсинг транскрипта, `respond`, ожидание ответа оператора, ручной кап параллельности.

## Память флота (грабли)

Чтобы воркеры не наступали по очереди на одни и те же грабли, есть курируемый файл
`memory/pitfalls.md`:

- **RETRIEVE** — на `spawn` его содержимое автоматически вшивается в промпт каждого
  воркера (между контрактом и задачей). В консоли: `memory: pitfalls injected (N chars)`.
- **DISTILL** — воркер сам репортит неочевидные грабли в секции `## PITFALLS-DISCOVERED`
  своего status-файла; `integrate` их авто-собирает сюда (дедуп + авто-коммит). В консоли:
  `memory: +N pitfall(s) harvested`. Ручных действий не требует.

Файл плоский и без ранжирования (Crawl-уровень) — он вшивается в КАЖДЫЙ промпт, поэтому держи
его коротким: `integrate` предупредит ⚠, если разрастётся — тогда подчисти дубли/мусор.
Пустой/удалённый файл = фича просто выключена (graceful no-op).

## Команды

```powershell
$py = ".\.venv\Scripts\python.exe"
& $py spawn_workers.py health                 # проверка готовности
& $py spawn_workers.py list                   # известные воркеры
& $py spawn_workers.py spawn foo bar          # запустить foo и bar
& $py spawn_workers.py spawn foo --dry-run     # показать, ничего не делая
& $py spawn_workers.py status                  # статус по всем
& $py spawn_workers.py tail foo -n 30          # хвост транскрипта foo
& $py spawn_workers.py integrate foo           # влить ветку foo в main
& $py spawn_workers.py cleanup foo             # убрать worktree+ветку foo
```

## Файлы здесь

- `worker-engineering-standards.md` — контракт воркера (копируется в каждый worktree).
- `memory/pitfalls.md` — **память флота**: грабли, на которых горели прошлые воркеры;
  `spawn` вшивает их в промпт КАЖДОГО воркера (см. ниже).
- `first-msgs/<name>.md` — задания (вход оркестратора).
- `<name>-scope.md` — скоупы (вход оркестратора).
- `<name>-status.md` — статусы (пишет воркер).
- `integration-reports/` — отчёты интеграций.
- `.workers-state.json`, `.worker-*` — runtime (в `.gitignore`).

`example-healthcheck*` — демо-воркер для иллюстрации; можно удалить.

## Настройки (env, необязательно)

- `CLAUDE_CLI` — путь к claude.exe (иначе автодетект из VSCode-расширения).
- `WORKER_BASE_BRANCH` — базовая ветка (по умолчанию `main`).
- `WORKER_PERMISSION_MODE` — `auto` (деф. с 25.07.2026) / `bypassPermissions` / `acceptEdits` / `manual` /
  `dontAsk` / `plan`. В CC 2.1.200 режим переименован в `manual`; старое значение `default`
  продолжает приниматься CLI как алиас и в `--help` не показывается. Канон-имя в env — `manual`,
  `spawn_workers.py` сам нормализует `default` → `manual`.
- `WORKER_MODEL` — алиас модели воркера. ⚠️ значение `inherit` снимает `--model`, и модель
  воркера выбирает CLI/аккаунт — в этом проекте `.claude/settings.json` пиннит `"model": "opus"`,
  а алиас `opus` резолвится в Opus 5 ($5/$25 против $3/$15 у Sonnet 5), поэтому `inherit` даёт
  непредсказуемую цену прогона.
- `WORKER_GUARD` — включает/настраивает guard-проверку воркера.
- `WORKER_KEEP_WINDOW` — не закрывать окно Windows Terminal после завершения воркера.
- `WORKER_EFFORT` — ось effort воркера (деф. `medium`); per-worker переопределяется полем
  `effort:` в LOOP CONTRACT.
- `WORKER_BUDGET_USD` — бюджет воркера в USD (деф. 25), прокидывается в `--max-budget-usd`;
  per-worker — `budget: / max_usd:`; значение `0`/`off` выключает флаг.
- `WORKER_SUBAGENT_DEPTH` — глубина вложенности сабагентов воркера (деф. 1 — запрещает воркеру
  спавнить вложенных сабагентов).
- `WORKER_MAX_SUBAGENTS` — сколько сабагентов воркер может гонять одновременно (деф. 4).
- `WORKER_MAX_CONCURRENT` — лимит одновременных воркеров (деф. 5). Это кап ОКОН-процессов
  проекта (про квоту аккаунта), а не лимит харнеса: 20 одновременных сабагентов — потолок
  ПЛАТФОРМЫ (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), но `spawn_workers` сам режет воркера
  жёстче — выставляет `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=4` и
  `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` (переопределяются `WORKER_MAX_SUBAGENTS` /
  `WORKER_SUBAGENT_DEPTH`), 200 спавнов на сессию. 5 окон × вложенный фан-аут — расход, который
  легко недооценить.

## ⚠️ Безопасность (осознанное решение оператора)

Воркеры по умолчанию запускаются с `--permission-mode auto` (с 25.07.2026; до этого —
`bypassPermissions`). Прежнее обоснование — «любой другой режим завис бы на первой же
`pytest`/`git`/`bash`» — **проверено и оказалось неверным**: на живых прогонах CC 2.1.219
headless-воркер в `auto` не виснет и не падает. Вызов, требующий одобрения, отклоняется,
воркер доводит остальную работу и словами докладывает, чего ему не хватило. Проверены обе
формы — запись файла за пределами рабочего каталога и сетевая команда (`curl`).

Размен осознанный: часть задач вернётся не выполненной, а с «нужно разрешение». Решение о
таком шаге принимает оператор — воркер лишь докладывает. Это и есть требуемое поведение.

**Git-worktree — НЕ песочница**: та же файловая система, те же креды, та же сеть. Поэтому
`auto` — не замена гарду, а слой над ним: `auto` ловит неизвестное, `claude_guard_hook.py`
режет катастрофу и текстом отправляет воркера доложить координатору строкой `КООРД: BLOCKED`.
Кому нужно прежнее поведение — `--perm bypassPermissions` / `$WORKER_PERMISSION_MODE`.

Security-review (2026-06-10) пометил **прежний** дефолт `bypassPermissions` как HIGH, и оператор
тогда сознательно принял этот риск ради полного автонома. С 25.07.2026 риск не принимается, а
снимается: связка `auto` + allowlist — ровно тот путь «`--perm` + allowlist инструментов»,
который security-review называл лечением. Docker-песочница остаётся следующим шагом, если
понадобится больше.

⚠️ **Allowlist обязателен, а не украшение.** Под `auto` `git add/commit/push` требуют одобрения,
а одобрять в headless некому — воркер вернётся с «ожидаю подтверждения» и БЕЗ коммита (проверено
живым прогоном 25.07.2026). Взять правила ему неоткуда: `.claude/settings.json` и
`settings.local.json` в `.gitignore` и в worktree не попадают. Поэтому список рабочего
инструментария едет вместе с гардом в одном `--settings` — константа `WORKER_ALLOW` в
`spawn_workers.py`. Меняешь набор инструментов воркера — правь её, иначе воркер молча
перестанет сдавать работу.

Понизить разово: `spawn ... --perm acceptEdits`.

### Чем понижать риск СЕЙЧАС (ревизия 25.07.2026)

- **`WORKER_PERMISSION_MODE=auto` — рабочий путь.** Auto-режим (классификатор вместо диалогов)
  доступен без opt-in; в CC 2.1.218 проверки dangerous-`rm`, фонового `&` и подозрительных
  Windows-путей перестали открывать диалоги — их судит классификатор, поэтому headless-воркер
  на них больше НЕ виснет. Это и есть «`--perm default` + allowlist», ради которого раньше
  приходилось выбирать bypass. Отказы приходят с причиной; сброс состояния — `claude auto-mode reset`;
  ужесточить проверку шелла — ключ `autoMode.classifyAllShell`.
- **⚠️ Песочница Claude Code (`sandbox.*`) нам НЕ доступна.** Она работает только на macOS, Linux и
  WSL2; нативная Windows не поддерживается ([docs](https://code.claude.com/docs/en/sandboxing)).
  Значит ключи `sandbox.filesystem.disabled` / `sandbox.network.strictAllowlist` / `sandbox.credentials`
  из свежих релизов для нашей машины бесполезны — не тратить на них время. Настоящая изоляция для
  воркеров = WSL2 или Docker, это отдельное решение оператора.
- **Бюджет как страховка:** `--max-budget-usd` с CC 2.1.217 действительно останавливает фоновых
  сабагентов при достижении лимита (раньше не останавливал) — ставить на прогонах флота.
