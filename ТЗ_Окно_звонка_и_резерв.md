## 0. Цель

Два связанных рабочих контура продавца:

1. **Окно входящего звонка** — при звонке клиента система определяет номер; если он есть в ERP, звонок (и экранная карточка) идёт продавцу, за которым закреплён клиент. Продавец сразу видит, кто звонит, и краткую историю, и из того же окна работает: комментарий, переход в сделку, создание сделки, подбор позиций и счёт.
2. **Резерв товара под счёт** — продавец во время звонка подбирает позиции/количество и выставляет счёт; товар автоматически встаёт в резерв на срок действия счёта (**5 дней со дня выставления**, как в счёт-протоколе). За 1 день до окончания клиенту уходит напоминание, что счёт будет аннулирован и товар снят с резерва; по истечении срока — счёт аннулируется и резерв снимается.
3. **Договор по шаблону** — в том же звонке продавец согласовывает условия, выбирает шаблон договора, узнаёт УНП; по УНП реквизиты контрагента подтягиваются из госреестра (ЕГР РБ). Продавец уточняет детали — и договор с уже заполненными условиями оплаты, сроками поставки и пр. отправляется клиенту **вместе со счётом** единым пакетом.
4. **AI-скрипт звонка (со-пилот продавца)** — система предлагает скрипт результативного разговора и в реальном времени подсказывает ответы на реплики/возражения клиента, ведя разговор к результату (счёт/договор/следующий шаг).

# Часть A. Окно входящего звонка (SALES-50 + SALES-52)

## A.1. Сценарий (happy path)

1. Клиент звонит → **Asterisk/FreePBX** (события через **AMI/ARI**) → коннектор `integrations` получает `{caller, callee, call_id, direction:"in", started_at}` (события `Newchannel`/`DialBegin`/`Hangup` или ARI Stasis).
2. Коннектор нормализует номер в E.164 (`+375…`) и эмитит `telephony.call.incoming` (payload: `caller_e164`, `callee`, `call_id`, `started_at`).
3. Sales `on_incoming_call(payload, ctx)`:
   a. ищет номер в shared kernel: `Contact.phone` → `Counterparty`; параллельно `Lead.phone`;
   b. **резолвит продавца** (см. A.2);
   c. создаёт `CallLog` (status `ringing`);
   d. **push карточки** этому продавцу через SSE (см. A.5);
   e. эмитит `sales.call.logged` (→ audit; звонок учитывается в KPI как активность).
4. Продавец видит всплывающую карточку, принимает звонок, работает действиями (A.3).
5. По завершении провайдер шлёт `telephony.call.ended` (`call_id`, `status` answered\|missed\|busy, `duration_sec`, `recording_url?`) → sales обновляет `CallLog`.

**Краевые ветки:**
- **Номер не найден** → карточка «Новый номер», действие «Создать лид/сделку»; резолв продавца — `leads.route_lead` (дежурный/правило распределения). Дефолт: общий пул + черновик лида.
- **Несколько сделок/продавцов** на контрагента → берём owner последней **активной** (не `won`/`lost`) сделки; если все закрыты — ответственного за контрагента; иначе распределение.
- **Продавец оффлайн** (нет SSE-сессии) → карточка кладётся в «пропущенные», `CallLog.status=missed`, уведомление + задача «перезвонить».

## A.2. Резолв продавца (owner) — порядок правил

1. Активная сделка контрагента с заполненным `Deal.owner` → её owner.
2. Если несколько активных — последняя по `created_at`.
3. Нет активных, но контрагент известен — owner последней закрытой сделки.
4. Контрагент неизвестен (новый номер) — `leads.route_lead`/дежурный пул.

Резолв — **серверная логика sales** (знает сделки/контрагентов). Коннектор телефонии не знает про owner.

## A.3. Карточка звонка — содержимое и действия

**Шапка (кто звонит):**
- Контакт: имя, должность, телефон (нормализованный + исходный).
- Контрагент: название, УНП, регион; статус (клиент/лид/новый).
- Бейдж: «закреплён за вами» / «чужой клиент (owner: …)» / «новый номер».

**Краткая история (read-only сводка):**
- Активные сделки: номер · стадия · сумма (BYN) · `next_step` (кликабельно → A.4 «провалиться»).
- **Открытые счета в резерве:** номер · сумма · `valid_until` · сколько дней до аннулирования (связка с Частью B — продавец сразу видит «горящий» резерв).
- Последний контакт: дата + канал + краткий текст (`Message`).
- Открытые задачи по сделкам (`DealTask`, вкл. просрочку).
- (Опц., feature-flag `AIOS_AI_ENABLED`) AI-резюме отношений + предлагаемый `next_step`.

**Действия (кнопки):**
| Действие | Что делает | Бэкенд |
|---|---|---|
| **Комментарий** | заметка по звонку | `Message(channel=phone, direction=in)` + апдейт `CallLog.comment` |
| **Провалиться в сделку** | открыть карточку активной сделки | переход на `/crm/deals/{id}` |
| **Создать сделку** | новый `Deal`, предзаполнен контрагент/контакт, `owner`=этот продавец, `stage=in_work` | `POST /sales/deals` (+ link `CallLog.deal_id`) |
| **Создать лид** (новый номер) | черновик `Lead` из номера | `POST /sales/leads` |
| **Подобрать позиции / выставить счёт** | быстрый переход к подбору SKU и счёту | связка с Частью B (`POST /deals/{id}/items`, `…/documents` kind=invoice) |
| **Поставить задачу** | «перезвонить»/follow-up | `POST /deals/{id}/tasks` (`DealTask`) |
| **Запланировать встречу** | задача-встреча + стадия `meeting` | `DealTask` + переход стадии |
| **Отметить результат** | тема/итог/классификация звонка | `CallLog.result` |

**Поведение UI:** всплывает поверх (слайдовер/модал), переживает отказ, можно свернуть в «активный звонок» в шапке; история звонков — отдельная вкладка.

## A.5. События и push (SSE)

- **Вход:** `telephony.call.incoming` / `telephony.call.ended` (от коннектора `integrations` поверх Asterisk AMI/ARI).
- **Выход (sales emit):** `sales.call.logged` (→ audit, KPI-активность), `sales.call.ended`.
- **Push продавцу:** SSE-эндпоинт `GET /sales/calls/stream` (подписка по текущему пользователю); сервер держит реестр активных подписок «owner → очередь». На `on_incoming_call` карточка пушится в очередь нужного owner. Fallback при отсутствии подписки — `status=missed` + задача.

> SSE выбран как минимально-инвазивный (одностороннее серверное событие, без отдельного WS-стека). Реестр подписок — in-process (как фоновый цикл ядра); при масштабировании — вынести в Redis pub/sub (заложить, не реализовывать сейчас).

# Часть B. Резерв товара под счёт + срок 5 дней (SALES-51)

## B.1. Жизненный цикл счёта с резервом

```
draft ──post──► posted ──reserve──► [reserved, valid_until = +5 дн]
                                         │
                 (valid_until − 1 день)  ├─► sales.invoice.expiring → напоминание клиенту + продавцу (reminded_at)
                                         │
                 оплата (finance.payment.paid / status=paid)
                                         ├─► reserve_status = consumed → передача в отгрузку
                                         │
                 истёк (valid_until) и не оплачен
                                         └─► status = cancelled, stock.release → reserve_status = released,
                                             события sales.invoice.cancelled + sales.stock.released
```

- **Резервируют склад:** `invoice` **и** `order` (расширяем `RESERVES_STOCK = {"invoice", "order"}`). Договор (`contract`) — нет.
- Резерв ставится по позициям сделки (`DealItem`: `sku_id`, `qty`) после `posted`.
- Продавец может: продлить (перевыставить новый счёт), отменить резерв раньше срока, оплатить (→ consumed).
- **Если остатка не хватает** — частичный резерв + позиция «под заказ» уходит на подтверждение закупщику; счёт клиенту отправляется авто **только после** подтверждения. См. **B.7**.

## B.2. Поля `DealDocument` + миграция

Добавить:
```
valid_until     date|null      # срок действия (created + 5 дней); только для kind in RESERVES_STOCK
reserve_status  str(16)        # none | reserved | released | consumed   (default none)
reserved_at     datetime|null
reminded_at     datetime|null  # когда отправлено напоминание (идемпотентность)
cancelled_at    datetime|null
```
`status` получает значение `cancelled` (к существующим draft/posted/paid). Миграция Alembic `00NN_sales_invoice_reserve`.

**Срок:** `valid_until = created_date + 5 календарных дней` (буквально «5 дней со дня выставления» из счёт-протокола). Срок — конфигурируемый (`AIOS_INVOICE_VALID_DAYS`, дефолт 5).

## B.3. Фоновые задачи (в цикле ядра)

Добавить в `_background_loop` (рядом с `relay_once`/`escalate_once`) шаг `invoice_reserve.tick`:
- **Напоминание:** счета с `reserve_status=reserved`, `status≠paid`, `reminded_at IS NULL`, `today ≥ valid_until − 1 день` → эмит `sales.invoice.expiring` (payload: deal_id, document_id, number, valid_until, counterparty, contact, amount) → проставить `reminded_at`. Обработчик уведомления шлёт клиенту по **email контакта контрагента** и **дублирует в Telegram, только если есть активный диалог** с клиентом (`Message(channel=telegram, direction=in)` за окно N дней); продавцу — in-app.
- **Аннулирование:** счета с `reserve_status=reserved`, `status≠paid`, `today > valid_until` → `stock.release(session, items)`, `status=cancelled`, `reserve_status=released`, `cancelled_at=now`; эмит `sales.invoice.cancelled` + `sales.stock.released`.
- Идемпотентность — через флаги (`reminded_at`, `reserve_status`), не по времени.

> Реализуется как функция `tick_invoice_reserve(session, services)` в sales, вызываемая из фонового цикла; в SQLite-тестах вызывается напрямую (без таймера).

## B.4. Контракт `stock.release`

Расширить Protocol (`core/services/stock.py`) — **объявление контракта в моей полосе, реализация в `integrations`**:
```python
class StockGateway(Protocol):
    async def reserve(self, session, items: list[dict]) -> list[dict]: ...
    async def release(self, session, items: list[dict]) -> list[dict]: ...   # снятие резерва
```
Если коннектор склада выключен — `release`/`reserve` отдают 503 (как сейчас). На уровне sales резерв пишем оптимистично + событие; фактическое движение остатков — за `integrations`/1С.

## B.5. Счёт-протокол (печатная форма)

Печатная форма счёта (PDF/HTML) содержит фразу-оговорку: **«Счёт действителен 5 дней со дня выставления. Указанный товар зарезервирован на складе на срок действия счёта; по истечении срока счёт аннулируется и резерв снимается.»** + дату `valid_until`. Текст — параметр шаблона (срок берётся из `AIOS_INVOICE_VALID_DAYS`).

## B.6. События и KPI

- Новые: `sales.invoice.expiring`, `sales.invoice.cancelled`, `sales.stock.released`.
- `sales.stock.reserved` — переиспользуем (расширяем на invoice).
- Оплата: уже есть `finance.payment.paid` → счёт `paid`; добавить переход `reserve_status → consumed`.
- KPI: аннулированные счета — отдельный анти-показатель (сорванные резервы) для аналитики РОПа (данные закладываем, экран РОПа — вне scope).

## B.7. Дефицит остатка → частичный резерв + подтверждение закупщика

Когда при выставлении счёта остатка хватает не на весь объём позиции:

1. **Частичный резерв:** `stock.reserve` резервирует доступное кол-во; недостающее (`shortfall = qty − available`) помечается как **«под заказ»** на позиции счёта.
2. **Срок заказа в счёте:** в позиции «под заказа» учитывается срок поставки (ожидаемая дата), который попадёт в печатную форму счёта.
3. **Подтверждение закупщика (НЕ авто-отправка клиенту):** счёт с позициями «под заказ» переходит в статус **`pending_supply`** (не `posted`-для-клиента) и эмитит `sales.invoice.supply_requested` → закупщик подтверждает по дефицитным позициям **возможность заказа**, **срок** и **цену**.
4. **После подтверждения** (`procurement.supply.confirmed` / решение через approvals-движок): сроки/цены проставляются в счёт, статус → `posted`, и счёт **автоматически отправляется клиенту** (email + Telegram по правилу B.3), резерв доступной части активен, `valid_until` отсчитывается от момента отправки клиенту.
5. **Если закупщик отклонил** (нельзя заказать / неприемлемый срок) → счёт возвращается продавцу (`supply_rejected`), продавец корректирует позиции/кол-во или предлагает альтернативу.

**Данные:** на позицию счёта/`DealItem` — `reserved_qty`, `backorder_qty`, `supply_eta` (date), `supply_price` (BYN, от закупщика). Статусы `DealDocument.status` дополняются: `pending_supply` (ждёт закупщика), `supply_rejected`.

**События:** `sales.invoice.supply_requested` (sales→procurement), подписка на `procurement.supply.confirmed` / `procurement.supply.rejected`. Конкретный механизм подтверждения (approvals-движок ядра vs прямой эндпоинт закупщика) — согласовать с сессией **procurement** (межмодульная граница, §3).

> **Граница:** подтверждение возможности/срока/цены — зона **procurement** (закупки). Sales формирует запрос и потребляет ответ через события; экран закупщика и логику подтверждения здесь не делаем. До готовности procurement — ручная заглушка подтверждения (эндпоинт `/sales/documents/{id}/supply-confirm` под правом РОПа) для сквозного теста.

# Часть C. Договор по шаблону + авто-реквизиты по УНП (SALES-53)

## C.1. Сценарий (в окне звонка)

1. Продавец согласовал условия → жмёт **«Подготовить договор»**, выбирает **шаблон** (`contract_template`).
2. Вводит/подтверждает **УНП** контрагента → бэкенд `core.services.registry.lookup(unp)` (ЕГР РБ, через `integrations`) подтягивает реквизиты: наименование, адрес, директор/ЛПР, статус, дата регистрации.
3. Реквизиты проставляются в `Counterparty` (обогащение по УНП — через существующий механизм sales, без правки shared-схемы) и подставляются в договор.
4. Продавец уточняет условия (оплата, сроки поставки, спецификация/цены, ответственность) — частично **предзаполнены из сделки/счёта** (позиции `DealItem`, суммы BYN, `supply_eta` из B.7).
5. Договор формируется как `DealDocument(kind=contract)` → согласование (`REQUIRES_APPROVAL={"contract"}`, как сейчас) → после `decide` договор + счёт уходят клиенту **единым пакетом** (см. C.4).

## C.2. Шаблоны договора — `contract_template` (схема `sales`)

```
contract_template
  id            PK
  code          str(64) unique
  title         str(255)
  body          text          # шаблон с плейсхолдерами {{...}}
  kind          str(32)       # поставка | разовый | рамочный | оферта
  active        bool
  created_at    datetime
```
Плейсхолдеры: реквизиты сторон (`{{seller.*}}`, `{{buyer.unp}}`, `{{buyer.name}}`, `{{buyer.address}}`, `{{buyer.director}}`), предмет/спецификация (из `DealItem`), `{{payment_terms}}`, `{{delivery_terms}}`, `{{valid_until}}`, суммы BYN. Рендер — server-side в HTML/PDF (как печатная форма счёта B.5).

## C.3. Условия договора на документе

На `DealDocument` (для `kind=contract`) добавить:
```
template_id    int|null      # FK sales.contract_template
payment_terms  str(255)|null # предоплата 100% / отсрочка N дней / по факту
delivery_terms str(255)|null # срок и условия поставки (вкл. supply_eta)
terms_json     json|null     # прочие согласованные условия (структурно)
```
Реквизиты покупателя берём из `Counterparty` (обогащён по УНП); продавца — из настроек организации (конфиг/справочник, не хардкод).

## C.4. Отправка пакетом «договор + счёт»

После согласования договора: эндпоинт `POST /sales/deals/{id}/send-package` собирает **счёт + договор** (PDF) и отправляет клиенту по правилу B.3 (email контрагента + Telegram при активном диалоге); эмит `sales.package.sent`. В истории сделки — одна запись «отправлен пакет: счёт №… + договор №…».

## C.5. Граница

`registry.lookup` (ЕГР РБ) реализует `integrations` (контракт уже в `core/services/registry.py`) — sales вызывает через фасад, при выключенном шлюзе реквизиты вводятся вручную (graceful). Рендер PDF — серверная утилита sales (общая со счётом). Справочник реквизитов **своей** организации — конфиг, не shared-схема.

# Часть D. AI-скрипт звонка — со-пилот продавца (SALES-54)

## D.1. Назначение

Система помогает провести **результативный звонок**: до/в начале разговора предлагает **скрипт** под контекст (стадия сделки, история, продукт, тип клиента), а в ходе разговора **подсказывает ответы на реплики/возражения** клиента и ведёт к результату (счёт / договор / следующий шаг). За feature-flag `AIOS_AI_ENABLED` (при выкл — статичные скрипты-шаблоны, без live-подсказок).

## D.2. Поведение

- **Скрипт под контекст:** при поднятии карточки звонка (Часть A) AI генерирует план разговора: цель звонка (по стадии воронки), 3–5 ключевых тезисов, вопросы для квалификации, предложение следующего шага. Источник контекста — сделки/история/позиции из карточки + `ai.py` (`next_step`, `summarize`).
- **Подсказки в реальном времени:** продавец отмечает возражение/реплику (выбор из частых или ввод) → AI предлагает 1–3 варианта ответа (работа с возражением: дорого→ценность, нет в наличии→срок заказа из B.7, думают→следующий шаг). Реактивно, как `on_incoming_message_ai`, но синхронно по запросу из карточки.
- **Ведение к результату:** AI подсказывает целевое действие текущей стадии (запросить цену, выставить счёт, подготовить договор) и формирует `next_step`/задачу по итогу.
- **Итог звонка:** AI-резюме разговора → `CallLog.result` + предложенный `next_step` (продавец подтверждает).

## D.3. Реализация

- Расширить `modules/sales/ai.py`: `call_script(context)` (генерация скрипта), `objection_reply(objection, context)` (ответы на возражение). Через шлюз `core.services.llm` (`enabled`/`model`/`complete`).
- Эндпоинты: `POST /sales/calls/{id}/ai/script`, `POST /sales/calls/{id}/ai/objection` (503 при выключенном AI; fallback — статичные скрипты из справочника).
- События: `ai.call_script.generated`, `ai.objection.suggested` (с `actor:"AI"` → audit), как прочие AI-события sales.
- **Без распознавания речи в этой итерации:** подсказки — по выбору/вводу продавца, не по live-транскрипту звонка (ASR — отдельная фаза, заложить точку расширения: транскрипт от телефонии → стрим в AI).

## D.4. Граница

AI-слой за feature-flag (как весь AI sales). LLM — через `core.services.llm`. ASR/транскрипция звонка — будущая фаза (зависит от записи разговора Asterisk, §A/integrations).

## 2. Порядок реализации (моя полоса, sales-only сначала)

1. **SALES-51 (резерв, без телефонии):** поля `DealDocument`/`DealItem` + миграция → расширить резерв на `invoice` + `valid_until` → `tick_invoice_reserve` + события → контракт `stock.release` → **B.7 дефицит:** частичный резерв + `pending_supply` + запрос закупщику + авто-отправка после подтверждения (заглушка `/supply-confirm` до готовности procurement) → печатная форма. *Тесты:* выставление счёта ставит резерв и `valid_until=+5`; дефицит → частичный резерв + `pending_supply`, клиенту НЕ ушло; подтверждение → `posted` + авто-отправка; tick за −1 день шлёт `expiring` один раз; tick после срока → `cancelled`+`released`; оплата → `consumed`.
2. **SALES-50 (окно звонка, sales-часть):** `call_log` + миграция → `on_incoming_call` резолв owner → SSE `/calls/stream` → эндпоинты журнала/действий. *Тесты:* резолв owner по номеру (4 правила), идемпотентность по `call_id`, missed при оффлайне.
3. **SALES-53 (договор по шаблону):** `contract_template` + миграция → поля условий на `DealDocument` → рендер договора по шаблону + `registry.lookup` (graceful при выкл) → `/send-package` (счёт+договор). *Тесты:* подстановка реквизитов по УНП; рендер с предзаполнением из сделки; пакет отправлен одной записью.
4. **SALES-54 (AI-скрипт):** `ai.py` `call_script`/`objection_reply` + эндпоинты + события; fallback на статичные скрипты при выкл AI. *Тесты:* 503/fallback при выключенном флаге; формат скрипта/подсказок.
5. **SALES-52 (коннектор телефонии, `integrations`):** webhook + нормализация E.164 + эмит событий. **Координация — вне полосы sales.** До готовности — `POST /sales/telephony/incoming` как заглушка-вход для ручного/тестового триггера.
6. **Frontend:** провайдер «активный звонок» + `IncomingCallCard` (с панелью AI-скрипта) + вкладка «Звонки»; кнопки «Подготовить договор»/«Отправить пакет»; в карточке счёта — бейдж резерва/срока.

## 3. Связь с другими сессиями

- **РОП-вкладка** (чужая сессия): потребляет `sales.invoice.cancelled`/`sales.call.logged` для аналитики — только события, экран не делаем.
- **finance** (оплаты): `finance.payment.paid` → `reserve_status=consumed`.
- **procurement** (закупки): подтверждение возможности/срока/цены по дефицитным позициям (B.7) — `sales.invoice.supply_requested` ↔ `procurement.supply.confirmed/rejected`; механизм подтверждения согласовать.
- **integrations** (телефония Asterisk AMI/ARI + `stock.release`): контракт здесь, реализация там — синхронизировать через `coordination/`.
- Push не делать — только локальные коммиты (submodule + bump указателя).
