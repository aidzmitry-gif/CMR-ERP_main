# ship-cycle — стандартный конвейер закрытия цикла

Заменяет ручной 4-шаговый ритуал, повторявшийся 12–16 раз за сессию (аудит 10–16.07).

## Шаг 0 — design-fork check (ДО реализации, если цикл ещё не реализован)

Один AskUserQuestion, если план цикла содержит хотя бы одну развилку:
- новый UI-элемент управляет тем же параметром/данными, что уже существующий
  (пример из аудита: переключатель «Чья доска» дублировал фильтр `?owner=` — выпилен через 9ч);
- добавляется ≥2-я однотипная панель/кнопка/очередь — спросить «отдельно или объединить»
  (пример: три панели пересобраны в кокпит на цикле 13 вместо цикла 1);
- в вёрстку попадают чувствительные данные (реквизиты/контакты/цены) — судьба: реальные /
  пример с пометкой / плейсхолдер.

Ответ записать в `coordination/DECISIONS.md` (дата, тег развилки, решение). Перед вопросом —
проверить, не закрыта ли развилка там ранее: закрытую не переспрашивать.

В headless-режиме (`claude --print`) AskUserQuestion НЕДОСТУПЕН — вопрос не задавать. Записать
нерешённую развилку в `coordination/DECISIONS.md` (или в свой status-файл, если работаешь
воркером) и остановиться, НЕ реализуя спорный пункт.

## Шаг 1 — гейты (одной командой, не набором отдельных вызовов)

- Python-правки: `powershell -ExecutionPolicy Bypass -File scripts/gate-py.ps1 <тест-файлы циклa>`
  (без аргументов — полный pytest; точечные тесты в цикле, полный прогон — раз перед коммитом).
- Frontend-правки: `npm run gates` в `frontend/` (typecheck+lint+vitest по изменённым);
  перед коммитом — `npm run gates:full`.
- Красный гейт = цикл не закрыт. Чинить, не обходить.

## Шаг 2 — коммит (правила общей ветки!)

- Staged — ТОЛЬКО свои файлы, `git add` по именам (НИКОГДА `add .` — в дереве чужой WIP).
- Если правился submodule (`modules/*`): коммит сначала в репо submodule, потом указатель
  в суперпроекте (иначе CI падает на gitlink).
- НИКАКОГО amend/reset/rebase на общей ветке. Только новый коммит.
- Формат сообщения: `feat|fix(<модуль>): <суть по-русски>` + trailer
  `Co-Authored-By: Claude <модель> <noreply@anthropic.com>`.

## Шаг 3 — ревью (ЗВАТЬ ЯВНО — само не запустится)

> ⚠️ С Claude Code 2.1.215 ассистент НЕ запускает `/code-review` и `/verify` по своей
> инициативе. Этот шаг обязателен и делается явной командой, иначе цикл закрыт без ревью.

Порядок по стандарту проекта (CLAUDE.md): **`/code-review` → `/simplify`**.
- `/code-review` с 2.1.218 идёт **фоновым сабагентом**: контекст сессии не забивается,
  результат приходит уведомлением. Не поллить его и не выдумывать вердикт заранее —
  дождаться уведомления.
- `/simplify` — чистка (reuse/упрощение/удаление), применяет правки сам.

Если нужен точечный ревьюер под конкретный коммит (а не диф ветки) — спавнить субагента
(тир Sonnet, `effort: medium`; деньги/безопасность/миграции — Opus 5, `effort: high` —
см. [MODEL-TIERING.md](../../../coordination/MODEL-TIERING.md)):

> Ревью коммита `<sha>` в «D:\6 Проекты\CRM ERP\Сlaude CRM - проект»: `git show <sha>`.
> Проверь по стандарту проекта (CLAUDE.md: лестница лени, репозитории-не-коммитят,
> transactional outbox, RBAC-слаги). Верни только реальные дефекты с file:line и
> минимальным фиксом; стилистику без последствий не тащи.

Сабагенты с 2.1.198 **фоновые по умолчанию** — спавнить и продолжать работу, результат
придёт уведомлением. Фиксы дефектов — отдельным коммитом тем же конвейером.
Вердикт ревьюера — в отчёт цикла.

## Шаг 4 — след

- PLAN.md: пункт цикла → ✓ (или «отложено/отменено» + причина одной строкой).
- Если сессия пережила ≥2 компакции или живёт ≥3 дня — закрыть её на этой вехе
  (см. CLAUDE.md, гигиена сессий). Побочную ветку работы отпочковать через `/fork`
  (копия диалога в фоновую сессию), а не тянуть в текущей.
