# UI-crawl — обход экрана, проверка кнопок и вёрстки, починка

Цель: за один проход убедиться, что **(а)** каждый интерактивный элемент имеет действие и
делает то, что должен, и **(б)** текст и картинки отображаются корректно (без наложений,
обрезки, вылета за экран, кривых переносов, мелкого шрифта). Найденное — чинится и
перепроверяется.

## Когда использовать

- «Проверь, что все кнопки работают / пройдись по экрану / прокликай всё».
- «Проверь вёрстку: наложения, переносы, обрезку текста, читаемость».
- После сборки/правки любого HTML-макета или страницы перед показом.

## Предусловия

1. **Локальный сервер** (file:// ограничивает часть проверок и кэширует):
   ```bash
   cd "<папка с макетами>" && python -m http.server 8899
   ```
   Открывать как `http://localhost:8899/<файл>.html?v=N` — `?v=N` сбивает кэш браузера.
2. **Playwright MCP** включён (`/mcp`). Инструменты: `browser_navigate`, `browser_evaluate`,
   `browser_click`, `browser_console_messages`, `browser_take_screenshot`, `browser_resize`.
   ⚠️ Профиль Chrome занят, если у пользователя открыто своё окно на том же профиле
   (`Browser is already in use`) — попросить закрыть это окно.

## Процедура (по каждому экрану)

### 1. Статический аудит обработчиков (быстро, без браузера)
Запустить на файлах:
```bash
node "<путь к скиллу>/scripts/handler-audit.mjs" file1.html [file2.html ...]
```
Выдаёт: функции, вызванные в `onclick/oninput/onchange/onkeydown`, но **не определённые**;
проверку синтаксиса каждого `<script>`-блока. Цель — `MISSING: none ✓` и `JS OK ✓`.

### 2. Живой click-through (браузер)
- `browser_resize` к эталонной ширине (десктоп: 1440×900; затем узкий: 768 и 390 для адаптива).
- `browser_navigate` на `…?v=N`, затем `browser_console_messages level:error` — **0 ошибок**
  (favicon 404 игнорировать).
- Вставить функцию из `scripts/browser-audit.js` в `browser_evaluate` — она вернёт:
  - `deadClickables` — элементы с `cursor:pointer`/кнопки/ссылки **без** обработчика и без
    делегирования (кандидаты в «мёртвые»);
  - `onclickBad` — обработчики, ссылающиеся на неопределённые функции;
  - `visual` — список визуальных проблем (см. §3).
- Для **каждого** найденного интерактивного элемента (и для переходов между состояниями/
  модалок) — кликнуть и зафиксировать: меняется ли DOM/состояние, нет ли ошибки в консоли,
  совпадает ли результат с ожиданием. Для data-driven экранов проверять изменение модели
  (массивы/итоги), а не только текст.
- ВАЖНО: делегированные обработчики (один listener на `document` для `.seg button` и т.п.)
  не видны как `onclick` — не считать их мёртвыми; проверять кликом.

### 3. Визуальный аудит (в той же `browser_evaluate`)
`scripts/browser-audit.js` помечает:
- `pageScrollX` — на странице появился горизонтальный скролл (что-то шире вьюпорта);
- `beyondViewport` — элементы, выходящие за правый край экрана (не `position:fixed`);
- `clipped` — одностолбцовый текст обрезан (`scrollWidth > clientWidth` при `overflow:hidden`);
- `overlap` — пары соседних текстовых элементов, чьи прямоугольники накладываются;
- `tinyText` — шрифт < 11px на непустом тексте (риск читаемости).
Прогонять на 1440, 768 и 390 px — переносы и наложения часто проявляются только на узком.
- **Скриншоты** ключевых состояний (`browser_take_screenshot`) — финальный судья по
  читаемости/наложениям, которые эвристики не ловят (контраст, эстетика, «слиплось»).

### 4. Отчёт
Свести в таблицу: `элемент | ожидание | факт | вердикт (✅/no-op/🐞/визуал)`. Сначала
показать сводку приоритетов.

### 5. Починка и перепроверка
- Мёртвой кнопке — дать **осмысленное** действие: рабочие операции над данными (переход
  стадии, добавление в заказ, фильтр) делать по-настоящему; вспомогательным (отправить по
  каналу, скачать) — подтверждающий тост, чтобы не было «ничего не произошло».
- Визуал: чинить переносы/обрезку через `min-width:0`, `flex-wrap`, `white-space`,
  `text-overflow:ellipsis`, корректные ширины грид-колонок; вылет за экран — `max-width:100%`,
  `box-sizing`, убрать фикс-ширины.
- После правок — повторить §1–3 на затронутом экране. Цель: 0 mismatch, 0 ошибок консоли,
  пустой `visual`.

## Подводные камни

- Один `browser_evaluate` с цепочкой действий может давать ложные срабатывания из-за
  состояния от предыдущих шагов — спорные кейсы проверять **изолированно** на свежей загрузке.
- `render()`-перерисовка сбрасывает фильтры/инлайн-состояние — это нормально.
- Эвристика `overlap`/`clipped` шумит (абсолютное позиционирование, декоративные слои) —
  доверять, но сверять глазами по скриншоту.
- Не коммитить мусорные скриншоты Playwright (`.playwright-mcp/`).

## Связки

- Большой объём независимых экранов → распараллелить через `orkestrator-lead`.
- Глубокий разбор логики/код-ревью изменений → отдельный проход ревьюером.
