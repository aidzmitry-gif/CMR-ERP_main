# CRM-ACC-FIN-PNL-002 — прибыль из бухгалтерской книги

## Проверенное состояние 2026-09-19
Baseline integration 76b5c6c; Finance b10cf60. Это контракт следующего пакета, не отчёт о выполнении.

- modules/finance/pnl.py считает landed расходом; frontend/src/components/erp/finance-view.tsx PnlTab вызывает /finance/pnl и называет результат операционной прибылью. Этот источник нельзя использовать для бухгалтерской прибыли.
- modules/accounting/sales.py posting_for уже объединяет признание продажи и списание стоимости 41 -> 90.4; inventory_issues.py использует inventory_cost и подтверждаемые receipts. Закупка сама по себе не расход продажи.
- modules/accounting/reports.py report считает pnl по immutable Entry/Line, исключает подтвержденные технические закрытия, ограничивает organization_id/posting_date, возвращает status/review_items/pending_documents/statutory_certified и расшифровки movements.
- GET /accounting/organizations/{org_id}/reports?start=...&end=... уже существует и защищён member (routes.py). accounting-view.tsx уже использует его и показывает прибыль. Новый API, таблица и второй расчёт прибыли не нужны.
- tests/accounting/test_shipment_reports_postgres.py содержит сценарий: поступление10 -> расход0; отгрузка одной из3ед -> доход20, расход3.33, прибыль16.67, остаток6.67; replay неизменен. В этом пакете прочитан исходник теста, новый PostgreSQL запуск НЕ выполнялся и PASS не заявляется.

## Следующее пользовательское изменение
Во вкладке Финансы/P&L показать отчёт по бухгалтерской книге выбранного доступного юрлица и периоду, используя существующий accounting endpoint. Не выбирать автоматически основную компанию. Суммы: Доходы, Расходы, Финансовый результат — точные поля pnl.income/expenses/profit. Не обозначать весь expenses как COGS и весь profit как operating_profit: классификации в этом API нет. Дать расшифровку по исходным проводкам, сохраняя source/entry_id/account и даты; переиспользовать существующую бухгалтерскую навигацию где она поддерживает переход.

Всегда показывать preliminary/closed_periods, pending_documents и review_items. closed_periods не означает statutory_certified. Нет доступа/нет организации/ошибка API -> явное состояние без подстановки legacy результата или нулей. При смене компании/дат старый или опоздавший ответ не должен показываться под новыми фильтрами.

CSV должен соответствовать именно показанному отчёту (его organization_id/from/to), а не текущим ещё не применённым полям формы. Экспорт несёт статусы/ограничения, суммы без изменения точности, корректное экранирование. Старый /finance/pnl остаётся технически совместимым до отдельной миграции потребителей; пользователю не представлять его как бухгалтерский результат.

## Ownership и проверка
После завершения текущего nullable-balance UI пакета один владелец frontend/src/components/erp/finance-view.tsx и связанного компонента/теста. Не пересекаться с Luna. Accounting mapping worktree и его routes/models/migration не трогать; Finance backend в этом пакете не нужен.

Проверить существующий API-контракт на синтетическом отчёте, выбор компании и403, незакрытый период, pending источники, stale response при смене компании/дат, вывод и CSV одинаковых примененных фильтров. Проверить что закупка без отгрузки не отображается как расход: переиспользовать существующее shipment-report evidence; повторять PostgreSQL только если меняется его код/контракт или evidence устарело. Не запускать полный suite и не расширять покрытие ради процентов. Браузерная приёмка заполненного сценария обязательна перед признанием UI готовым.

## Границы готовности
Этот пакет подключает уже имеющуюся бухгалтерскую прибыль, но не доказывает полноту первичных документов, нормативную актуальность, закрытие месяца или готовность отказаться от1С. Корректность проводок/стоимости и поздних расходов остаётся обязательной; пропущенные документы не превращаются в подтверждённую нулевую прибыль.
